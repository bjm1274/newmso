# 메뉴 전수조사 보고서 — 채팅 (메신저)

> 조사 대상: `app/main/기능부품/메신저*.ts(x)` + `chatQueryService.ts` + `useChatTypingD1.ts` (약 50개 파일)
> 특징: 단일 진입점 `메신저.tsx`(3588줄)가 20여 개 훅을 조합하는 대규모 메신저

## 1. 메뉴 개요

채팅은 병원 메신저다. 1:1/그룹 대화, 공지방, 병동 퀵리플라이, 투표, 반응, 고정, 스레드, 멘션, 첨부(이미지/영상/파일), 재시도 큐, 예약 공지, 타이핑 상태, 읽음 표시를 지원한다.

## 3. 기능별 상세 분석

### 3.1 데이터 계층
- **chat_rooms**: Postgres(`db`)에서 조회, `chatQueryService`가 60초 TTL 캐시 + localStorage 캐시 + missing-column fallback.
- **messages**: `selectChatMessagesWithFallback`으로 조회. 첨부 메타는 `메신저첨부`의 hidden-meta 블록으로 인코딩.
- **notifications(D1)**: 메시지/멘션 미읽음 알림을 `d1`로 별도 관리. 방 읽음 처리 시 `metadata.room_id`를 JS로 매칭해 50개 단위 청크 업데이트.

### 3.2 실시간 동기화
- `useChatRealtimeSubscriptions` → `subscribeRealtime`(polling-bus)로 메시지/방 변경 구독.
- WS 활성 시 `pokeChannel`로 즉시 반영, 비활성 시 5초 폴백 폴링.

### 3.3 메시지 전송/재시도
- `useChatMessageSending` → `createOrUpsertChatRoom` → `triggerChatPush`(백그라운드 푸시 fire-and-forget).
- 전송 실패 시 `메신저재시도큐`에 보관, `RetryQueueBanner`로 노출.

### 3.4 읽음 처리
- 방 진입 시 `markConversationNotificationsAsRead`가 D1 notifications의 message/mention을 읽음 처리.
- 전체 unread=0 확인 시에만 0으로 확정된 방 알림을 일괄 읽음 처리(전역 wipe 방지).

### 3.5 특수 메시지
- **공지방**: `NOTICE_ROOM_ID` + `CAN_WRITE_NOTICE_POSITIONS`(대표/부장/팀장 등)만 작성 가능.
- **병동 메시지**: `[[WARD_MESSAGE_META]]` 블록으로 환자명/차트번호/수술명 메타 인코딩, 퀵리플라이 4종.
- **투표**: `[[POLL_META]]` 블록으로 마감/익명/경품/강퇴 투표 메타 인코딩.
- **스레드/반응/고정**: `메신저파생훅`·`메신저스레드패널`에서 처리.

## 4. 발견된 문제점 / 잠재 리스크

### 🔴 중대 (기능 결함 가능성)
1. **`메신저.tsx` 3588줄 단일 컴포넌트** — 20여 개 훅 조합 + 인라인 로직 혼재. 유지보수성 심각. 부분 수정 시 회귀 위험 높음.
2. **이중 데이터소스 정합성** — chat_rooms는 Postgres, 메시지/알림은 D1(notifications) 분리. 읽음 처리·미읽음 집계가 양쪽 저장소를 교차 참조하므로 시차/불일치 가능성.

### 🟡 경미 (품질/리스크)
3. **메타 인코딩을 문자열 블록(`[[WARD_MESSAGE_META]]`, `[[POLL_META]]`)으로 처리** — content 컬럼에 JSON을 숨겨 넣는 방식. 파싱 실패 시 폴백은 있으나, 정규화/검색/마이그레이션에 취약.
4. **D1 JSONPath 미지원 우회** — `metadata->>room_id` 필터 대신 JS 매칭 후 50개 단위 청크 업데이트. 데이터 많아지면 성능 저하.
5. **캐시 TTL 60초 + localStorage 캐시** — WS 단절 시 최대 60초 stale 데이터 노출 가능.
