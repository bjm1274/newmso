# 추가기능 5종 → allemr(EMR) 이식 타당성 보고서

> 작성일: 2026-06-02 · 대상: newmso ERP 추가기능 5종(OP체크·퇴원심사·인계노트·수술상담·마감보고)
> 방식: 기능별 코드 5그룹 병렬 정독(Sonnet) + 종합(Opus). 파일:라인 근거 기반. 코드 수정 없음(분석 전용).
> 전제: `allemr`는 newmso 외부 시스템(코드 내 참조 0건) — 별도 EMR로의 **코드 이식**을 검토.

## 1. 공통 이식 인프라 (5종 전체 공유 — 한 번 구축하면 재사용)

5개 기능을 개별적으로 보지 말고, **공통 어댑터 레이어를 먼저 구축**하면 기능별 재작업이 크게 줄어듭니다. 5종이 공유하는 newmso 결합점:

| 공통 의존 | 사용 기능 | 이식 시 처리 |
|----------|----------|-------------|
| `@/lib/supabase` (D1 호환 클라이언트) | 5종 전부(수술상담 PC 제외) | **EMR DB 어댑터 1개 구축** → `.from().select/insert/upsert/delete` 인터페이스 호환 shim 만들면 쿼리 코드 대부분 보존 |
| `@/lib/supabase-compat` (`withMissingColumnsFallback`) | OP체크·인계노트 | EMR이 **완전 스키마**를 처음부터 정의하면 폴백 래퍼 **제거**(불필요) |
| `useActionDialog` / `toast` | 5종 전부 | EMR 디자인 시스템의 Dialog/Toast로 단순 교체 |
| `@/lib/access-control` | 마감보고·(공통 권한) | EMR RBAC로 교체 |
| PHI 평문 저장 | OP체크·퇴원심사·인계노트·수술상담 | **환자 마스터 FK 연계 + 암호화/접근제어**(ISMS·개인정보보호법) — 통합 설계 선행 |
| Gemini API (`GEMINI_API_KEY`) | 퇴원심사·수술상담 | EMR가 동일 키 보유 시 그대로 동작 |

> **권고:** ① EMR DB 어댑터(supabase 인터페이스 호환 shim), ② Dialog/Toast 매핑, ③ 환자 마스터 FK 연계 정책 — 이 3가지를 "공통 이식 기반"으로 먼저 만들면, 이후 기능별 이식이 도메인 로직 중심으로 단순화됩니다.

## 2. 기능별 상세

### 🟢 ① 수술상담 — 강력추천 (1순위)

**무엇:** 의사-환자 수술 전 상담을 **음성 녹음/업로드 → Gemini AI 분석 → 13개 임상 필드 구조화**(주호소·진단·수술계획·합병증·동의항목·처방·다음예약 등)하는 임상 문서화 도구.

**왜 1순위인가:**
- **결합도 하** — PC 컴포넌트(`수술상담.tsx`)는 시스템 DB 결합이 **0**. `useActionDialog`·`toast`만 의존. types/utils/components 모두 순수 모듈.
- **마이그레이션 부담 없음** — PC 분석 결과가 현재 `localStorage`(`erp_consultation_records`)에만 저장 → 이관할 레거시 데이터가 없어 **EMR에서 새로 시작**하면 됨.
- **AI 파이프라인 완성** — Gemini 2.5 Flash/Pro 호출·JSON 파싱·폴백 모델까지 완성된 `/api/consultation/transcribe` 라우트를 그대로 이식.
- **임상 본원** — 수술 동의(`consent_required`, 의료법 제24조의2)·합병증 설명·수술계획은 EMR 의무기록 그 자체. ERP보다 EMR에 있는 것이 옳은 위치.

**필요 작업(재작업 25–30%):** AI 분석 결과 **DB 영속화 경로 신규 설계**(현재 localStorage), 인증 교체, `op_consultations` 등가 테이블 정의.
**주의:** AI 추출 결과의 **법적 지위**(참고문서 vs 의무기록 원본) 사전 정의 필수 — 코드에도 "실제 서명 여부 별도 확인" 주석 존재(`수술상담-components.tsx:89`).

### 🟢 ② 퇴원심사 — 추천 (2순위)

**무엇:** 퇴원 환자의 차트·청구 항목이 **건강보험 요양급여기준·DRG 분류 규정**에 맞는지 심사하는 보험심사 워크플로우. 규정 엔진 + AI 이중 검토 구조.

**왜 추천인가:**
- **규정 엔진이 완전 독립** — `lib/discharge-review-rules.ts`(~600줄)는 **외부 의존 0**(타입 import 1개뿐). DRG 7개 질병군 규칙, 12개 임상 키워드 분류, 중복청구 탐지, 4단계 심각도 체계가 순수 함수. **그대로 복사 가능**.
- **법적 근거 내장** — 체크리스트 항목마다 보건복지부 고시 PDF 페이지를 `basis`로 명시 → 이의제기 시 근거 추적.
- **EMR 핵심 수요** — DRG 기반 입원 보험심사는 국내 입원병상 병원의 보편 워크플로우. 청구 데이터 직접 연동으로 수작업 오류 감소.
- **결정론적 규정 + AI** — 규정 엔진이 먼저 실행되고 그 결과를 AI 프롬프트에 포함해 차이를 설명하게 설계.

**필요 작업(재작업 55% — 대부분 인프라):** 도메인 로직 재작성은 최소(~5%), 나머지는 DB 클라이언트·인증·UI 컴포넌트 교체.
**주의:** ① 사용자 정의 규정이 현재 **localStorage**(`erp_discharge_custom_rules`) 저장 → **서버 영속화로 반드시 교체**(다기기/다사용자). ② AI 분석은 2단계로 분리 가능(규정 엔진 단독으로도 가치). ③ 외래 전용 EMR이면 우선순위 하락.

### 🟢 ③ 인계노트 — 추천 (3순위)

**무엇:** 교대 근무(Day/Evening/Night) 간 **간호 인수인계** 기록. 공통 인계 + 환자별 인계(병실·침대·환자명 연결) 2-track + 병상 스냅샷 + 템플릿 버전관리.

**왜 추천인가:**
- **로직 독립** — `lib/handover-notes.ts`(369줄 전체) 외부 의존 0, 즉시 이식. 병상 이력 추적(`patientEpisodes`) 같은 복잡한 파생 계산도 순수 함수.
- **환자안전 핵심** — 간호 인계(Nursing Handoff)는 TJC가 National Patient Safety Goal로 지정. 교대 시 환자상태 전달 누락 방지.
- **재작업 35–40%** — 대부분 스타일·DB 레이어 교체, 기획·알고리즘 재설계 비용 거의 없음.

**필요 작업:** ⚠️ **company 격리 컬럼 없음**(코드 주석으로 확인, `data-hooks.ts:364`) → 다중 병원 배포 시 인계 혼합. EMR에서 **company 격리 + 확장 컬럼 10개를 정본 스키마로 신설** 필요(현 newmso는 content 마커 인코딩으로 우회 중).
**개선 검토:** SBAR 구조화 필드 없음(자유텍스트), 수신자 서명/확인 추적 없음(`is_completed` 단일 플래그) — EMR 의료진 요구에 따라 추가 검토.

### 🟡 ④ OP체크 — 조건부 추천 (4순위)

**무엇:** 수술실 간호사가 수술 환자 준비상태를 실시간 체크하는 **수술 전 안전 체크리스트**(WHO Surgical Safety Checklist 유사). 템플릿 자동생성·상태전이·2단계 안전확인 팝업·병동 이동요청 메시지·소모품 재고차감.

**왜 조건부인가:**
- **임상 가치 최고** — 환자명·수술부위 2중 확인, 수술 시작/종료 타임스탬프는 의료사고 예방 직결. EMR에 부재한 영역.
- **그러나 결합도 상** — 두 개의 깊은 newmso 결합:
  1. **수술일정 = `board_posts`(게시판)에 종속** — 환자/차트번호/수술명/수술실이 모두 게시판 레코드. EMR은 자체 수술예약 테이블이 있으므로 **데이터 소스 근본 교체** 필요.
  2. **병동 메시지 = `chat_rooms`/`messages` 직접 접근** — newmso 채팅 인프라 전체에 의존. EMR 메시징/알림으로 완전 재작성.
- **재작업 60–65%** — `OP체크.tsx` 본체가 상태관리+DB직접호출 혼합 구조라 레이어 분리 리팩터 필요.

**이식 조건:** EMR이 **(a) 수술예약 API 노출** + **(b) 내부 메시징/알림 채널** 둘 다 제공하면 재작업 40% 이하로 하락 → 체크리스트 로직·UI·템플릿 시스템 재사용 가치 충분. **둘 다 없으면 신규 개발 권장.**
**재사용 가능(35–40%):** helpers/utils/constants/PrintModal/ChecklistItemRows 등 순수 로직·프레젠테이션.

### 🔴 ⑤ 마감보고 — 비추천 (제외)

**무엇:** 당일 수납(현금/카드/이체) 내역 입력 + 기초·기말 시재 비교로 현금 정산오차 검증하는 **일일 금전출납 마감**(원무 Front Office).

**왜 비추천인가:**
1. **newmso 원본도 폐기 방향** — UI에 "Chart 프로그램 이관 예정" 배너 하드코딩(`마감보고.tsx:404`), 메뉴 메타 `external:'chart'`(`추가기능공통.tsx:225`). 자체적으로 ERP 부적합 판단.
2. **EMR 도메인 아님** — 임상 기록과 무관한 현금출납. 전형적 ERP/원무 영역.
3. **시너지 없음** — `daily_closure_items.patient_name`이 자유 텍스트 입력으로 **EMR 환자 ID와 미연계** → EMR 결합해도 데이터 활용 가치 없음.
4. 재작업 35–40%(권한·DB·멀티법인) 비용도 무시 못 함.

**조건부 재고:** allemr가 **원무 통합형 1인 의원 솔루션**을 지향하고 patient_name을 환자 FK로 교체할 명확한 시나리오가 있을 때만.

## 3. 권장 이식 로드맵

```
[0단계] 공통 이식 기반 구축 (1회)
  - EMR DB 어댑터(supabase 인터페이스 호환 shim)
  - Dialog/Toast 매핑, 인증/RBAC 어댑터
  - 환자 마스터 FK 연계 + PHI 암호화/접근제어 정책

[1단계] 수술상담 이식 (최저비용·최고 ROI)
  - localStorage → DB 영속화 신설, AI 라우트 이식, 법적지위 정의

[2단계] 퇴원심사 이식 (규정엔진 그대로 + 인프라 교체)
  - discharge-review-rules.ts 복사, 사용자규정 서버 영속화
  - AI 분석은 2-b로 분리 가능

[3단계] 인계노트 이식 (정본 스키마 신설이 관건)
  - company 격리 + 확장컬럼 10개 정본화, SBAR/서명 추가 검토

[4단계] OP체크 — EMR 수술예약 API·메시징 준비 여부로 Go/No-Go 결정
  - 조건 충족 시 이식, 미충족 시 신규 개발

[제외] 마감보고 — 이식하지 않음 (ERP 잔류 또는 Chart 이관)
```

## 4. 종합 의사결정

| 구분 | 기능 | 근거 |
|------|------|------|
| **즉시 이식 권장** | 수술상담, 퇴원심사, 인계노트 | EMR 본원 워크플로우 + 도메인 로직 독립 + 이식비용 합리적 |
| **조건부(EMR 인프라 의존)** | OP체크 | 수술예약 API + 메시징 채널 제공 시에만 |
| **이식 제외** | 마감보고 | EMR 비적합 + 원본도 폐기 예정 |

**총평:** 5종 중 **3종은 EMR로 옮길 때 오히려 "제자리를 찾는"** 임상 기능입니다(수술상담·퇴원심사·인계노트). 핵심 도메인 로직이 순수 함수로 잘 분리돼 있어 이식 비용 대부분은 인프라 어댑터 교체에 집중되며, **공통 기반(0단계)을 먼저 구축하면 3종 합산 재작업이 크게 절감**됩니다. OP체크는 가치는 높으나 EMR 측 인프라 전제가 필요하고, 마감보고는 EMR에 넣지 않는 것이 옳습니다.
