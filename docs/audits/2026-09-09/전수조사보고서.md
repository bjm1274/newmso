## 1. 핵심 결론

메신저와 인사관리에서 **데이터가 실제로 삭제되지 않아도 사라지거나 0으로 보이는 결함**을 확인했다. 조회 실패를 정상적인 빈 결과로 취급하는 것이 주요 원인이다. 그 밖에 시간 정렬, 페이지네이션, 접근 권한, 배치 저장, 자동 작업, 품질 검증 구성에도 결함이 있다.

총 **16개 개선 항목(P1 10개, P2 6개)**을 정리했다. 원본 함수·정책 또는 동일 SQL을 이용한 재현 9건, 로컬 Chromium 재현 1건, 로컬 DB 집계로 확인한 시간 정렬 문제 1건이 포함된다. 나머지는 코드 흐름과 실행 구성에 근거한 판정이다. 같은 공통 계층 문제가 여러 기능에 영향을 줄 수 있어 항목 수를 화면별로 중복 계산하지 않았다.

**사용자가 경험한 ‘메신저 전송 후 프로그램 종료’의 정확한 원인은 아직 확정할 수 없다.** 채팅 목록이 비워지는 현상과 청크 오류 시 반복 새로고침은 재현했지만, Electron 프로세스 종료·렌더러 크래시를 실제로 관측한 것은 아니다. 원인으로 단정하지 않는다.

로컬 DB `quick_check`는 `ok`였다. 이는 SQLite의 기본 구조 검사 결과이며, 과거 데이터 삭제·업무 데이터의 정합성·운영 서버의 상태를 보장하지 않는다.

## 5. 메신저 및 종료 현상 상세

### F01. 조회 실패가 현재 대화방을 닫는 것으로 처리됨

- 위치: `app/main/기능부품/메신저방데이터훅.ts:1406`, `:1411`, `:1418`.
- 원인: `fetchAllChatRooms()`의 error를 기록한 뒤 계속 진행해 `data || []`를 정상 목록처럼 반영한다. 현재 방을 찾지 못하면 `setRoom(null)` 또는 다른 방으로 이동한다.
- 재현: 기존 방 1개를 가진 상태에서 429 응답을 주입했다. 방 목록 0개, 선택 방 null로 바뀌었다.
- 영향: 사용자는 전송 직후 갱신 중 대화가 닫히거나 데이터가 사라졌다고 느낄 수 있다. 이후 성공한 갱신에서 목록이 돌아오는 증상과 연결된다. DB 삭제는 이 경로에서 일어나지 않는다.
- 수정: 오류 응답이면 기존 방/목록을 유지하고 갱신 실패 상태를 표시한다. 정상 응답에서 멤버십이 실제로 사라진 경우에만 방을 해제한다.

### F02. 문자열 날짜 정렬과 실제 시간 정렬이 다름

- 위치: `app/main/기능부품/메신저방데이터훅.ts:727`, `:732`; `app/api/d1/mutate/route.ts:29`의 날짜 처리 설명도 실제 데이터 상태와 다름.
- 원인: `YYYY-MM-DD HH:mm:ss`와 `YYYY-MM-DDTHH:mm:ss...`를 TEXT로 정렬/비교한다. 같은 날짜에서는 시각보다 공백과 T의 문자 순서가 우선한다.
- 증거: 로컬 messages 24,340개에서 두 형식이 혼재하며 방·날짜별 4개 그룹의 최신행 판정이 실제 시간과 달랐다.
- 영향: 최신 메시지가 첫 페이지에 들어오지 않거나 사이드바/과거 조회 순서가 어긋날 수 있다. 화면에서 날짜 객체로 재정렬해도 서버가 잘못 선택한 페이지 밖의 행은 복구되지 않는다.
- 수정: 저장·조회·커서가 같은 UTC 정규형 또는 정수 타임스탬프를 사용하게 통일한다. 기존 데이터 변환은 별도 백업·검증 후 수행하고 인덱스도 같이 설계한다.

### F03. 같은 시각의 메시지가 페이지 경계에서 빠짐

- 위치: `app/main/기능부품/메신저방데이터훅.ts:727` 및 `:732`.
- 원인: 정렬은 `(created_at DESC, id DESC)`인데 이전 페이지 조건은 `created_at < cursor`만 사용한다. 같은 created_at이면서 아직 읽지 않은 id는 모두 제외된다.
- 재현: 같은 초에 저장된 합성 메시지 105개 중 첫 20개 조회 뒤 다음 페이지가 0개, 85개가 도달 불가가 됐다. 이 극단적 조건이 로컬 실데이터에 존재한다고 주장하는 것은 아니다. 페이지 경계의 2개 동시 메시지만으로도 일부 누락이 가능하다.
- 수정: `(time < cursorTime) OR (time = cursorTime AND id < cursorId)` 형태의 복합 커서를 사용한다. F02 정규화와 함께 회귀시험한다.

### F04. 미읽음 0을 영구적으로 보존함

- 위치: `app/main/기능부품/메신저방데이터훅.ts:179`.
- 원인: 이전 미읽음 값이 0이면 현재 열린 방인지에 상관없이 새 계산값을 0으로 덮는다.
- 재현: 닫힌 방의 이전 값 0, 서버 기준 미읽음 3을 주입했는데 결과 0.
- 수정: 현재 열려 있는 방에 한해서만 0을 유지하고 닫힌 방은 최신 조회값을 반영한다.

### F05. 반복 청크 오류 시 자동 새로고침 반복 가능

- 위치: `app/components/ErrorBoundary.tsx:57`, `:70`.
- 원인: 오류 처리에서 sessionStorage에 1회 새로고침 표식을 남기지만 `componentDidMount()`가 이를 삭제한다. 재로딩 후 정상 마운트했다가 같은 청크 오류를 다시 만나면 또 새로고침된다.
- 재현: 원본 컴포넌트의 마운트→오류→재마운트→동일 오류 순서에서 자동 reload가 2회 호출됐다.
- 영향: 배포 청크/캐시/네트워크 문제가 지속되는 조건에서 화면 재시작과 미저장 상태 유실을 반복할 수 있다.
- 수정: 마운트 시 무조건 삭제하지 말고 빌드 식별자와 냉각 시간을 기준으로 방어한다. `lib/stale-build-guard.ts`와 중복 자동 복구 정책을 통합한다.
- 한계: 이것이 사용자에게 발생한 Electron 프로세스 종료 원인이라는 증거는 아직 없다.

### F08. 타인 퇴직연금 정보의 열람 제한 누락

- 위치: `lib/db/auth/policies.ts:1786`, `:1806`; `lib/db/schema.ts`의 `retirement_pensions`.
- 원인: 민감 테이블 묶음에서 퇴직연금을 AUTHENTICATED 조회로 등록했다. 이 경로는 로그인 여부만 보고 반환하며 본인·회사·인사권한을 검사하지 않는다.
- 재현: 일반 직원 claims와 타인 소유의 합성 퇴직연금 행을 원본 `filterByPolicy()`에 전달하자 반환됐다. 실제 타인의 자료를 HTTP로 조회하지 않았다.
- 영향: 계좌번호·납입액·누적액 같은 직원 정보가 범용 query API를 통해 노출될 수 있다. 같은 등록 묶음의 세무·프리랜서 지급 자료도 권한 재점검이 필요하다.
- 수정: 본인 또는 허가된 인사·재무 담당자의 대상 직원 범위로 제한하고 민감 필드는 역할별로 최소화한다.

### F09. 회사 관리자가 타사 직원 급여를 수정할 수 있는 정책

- 위치: `lib/db/auth/policies.ts:1033`, `:1943`; `app/api/d1/mutate/route.ts:930`.
- 원인: payroll_records의 쓰기는 ADMIN_OR_MANAGER다. 해당 행에 회사 컬럼이 없으면 공용 데이터처럼 허용하는데, 급여 소유 회사는 staff_id를 통해 확인해야 한다.
- 재현: 비전사 관리자이면서 회사 관리 권한만 있는 claims로 다른 직원의 합성 급여 수정 정책을 호출했다. DB의 대상 직원 회사 조회 없이 true가 반환됐다.
- 영향: 대상 id를 아는 관리자가 타사 급여를 변경할 수 있는 경계 결함이다. 실제 운영 데이터 변경은 수행하지 않았다.
- 수정: staff_id로 직원의 회사·급여 관리 권한을 확인한다. INSERT/UPDATE/UPSERT/DELETE와 소유자 변경을 함께 검사한다.

### F13. 서류 촬영이 전역 Permissions-Policy로 차단됨

- 위치: `next.config.ts:53`, `:115`; `app/main/기능부품/인사관리서브/스마트서류제출.tsx:404`.
- 원인: 모든 페이지에 `camera=(), microphone=()`를 적용하면서 서류 촬영은 getUserMedia를 호출한다.
- 재현: 원본 헤더를 적용한 로컬 페이지에서 Chromium의 cameraAllowed=false, getUserMedia 결과 NotAllowedError를 확인했다. 실제 카메라를 사용하지 않도록 가상 장치를 썼다.
- 영향: 사용자가 카메라 권한을 허용해도 촬영 화면이 닫히며 권한 안내만 반복될 수 있다. 개인 서류 제출도 같은 호출을 사용한다.
- 수정: 필요한 동일 출처에서 camera 사용을 허용하도록 정책을 조정하고 불필요한 권한 제한은 유지한다.

### F16. 급여 마감 확인과 쓰기가 원자적으로 연결되지 않음

- 위치: `app/api/payroll/shadow-verify/route.ts:103`; `app/main/기능부품/인사관리서브/급여명세/급여정산.tsx:1462`; `app/api/d1/mutate/route.ts:930`.
- 원인: shadow-verify가 잠금을 확인하지만 실제 범용 mutate의 payroll_records 쓰기에는 월 마감 잠금 검사가 없다.
- 영향: 검증 요청 후 다른 담당자가 월을 잠그는 경우, 이미 검증을 마친 저장이 잠금 이후에 진행될 수 있다. 범용 쓰기 호출은 검증 단계 자체를 거치지 않을 수도 있다.
- 수정: 급여 전용 저장 API 안에서 대상 회사·월 잠금·검증·쓰기를 하나의 트랜잭션으로 묶는다. 범용 급여 쓰기는 제한한다.
- 검증 수준: 코드 경로 확인. 실제 마감 월의 데이터를 수정하지 않았다.

## 7. 공통 계층·운영 상세

### F10. 비공개방 고정 메타데이터에 방 멤버십 검사 없음

- 위치: `lib/db/auth/policies.ts:952`; `app/api/d1/query/route.ts:463`.
- 원인: pinned_messages 조회·삽입·수정·삭제를 AUTHENTICATED로 등록했다.
- 재현: 방 멤버십이 없는 합성 일반 직원이 타사 비공개방 고정 행을 열람하고 삽입 권한 검사도 통과했다.
- 영향: 비공개방의 고정 메시지 식별자 열람 및 고정 상태 조작이 가능하다. 메시지 본문 전체가 이 결함으로 직접 유출된다는 뜻은 아니다. room_read_cursors와 message_reactions의 조회 범위도 함께 점검해야 한다.
- 수정: room_id 또는 message_id로 부모 방의 멤버십과 액션 권한을 확인한다.

### F11. 대량 IN 조회에서 정렬·페이지 크기가 바뀜

- 위치: `app/api/d1/query/route.ts:422`, `:454`, `:457`.
- 원인: IN 조건을 분할한 각 쿼리에 LIMIT/OFFSET을 각각 적용하고 단순 연결한다. 최종 전역 정렬이나 페이지 절단이 없다.
- 재현: id 105개, 내림차순 LIMIT 2의 기대값은 [105,104]인데 원본 함수 결과는 [100,99,105,104]였다.
- 영향: 직원별 급여·근태·대화·재고 등 다수 식별자를 사용하는 조회에서 순서·행 수·페이지 누락이 달라질 수 있다.
- 수정: SQLite 백엔드의 실제 바인딩 한도를 고려해 청킹을 제거하거나, 전역 정렬과 페이지 의미를 보존하는 조회로 변경한다. 변경 전에 권한 필터가 페이지 선택 이전에 적용되는지도 함께 점검한다.

### F12. 배치 INSERT가 중간 실패 시 부분 저장됨

- 위치: `app/api/d1/mutate/route.ts:682`, `:690`, `:727`.
- 원인: 여러 청크를 `await db.run()`으로 순차 커밋하며 전체를 감싸는 transaction/batch가 없다.
- 발생 조건: 앞 청크는 성공하고 뒤 청크에서 UNIQUE·CHECK·FK 등 DB 제약 오류가 발생하는 경우.
- 영향: API는 실패를 반환하지만 앞부분은 남는다. 사용자가 재시도하면 중복·일부만 존재하는 상태가 생길 수 있다. ‘실패했는데 데이터가 있다’는 증상과 연결된다.
- 수정: 전체 요청을 원자적 DB batch로 실행하고 중복 요청에도 같은 결과를 반환하도록 요청 식별자를 설계한다.
- 검증 수준: 코드 흐름 확인. 운영 배치 저장을 실패시키는 실험은 하지 않았다.

### F14. 서버 자동 작업 두 종류가 스케줄에서 누락

- 위치: `server.mjs:438`; `app/api/cron/auto-report/route.ts`, `app/api/cron/todo-reminders/route.ts`.
- 결과: cron route 18개 중 서버 직접 연결은 14개다. 4개 단순 차집합 중 license-expiry-check와 inapp-notifications는 push-subscription-cleanup 내부에서 호출되므로 누락 결함에서 제외했다.
- 남는 문제: auto-report와 todo-reminders가 server.mjs 스케줄에 없다. 할일은 로그인 사용자 요청/관리자 수동 실행 경로가 있으나 무인 예약 실행을 대체하지 않는다.
- 영향: 외부 스케줄러가 없다면 예약 보고서와 무인 할일 알림이 실행되지 않는다.
- 수정: 현재 서버 기준으로 스케줄을 등록하고 마지막 성공/실패 상태를 관측한다. 외부 스케줄러가 이미 있는지는 배포 환경에서 확인해야 한다.

### F15. 품질 검사·테스트 구성의 마이그레이션 미완료

- 위치: `scripts/verify-cron-wiring.mjs:27`, `.github/workflows/quality.yml`, `package.json`.
- 결과: verify:cron은 없는 wrangler.toml에서 즉시 실패한다. test:e2e 관련 명령은 없는 scripts/seed-e2e-d1.mjs를 참조한다. CI 설명과 배포 경로에는 과거 Cloudflare 구조가 남아 있다.
- lint: 전체 오류 41개 중 app/lib의 실소스 오류는 useSheetHistory.ts:25와 모바일/채팅/index.tsx:114,117의 render 중 ref 접근 3개다. 이 오류만으로 실제 종료 원인을 단정할 수 없다. 나머지는 기존 진단 스크립트의 규칙 위반이다.
- 영향: 정상적인 품질 게이트 및 자동 회귀시험 실행을 신뢰하기 어렵다.
- 수정: Node/SQLite 기준으로 크론·시드·CI를 갱신하고 임시 진단 파일의 lint 대상 여부를 명확히 한다. 테스트를 실제 DB/모의 API/설치형 앱으로 구분한다.

## 8. 종료 현상 확정을 위한 남은 조사

전송 오류와 ‘창 종료’, ‘로그인 이동’, ‘오류 화면’, ‘새로고침’은 다른 사건이다. 다음 증거를 같은 시각에 묶어야 한다.

1. 발생 환경과 버전: Windows 설치형/PC 브라우저/모바일, 설치 앱 버전과 서버 커밋.
2. 오류 화면이면 `/api/client-error`의 해당 시각 서버 로그와 componentStack. 이 API는 현재 console.error만 기록한다.
3. 진짜 창/프로세스 종료면 Electron의 render-process-gone·child-process-gone·크래시 덤프 및 OS 오류 기록. 현재 main.js에는 이 이벤트를 저장하는 진단 경로가 없다.
4. 전송 HTTP 상태와 후속 chat_rooms 조회 상태, 요청 지연, 429/5xx, 재로그인 여부.
5. 텍스트/답글/첨부/이모티콘별 반복 재현과 응답 지연 중 방 이동 시험.

F01·F05는 증상과 연결 가능한 확인된 결함이지만, 실제 종료 사건의 최종 원인으로 확정하지 않았다. 크래시 기록을 수집하기 전까지 ‘종료 원인 해결’로 보고하면 안 된다.

### 회귀시험 합격 조건

- 방 목록 실패 후 현재 방과 메시지가 유지되고 재시도 성공 시 복구된다.

- 연차/근태 조회 실패가 정상 0일 또는 내역 없음으로 표시되지 않는다.

- 동일 출처 서류 촬영이 정상 동작하고 닫을 때 장치가 해제된다.
- 예약 작업이 무인 상태에서 실행되며 실패가 성공처럼 기록되지 않는다.
