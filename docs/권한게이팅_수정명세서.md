## 0. 먼저 알아야 할 것 (권한 런타임 모델)

작업 전 반드시 이해할 데이터 흐름. **대부분 결함이 "클라이언트 게이팅"이며, 같은 키를 서버/클라가 다르게 본다.**

- **DB**: `staff_members.permissions`(JSON)에 전체 세분 권한 저장.
- **로그인 토큰**: `app/api/auth/master-login` → `lib/server-session.ts`의 `compactSessionPermissions()`가 **화이트리스트 키만** 토큰에 남김. 화이트리스트 = `SESSION_PERMISSION_KEYS`(`admin, mso, system_master, hr, inventory, approval, hr_교대근무, hr_근무표생성`) + `menu_`로 시작하는 키. **그 외(board_*, 세분 hr_*, inventory_*, admin_*, extra_*, chat_*, mypage_*, staff_meta_*)는 토큰에서 제거됨.**
- **클라이언트**: `/main` 진입·30분 갱신 시 `GET /api/auth/session` → `resolveLatestSessionUser()`가 **D1에서 전체 권한 재조회** → 클라 `user.permissions`는 DB와 동일. **즉 클라이언트 게이팅은 compaction 영향을 받지 않는다.**
- **서버 API 라우트**: `readSessionFromRequest()` → 토큰의 **compacted 권한만** 사용.
- **바이패스**: `isPrivilegedUser`(named system master), `isAdminUser`(role==='admin' 또는 permissions.admin)는 대부분 우회. **→ 모든 결함의 영향 대상은 비-관리자 일반 직원.**

### 공통 근본원인
관리자 권한편집 UI(`lib/feature-permissions.ts`)가 **부여하는 키** ≠ 코드(`lib/access-control.ts` 등)가 **검사하는 키**. 또는 부여 키를 읽는 코드가 아예 없음(사문 권한).

### 핵심 파일
| 파일 | 역할 |
|---|---|
| `lib/access-control.ts` | 모든 권한 판정 함수 + `LEGACY_PERMISSION_ALIASES` 별칭 그래프 (**수정 대부분 여기 집중**) |
| `lib/feature-permissions.ts` | 관리자 UI가 토글로 부여하는 키 정의 |
| `lib/profile-photo.ts` | 권한 정규화·기본값 주입·세분키 마이그레이션 |
| `lib/server-session.ts` | 토큰 권한 compaction 화이트리스트 |

### 작업 원칙
1. **단일 소스 우선**: 가능하면 `lib/access-control.ts`의 별칭/판정만 고쳐 PC·모바일 동시 해결. 컴포넌트 개별 수정은 최소화.
2. **`expandPermissionKeys`는 단방향 BFS**: `hasPermission(user, K)`는 `LEGACY_PERMISSION_ALIASES[K]`를 따라 확장. 따라서 "검사키 K"에 "부여키들"을 별칭으로 추가하면 부여키 보유 시 K가 충족됨(=역방향 별칭). `visited` set으로 순환 방지되므로 추가는 안전.
3. **명시 false 우선**: `getExplicitPermissionState`가 명시값(true/false)을 최우선 반영. 별칭은 "미설정(undefined)"일 때만 작동 → 명시 거부는 유지됨.
4. 변경 후 반드시 `npx tsc --noEmit` + 변경 파일 `npx eslint` 통과.

```ts
export function canAccessBoard(
  user: UserLike | null | undefined,
  boardId: string,
  action: BoardPermissionAction = 'read'

  if (isPrivilegedUser(user)) return true;
  if (!canAccessMainMenu(user, '게시판')) return false;

  if (boardId === '업무가이드' && action === 'read') return true;

}
```

#### 결함 2 — 재고 4개 워크센터 단일키 게이트

**2-a. `lib/access-control.ts` `canAccessInventorySection`을 워크센터별 OR 합집합으로**:
```ts
export function canAccessInventorySection(
  user: UserLike | null | undefined,
  sectionIdOrPermissionKey: string
): boolean {
  const WORKCENTER_UNIONS: Record<string, string[]> = {
    status:  ['inventory_현황', 'inventory_이력', 'inventory_내부서재고'],
    io:      ['inventory_등록', 'inventory_발주', 'inventory_거래처', 'inventory_납품확인서', 'inventory_이관'],
    item:    ['inventory_자산', 'inventory_스캔', 'inventory_카테고리', 'inventory_UDI'],
    analyze: ['inventory_월마감', 'inventory_수요예측', 'inventory_재고실사', 'inventory_소모품통계', 'inventory_AS반품'],
  };
  const group = WORKCENTER_UNIONS[sectionIdOrPermissionKey];
  if (group) {
    return group.some((key) => canAccessDetailedSection(user, '재고관리', key, INVENTORY_PERMISSION_KEYS));
  }
  return canAccessDetailedSection(user, '재고관리', sectionIdOrPermissionKey, INVENTORY_PERMISSION_KEYS);
}
```

#### 결함 3 — PC 본인 급여명세 탭이 hr_급여(전사권한) 요구

- **증상**: `hr_급여`(인사 전사 급여권한) 없는 일반 직원이 PC 마이페이지 '급여·증명서' 탭을 못 봄. 부여된 `mypage_급여조회`(본인조회용, 기본 true)는 무시됨. 모바일은 비밀번호 게이트만으로 본인 급여 열람 가능 → PC/모바일 불일치.
- **근본원인**: `canAccessMyPageTab` 'salary'가 `hr_급여`만 검사([access-control.ts:422-423](lib/access-control.ts)). `mypage_급여조회`는 어디서도 안 읽힘(사문).

**3-a. `lib/access-control.ts` `canAccessMyPageTab` 'salary' 케이스**:
```ts
// 현재
case 'salary':
  return isPrivilegedUser(user) || hasPermission(user, 'hr_급여');
// 수정
case 'salary': {
  const own = getExplicitPermissionState(user, 'mypage_급여조회');
  if (own !== null) return own;                 // 명시 부여/거부 우선
  return isPrivilegedUser(user) || hasPermission(user, 'hr_급여');
}
```
> `mypage_급여조회`는 기본 true 주입([profile-photo.ts:155](lib/profile-photo.ts))이라 **모든 직원에게 본인 급여탭 노출**(모바일과 동등). 본인조회를 기본 차단하고 싶으면 profile-photo.ts:155의 기본 주입을 false로 바꾸거나 제거하고 관리자가 명시 부여.
