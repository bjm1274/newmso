# 오류 및 버그 탐색 보고서

- 점검일: 2026-07-22
- 대상: `newmso` Next.js 애플리케이션
- 방식: 정적 코드 검토, TypeScript 검사, 프로덕션 빌드, 기존 E2E 테스트 실행 시도
- 범위: 인증·권한, 출퇴근, AI/음성 처리 API, 배포 검증

## 요약

확정 결함 4건을 확인했다. 최우선 조치는 운영 환경에서 가능한 GPS 출퇴근 우회 제거와, 실제 수술상담 화면이 사용하는 분석 API의 권한·파일 크기 검증 추가다. 별도로 배포되어 있지만 현재 화면에서 사용되지 않는 음성 전사 API에는 서버 측 요청 위조(SSRF) 가능성이 있다.

| 우선순위 | 건수 | 요지 |
| --- | ---: | --- |
| P1 (높음) | 3 | 출퇴근 위·변조, 수술상담 권한 우회/무제한 업로드, 임의 URL 서버 요청 |
| P2 (중간) | 1 | Gemini 채팅 API의 기능 권한·요청량 검증 부재 |

## 확정 결함

### P1-1. 운영 환경에서도 `localStorage`로 GPS 출퇴근 제한을 우회할 수 있음

**영향**  원격지 사용자가 출근/퇴근을 정상 위치에서 한 것처럼 등록할 수 있다. 근태 데이터의 신뢰성과 급여·감사 후속 처리에 직접 영향을 준다.

**근거**

- PC 출퇴근 화면은 `bypass_gps` 값이 `'true'`이면 거리 값을 `0`으로 설정하고 위치 검증을 성공 처리한다: `app/main/기능부품/마이페이지/출퇴근기록/index.tsx:624`.
- 이후 동일 화면은 출근 기록을 저장한다: `app/main/기능부품/마이페이지/출퇴근기록/index.tsx:879`.
- 모바일 화면에도 같은 우회가 있으며, 출근/퇴근 변경을 D1에 기록한다: `app/main/모바일/내정보/출퇴근체크인.tsx:253`, `:324`, `:366`.
- 서버의 `attendance` 정책은 사용자/조직 범위를 확인하지만 위치 증빙은 확인하지 않는다: `lib/db/auth/policies.ts:452`.

**재현 절차**

1. 일반 직원 계정으로 운영 사이트에 로그인한다.
2. 브라우저 개발자 도구에서 `localStorage.setItem('bypass_gps', 'true')`를 실행한다.
3. 내 정보의 출퇴근 기능을 열어 출근 또는 퇴근을 누른다.
4. GPS 권한·실제 거리와 관계없이 위치 검증을 통과하고 근태 레코드가 저장된다.

**권장 조치**

- `bypass_gps` 분기를 운영 번들에서 완전히 제거한다. 개발 전용이 필요하면 `NODE_ENV === 'development'`와 localhost를 **동시에** 요구하고, 클라이언트 저장소 값은 신뢰하지 않는다.
- 근태 API를 전용 서버 엔드포인트로 분리해 위치 좌표·정확도·측정 시각을 검증하고, 우회·수정 이력을 감사 로그에 남긴다.
- 이미 저장된 비정상 근태를 `bypass_gps` 사용 여부가 아니라 위치 증빙 부재 및 비정상 시간대로 별도 점검한다.

### P1-2. 실제 수술상담 분석 API에 기능 권한과 서버 측 파일 한도가 없음

**영향**  수술상담 권한이 없는 로그인 사용자가 환자 음성 파일을 Google Gemini로 전송·분석할 수 있다. 또한 클라이언트의 100MB 제한을 우회해 서버 메모리와 AI 사용량을 과도하게 소비시킬 수 있다.

**근거**

- 실제 PC 수술상담 화면은 `/api/consultation/analyze`를 호출한다: `app/main/기능부품/수술상담.tsx:211`.
- 해당 API는 로그인 사용자 ID만 확인하며, 추가 기능 메뉴·수술상담 권한을 확인하지 않는다: `app/api/consultation/analyze/route.ts:40`.
- 파일은 비어 있지 않은지만 확인하고 크기·MIME allowlist를 서버에서 제한하지 않는다: `app/api/consultation/analyze/route.ts:52-63`.
- 파일 전체를 `arrayBuffer()`로 메모리에 올린 뒤 Gemini에 전송한다: `app/api/consultation/analyze/route.ts:62`.
- 권한 E2E 테스트는 다른 경로인 `/api/consultation/transcribe`만 점검한다: `tests/e2e/api-authorization.desktop.spec.ts:140`, `:170`.

**재현 절차**

1. `menu_추가기능` 또는 `extra_수술상담` 권한이 없는 활성 직원으로 로그인한다.
2. 개발자 도구/스크립트로 `/api/consultation/analyze`에 유효한 세션 쿠키와 `FormData(file, mimeType)`를 전송한다.
3. API는 403이 아니라 파일 검증·Gemini 호출 단계로 진행한다. API 키가 없는 환경에서는 그 이후의 500 응답으로도 권한 검증 누락을 확인할 수 있다.

**권장 조치**

- API 진입부를 `readAuthorizedExtraFeatureUser(request, '수술상담')` 기반으로 바꾸고 권한 없는 요청은 파일을 읽기 전에 403으로 종료한다.
- 서버에서 허용 오디오 MIME 목록과 최대 크기(예: 100MB)를 검증한다. `Content-Length`만 신뢰하지 말고 스트리밍 중 누적 바이트를 제한한다.
- 파일을 통째로 `arrayBuffer()`에 적재하지 말고, 상한이 적용된 스트림으로 처리한다.
- 이 **실제 사용 경로**에 대한 권한 거부·용량 초과 E2E/통합 테스트를 추가한다.

### P1-3. 배포된 `/api/consultation/transcribe`가 임의 URL을 서버에서 가져옴 (SSRF/외부 전송)

**영향**  수술상담 권한 사용자가 `audioUrl`에 임의 URL을 넣어 애플리케이션 서버가 해당 URL을 요청하게 할 수 있다. 응답 바이트는 Gemini 업로드 흐름으로 전달된다. 내부 접근 가능 주소 탐색, 임의 외부 데이터의 제3자 전송, 대역폭·AI 비용 소모 위험이 있다.

**근거**

- 이 경로는 추가 기능 권한을 올바르게 확인한다: `app/api/consultation/transcribe/route.ts:80`.
- 그러나 요청의 `audioUrl`, `mimeType`, `fileSize`를 그대로 수용한다: `app/api/consultation/transcribe/route.ts:88-106`.
- URL의 스킴·호스트·R2 버킷·사설 IP·서명 여부를 검증하지 않은 채 `fetch(audioUrl)`를 실행한다: `app/api/consultation/transcribe/route.ts:111`.
- `fileSize`는 요청자가 선언한 값일 뿐, 실제 내려받은 스트림 길이를 검증하지 않으며 Gemini 업로드 헤더에 그대로 사용한다: `app/api/consultation/transcribe/route.ts:127`.

**재현 절차**

1. 수술상담 권한이 있는 계정으로 로그인한다.
2. `/api/consultation/transcribe`에 허용 크기로 가장한 `fileSize`와 외부 제어 URL을 `audioUrl`로 전송한다.
3. 서버는 해당 URL에 요청을 보내고, 성공 응답 본문을 Gemini 업로드에 스트리밍한다.

**권장 조치**

- 클라이언트가 URL을 제출하지 않도록 하고, 서버가 인증된 R2 객체 키만 받아 내부 버킷 바인딩으로 읽는다.
- 불가피하게 URL을 허용하면 HTTPS·정확한 허용 호스트·정규화된 경로만 허용하고, DNS 재해석/사설·링크 로컬 IP 차단 및 redirect 금지를 적용한다.
- 응답 `Content-Type`, 실제 `Content-Length`, 스트리밍 누적 크기를 모두 검증한다.
- 이 API가 더 이상 필요 없으면 라우트를 삭제하거나 실제 사용 경로를 안전한 구현으로 통합한다.

### P2-1. Gemini 채팅 API가 기능 권한 및 요청량·본문 한도를 적용하지 않음

**영향**  로그인만 한 사용자가 UI에서 숨겨진 경우에도 Gemini 호출을 직접 시도할 수 있다. 메시지 이력과 `systemInstruction`의 개수·문자 수 제한, 사용자별 요청 제한이 없어 AI 비용 급증과 대용량 요청에 취약하다.

**근거**

- `/api/ai/chat`은 세션 사용자 ID만 검사한다: `app/api/ai/chat/route.ts:20-23`.
- 클라이언트가 보낸 `messages`와 `systemInstruction`을 별도의 스키마/크기 검증 없이 모델 입력으로 사용한다: `app/api/ai/chat/route.ts:26-28`, `:49-58`.
- 같은 프로젝트의 근무표 AI API에는 사용자별 시간당 10회 제한이 존재하지만, 채팅 API에는 동등한 제한이 없다: `app/api/ai/roster-recommendation/route.ts:8-22`.
- UI 권한 규칙은 추가 기능 메뉴 및 Gemini 권한을 고려한다: `lib/access-control.ts:674-704`. 서버 API와 규칙이 일치하지 않는다.

**권장 조치**

- `readAuthorizedExtraFeatureUser(request, 'Gemini어시스턴트')` 또는 동등한 서버 권한 검사를 적용한다.
- Zod 등으로 메시지 개수, 각 메시지 길이, 총 문자 수, 허용 role을 제한하고 서버 고정 시스템 지침을 사용한다.
- 다중 인스턴스 환경에서도 공유되는 rate limit(KV/Durable Object/DB)을 적용하고 호출량·오류·토큰 사용량을 감사한다.

## 후속 권장 순서

1. P1-1의 운영 GPS 우회를 즉시 제거하고 비정상 근태를 점검한다.
2. P1-2의 실제 수술상담 API에 권한·용량 검증을 추가하고, 보호된 미사용 전사 API와 구현을 통합 또는 제거한다.
3. P1-3의 임의 URL fetch를 R2 객체 키 기반 접근으로 대체한다.
4. P2-1 AI 호출 정책과 rate limit을 통합한 뒤, Playwright 브라우저를 설치한 환경에서 권한 회귀 테스트를 실행한다.
