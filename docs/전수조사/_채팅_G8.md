## 분류별 발견

### SEC 보안 / D1 정본 불일치 (가장 치명)

**[SEC-1 / 높음] 업로드.ts 오프라인 큐가 잘못된 테이블 `chat_messages`에 insert → 파일 메시지 영구 유실**
- `app/main/모바일/채팅/업로드.ts:183, 228` — `onSuccessAction: { kind: 'insert', table: 'chat_messages', ... }`
- 정본 `lib/db/schema.ts:328` `chat_messages` = {id, room_id, sender_id, content, type, created_at} **뿐**. `file_url/file_name/file_size_bytes/message_type` 컬럼 없음.
- 반면 온라인 경로(`insertChatMessageWithFallback`, `lib/chat-message-write.ts:31`)는 정본 `messages` 테이블에 insert. 읽기 경로(`data-hooks.ts:227` `from('messages')`)도 `messages`만 조회.
- 결과: 오프라인에서 첨부 전송 → 온라인 복귀 시 큐가 `chat_messages`(미사용 legacy 테이블)에 insert 시도. 미존재 컬럼으로 SQL 에러→catch 삼킴, 혹은 일부만 들어가도 `messages`를 보는 화면엔 **절대 안 나타남**. 사용자에겐 "전송됨" 표시 후 무음 유실.
- 근거: `grep chat_messages` 결과 활성 read/write 경로 없음(schema/relations/policies/counters만 참조).
- 조치: 두 곳 `table: 'chat_messages'` → `table: 'messages'` 로 변경. payloadTemplate 키는 `messages` 컬럼과 이미 일치(room_id/sender_id/message_type/file_url/file_name/file_size_bytes).

**[SEC-2 / 의심·낮음] 업로드 MIME 화이트리스트 미적용 — accept만으로 통제**
- `업로드.ts:77 validateMobileUploadTarget`는 size만 검증하고 type은 image/video/기타 분기만. 실행파일·SVG(XSS 벡터) 등 차단 없음.
- 단 첨부는 `<a target=_blank>` 링크/`<img src>`로만 렌더(`메시지버블.tsx:199,213`)되어 직접 실행 위험은 낮음. 서버(`/api/chat/upload`)에서 추가 검증한다는 주석(업로드.ts:11) — 서버측 검증 존재 여부는 본 조사 범위 밖(의심). 조치: 서버 라우트에 MIME 화이트리스트/확장자 검증 확인 권장.

### D 중복 / Q 유사기능 (데스크톱 메신저)

**[Q-1 / 낮음] 이모지피커 중복 — 데스크톱 `메신저액션서브/EmojiPicker.tsx`와 별도 구현**
- 모바일 `이모지피커.tsx`(32개 고정 그리드) vs PC `app/main/기능부품/메신저액션서브/EmojiPicker.tsx`(~120개 + 검색 + 카테고리 7탭 + 키보드 네비). 팔레트/목적 중복이나 PC가 훨씬 무겁고 데스크톱 전용 UX. 모바일 경량화는 합리적 — 통합 비권장. 공통화 가능한 것은 팔레트 상수 정도. 의도된 분리로 판단.

**[Q-2 / 낮음] 반응 toggle 로직 중복 — PC `메신저액션훅.toggleReaction`와 유사**
- `반응.ts:102 toggleMobileReaction`은 PC 패턴을 단순 재구현(주석에 명시). select→insert/delete 2-step race 동일. 중복이나 의존 최소화 의도. 유지 허용.

### P 성능 (폴링)

**[P-1 / 중간] 방 진입 시 메시지 2초 폴링 + 방목록 5초 폴링 동시 — refresh마다 전체 100건 재조회 + 반응 재조회**
- `data-hooks.ts:177 ROOM_MESSAGE_POLL_INTERVAL_MS=2_000` + `:92 ROOM_POLL_INTERVAL_MS=5_000`.
- 폴링 tick마다 `refresh()`가 messages 100건 + `fetchReactionsForMessages`(IN 쿼리) 무조건 재실행(`data-hooks.ts:243`). 증분/변경감지 없음. 방에 머무를 때 2초마다 2쿼리. 다수 사용자·대형 방에서 D1 read 부하.
- 조치: created_at tail 증분 폴링 또는 last 메시지 id 비교 후 변경 시에만 reaction 재조회.

**[P-2 / 낮음] 읽음 cursor upsert가 `messages.length` 변할 때마다 실행**
- `data-hooks.ts:337-353` effect deps `[roomId, userId, messages.length]`. 폴링으로 메시지 1건 늘 때마다 `room_read_cursors` upsert + `pokeChannel`. 빈번한 쓰기. 조치: 디바운스 또는 방 이탈/포커스 시점으로 제한.

### E 에러처리

**[E-1 / 중간] 무음 실패 다발 — catch에서 빈 배열/무시 (정본 컬럼 불일치 시 진단 불가)**
- `data-hooks.ts:66,140,250,349` / `반응.ts:62` / `업로드.ts` 등 — 모든 supabase 호출 catch가 silent(setState 빈값 또는 무시). 주석상 "조회 실패는 toast 안 함" 정책이나, SEC-1 같은 컬럼 오류가 전부 삼켜져 무음 기능불능을 유발. 최소한 `console.error`(DBG) 또는 dev 환경 로깅 권장.

**[E-2 / 낮음] sendMobileFileMessage 오프라인 분기에서 enqueue 결과 비큐잉·비에러 시 흐름 누수**
- `업로드.ts:166-189` `isOffline` 분기: `result.queued`도 `result.error`도 아니면(둘 다 falsy) 아래 온라인 경로로 그대로 진행 → 오프라인인데 fetch 시도. 드문 케이스지만 방어 부재. 의심.

## D1 정본 대조 결론
- `messages`/`message_reactions`/`room_read_cursors` 컬럼 사용 **정확**(file_url/file_name/file_size_bytes/message_type/sender_name, reader 측 unread는 room_read_cursors.last_read_at 사용 — fetchChatUnreadCountsByRoom:201과 일치).
- `.eq('is_deleted', false)` → 서버 `app/api/d1/query/route.ts:109`가 boolean→0 변환하므로 정상 동작.
- **유일한 정본 불일치 = SEC-1 (오프라인 큐 `chat_messages`)**. 타 모바일 메뉴의 "옛 Supabase 스키마 컬럼" 다발과 달리, 채팅 read/write 본류는 정본과 일치. 오프라인 첨부 한 경로만 잘못된 legacy 테이블 타겟.
