## SEC — 보안 (권한상승·접근제어·감사)

### [SEC-1] (Critical) staff_members 권한/역할 변경에 서버측 인가 없음 — 권한 상승
- 정본 정책: `lib/db/auth/policies.ts:115`
  ```
  staff_members: PUBLIC_ALL('staff_members'),
  ```
  `PUBLIC_ALL`은 select/insert/update/delete 모두 `'PUBLIC'`(`policies.ts:105-111`).
- mutate 라우트는 로그인 여부만 본다: `app/api/d1/mutate/route.ts:236-239`(`Unauthorized` 401만), `:331` `assertAccess(... op:'update' ...)` → `staff_members`는 PUBLIC이라 통과.
- 클라이언트 변경 경로: `직원권한통합.tsx:123-134 updateStaffRecord` → `supabase.from('staff_members').update(updates)`. `handleRoleChange`(`:178-222`), `setPermissions`(`:224-252`), `copyPermissionsToStaff`(`:299-374`)가 모두 이 경로 사용.
- 결과: `lib/system-master.ts`·UI의 `isSystemMaster`/`hasSystemMasterPermission` 게이트는 **렌더 차단(클라이언트 전용)** 일 뿐. 임의 인증 사용자가 직접 fetch로
  `{op:'update',table:'staff_members',set:{role:'admin',permissions:{...,system_master:true}},where:[{field:'id',op:'eq',value:'<자기 id>'}]}`
  를 보내면 관리자/시스템마스터로 승격된다. **즉시 수정 권장**: `staff_members`의 update 정책을 admin/mso 한정으로 좁히거나, role/permissions 같은 민감 컬럼 변경을 전용 서버 라우트(인가 검증 포함)로 분리.

### [SEC-2] (High) 채팅 메시지 삭제도 동일하게 PUBLIC `messages` 직접 삭제
- `시스템마스터센터.tsx:1350`
  ```
  const { error: delErr } = await supabase.from('messages').delete().eq('id', message.id);
  ```
- `messages: PUBLIC_ALL('messages')`(`policies.ts:131`) + mutate delete는 로그인만 검사. 시스템마스터 전용 화면이지만 서버는 시스템마스터 여부를 검증하지 않으므로, 임의 사용자가 직접 임의 메시지 삭제 가능. (채팅방 삭제는 `:381` `/api/admin/system-master` 서버 라우트를 쓰는데, 메시지 삭제만 클라이언트 직삭으로 일관성 깨짐 — D 참고.)

### [SEC-3] (Medium) 권한 토글에 "자기 자신 권한 상향" 가드 없음
- `직원권한통합.tsx:256-297 togglePermission`/`applyGroupPermission`, `:178 handleRoleChange`는 `selectedStaff`가 현재 로그인 사용자 본인인지 확인하지 않는다. 본인 계정 선택 후 admin 부여/critical 권한 자가 부여가 UI상으로도 가능(서버가 막지 않으므로 SEC-1과 결합 시 위험 가중).

### [SEC-4] (Low/감사) 감사 로그가 클라이언트에서 작성됨 — 위변조·누락 가능
- `직원권한통합.tsx:162,208,234,350` `logAudit(...)`는 클라이언트 `readClientAuditActor()`(`:142,182,226,313`)로 actor를 채워 호출. 실제 변경(`updateStaffRecord`)과 별개 호출이라, 변경은 성공하고 감사 로그만 누락/위조될 수 있음. actor가 클라이언트 신뢰값이라 SEC-1과 결합 시 "누가 바꿨는지" 신뢰 불가.

## 테이블 정합성 (staff_members/companies/permissions)
- `permissions`는 별도 테이블이 아니라 `staff_members.permissions` JSON 컬럼(권한+개인데이터 혼재). `buildPermissionsForCopy`(`직원권한통합.tsx:57-78`)가 비-권한 개인키(`NON_PERMISSION_PERSONAL_KEYS` `:23-50`)를 복사에서 제외하는 처리는 양호.
- `companies`: `회사관리.tsx` 폼은 schema의 `seal_url`,`leave_policy`,`unused_leave_compensation`,`fiscal_year_start_month`,`business_number`(중복 컬럼: `business_no`도 존재, schema.ts:412-413) 미관리 — 다른 화면 분담이나, `business_no` vs `business_number` 컬럼 이중 존재는 정합성 리스크.
