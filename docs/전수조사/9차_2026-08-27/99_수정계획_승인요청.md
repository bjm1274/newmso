## 1. 이 문서의 사용법

**이번 조사에서 저장소 소스는 한 줄도 고치지 않았다.** 아래 묶음 앞의 체크박스를 **체크한 것만** 진행한다.

- 묶음은 **한 커밋 단위**로 설계했다. 같은 원인 축을 공유하거나, 따로 고치면 반쪽 상태가 되는 것들을 묶었다.
- **회귀위험**은 "이 수정이 멀쩡히 돌던 것을 깨뜨릴 확률"이다. 운영 중인 시스템이라 이 값을 우선 봐야 한다.
- **§5 PLAUSIBLE 15건은 승인 대상이 아니다** — 확인이 먼저다.
- **§6 REFUTED 3건은 고치지 않는다.**

| id | 내용 |
|---|---|
| **`P0-D05-001`** | `approvals` insert 에 컬럼 가드가 없어 `status='승인'` 인 문서를 처음부터 만들 수 있다 → `/api/approvals/process-final` 로 자기 기본급·인사발령 집행 |

**수정**
1. `approvalsUpdateGuard` 와 동등한 컬럼 가드를 **insert 에도** 건다. 신규 결재의 `status` 는 `'대기'`/`'진행중'` 계열만 허용하고 `sender_id` 는 서버가 세션 값으로 덮어쓴다.
2. `/api/approvals/process-final` 이 `approval_history` 로 결재선 진행을 **DB 에서 재검증**하게 한다. (지금은 `status` 와 `current_approver_id` 만 보는데 둘 다 공격자가 채운 값이다.)
3. `register-staff` 의 루프를 `if (!value) continue;` (truthy 기준)로 바꾸고, `StaffRowSchema.permissions` 를 `z.record(z.string(), z.boolean())` 으로 좁힌다. 저장 직전 `Boolean(v)` 정규화도 함께.

**회귀위험이 낮은 이유**: 정상 흐름은 결재 문서를 `'대기'` 로 만들고 전이는 `/api/approvals/transition` 을 탄다. 1·2 는 그 경로를 건드리지 않는다. 3 은 현재 UI 가 boolean 만 보내므로 동작이 같다.

**검증**: 신규 결재 생성 → `status` 가 `'대기'` 로 강제되는지 · 기존 승인 플로우 1건 end-to-end · `permissions:{admin:1}` 요청이 400/403 인지.

- **`company_holidays` 근로자의날 행 교정** — 코드 수정과 함께 진행하되, 반복 공휴일을 연도별 행으로 둘지는 운영 판단이다.
- **2026-06 급여정산 재확인** — 근태 102행이 빠진 채 계산됐다(`P-02`). 그 102행이 전부 정상 출퇴근이면 금액 차이가 없으므로 소급이 불필요하다. **담당자 확인이 먼저다.**
- **`salary_change_history` 의 `'2026-09'` 2건** — 다음 달 발효분이다. 급여 마감 전에 `2026-09-01` 등으로 교정할 것.
- **결재자 없는 연차 결재 31건**(`P-08`) — 연차 값에 영향이 없음을 확인한 뒤 상태 정리.
- **`deploy.yml` 품질 게이트** — 8차 4-5 가 아직 열려 있다. `needs` 가 없어 **테스트가 깨져도 배포된다.**

## 7. 이 조사가 확인하지 못한 것

정직하게 남긴다.

- **E2E 미실행.** 시드가 로컬 D1 에 쓰기 때문에 READ-ONLY 원칙과 충돌한다. 수정 단계의 회귀 게이트로 미룬다.
- **`npm run build` 미실행.** 타입체크(오류 0)로 대체했다.
- **`verify:policies`(360케이스) 미실행.** 로컬 dev 서버가 필요하다.
- **`leave_ledger` ↔ `leave_balances` 정합 미확정.** 미러가 화면 조회 시 갱신되는 구조라 드리프트가 곧 결함은 아니다. 제대로 대조하려면 직원별 주기 계산을 재현해야 해서 이번 범위에서 뺐다.
- **`P-07` 의 중복 생성 재현 미실시.** 서버에 유일성 제약이 없다는 사실과 1초 차이 생성 쌍은 확인했으나, 실제 재현은 하지 않았다.
