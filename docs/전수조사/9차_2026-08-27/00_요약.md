## 1. 왜 9차인가

8차 전수조사(2026-08-03)는 CONFIRMED 237건(P0 22 · P1 92 · P2 123)을 냈고, 그 수정이 현재 브랜치 `fix/8th-audit-stage1` 에서 진행 중이다. 그 사이 **100커밋 · 522파일**이 바뀌었다. 두 가지를 확인해야 했다:

2. 그 100커밋이 **새로 깨뜨린 것**은 없는가

여기에 8차가 하지 않았던 축을 하나 더했다 — **운영 D1 실데이터 실측**. 코드만 읽어서는 나오지 않는 결함이 여기서 나왔고, 실제로 이번 최상위 P0 두 건 중 하나가 그것이다.

## 4. 지금 당장 봐야 할 것 — P0 4건

| # | 무엇 | 출처 |
|---|---|---|
| **A** | 일반 직원이 요청 2번으로 **자기 기본급을 임의 금액으로 올릴 수 있다** | `P0-D05-001` |
| **B** | 인사담당자가 `permissions:{admin:1}` 로 **관리자 계정을 만들 수 있다** | `P0-D01-003` |
| **C** | 공휴일 값 1행(`"5/1"`)이 **전 직원의 캘린더 구독을 500 으로 죽인다** | `P-01` |
| **D** | 중복 1:1 방의 **메시지 450건이 모바일에서만 안 보인다** | `P-07` |

### A · 결재 문서를 승인 상태로 "만들어서" 자기 급여를 올린다

8차는 `approvals` 의 `status` 위조를 막았지만 **update 에만** 걸었다. insert 에는 컬럼 가드가 없다.

```
① /api/d1/mutate insert → approvals(status:'승인', sender_id:본인, current_approver_id:본인,
                                    type:'급여인상평가서', meta_data:{targetStaffId:본인, newSalary:임의})
② /api/approvals/process-final → staff_members.base_salary 를 그 값으로 UPDATE
```

`process-final` 은 `approval_history` 를 보지 않고 **DB 의 status 와 current_approver_id 만** 확인하는데, 둘 다 ①에서 공격자가 채운 값이다. 같은 경로로 직급·부서 변경(`인사명령`)도 되고 `staff_transfer_history` 에 정상 발령 이력까지 남는다. 급여 워크센터·명세서·4대보험이 그 `base_salary` 를 그대로 쓰므로 **실제 지급액이 바뀐다.**

### B · true 가 아닌 truthy 로 권한 검사를 통과한다

```ts
// app/api/d1/rpc/register-staff/route.ts:162
for (const [key, value] of Object.entries(staff.permissions ?? {})) {
  if (value !== true) continue;        // admin:1 은 여기서 빠져나간다
  ...ADMIN_ONLY_PERMISSION_KEYS 검사...
}
```

저장은 `JSON.stringify` 로 정제 없이 들어가고, **읽는 쪽은 전부 truthy 판정**이다(`perms.admin || perms.mso || …`). 게다가 신규 계정은 `password_reset_required:1` 로 저장되고 마스터 로그인은 그 플래그가 서 있으면 "입력한 비밀번호를 새 비밀번호로 설정하고 로그인" 시킨다 — **만든 사람이 그 계정에 바로 들어갈 수 있다.** 체인이 끝까지 닫힌다.

### C · 캘린더 구독이 전 직원에게서 죽어 있다

`company_holidays` 6행 중 1행의 `holiday_date` 가 `"5/1"` 이다(근로자의날, `company_name='전체'`).

```ts
"5/1".split('-').map(Number)  ->  [NaN]
new Date(Date.UTC(NaN, NaN, undefined))  ->  Invalid Date
Invalid Date.toISOString()  ->  RangeError 를 던진다   ← 값을 반환하지 않는다
```

이 예외는 `company_holidays` 조회를 감싼 try/catch **밖**에서 터져 최상위 catch 로 떨어지고 `500` 이 나간다. 구글/애플 캘린더는 조용히 동기화를 멈추므로 사용자는 "일정이 안 올라온다"로만 인지한다.

### D · 모바일에서만 메시지 450건이 사라져 있다

같은 상대와의 1:1 방이 중복 생성돼(여분 159개, 어제도 2건) 대화가 여러 방에 흩어져 있다. **PC 는 형제 방을 합쳐 읽는데(`.in('room_id', roomIdsToLoad)`) 모바일은 대표 방 하나만 읽는다(`.eq('room_id', …)`).**

```
가려진 방 51개 · 가려진 메시지 450건
이나림   보이는 방 0건 / 가려진 방 2개에 229건   ← 열면 빈 화면인데 메모 229건이 있다
```

안읽음 개수는 형제 방까지 합산한다. **개수는 합치고 내용은 안 합친다** — "배지는 뜨는데 열면 그 메시지가 없다"가 여기서 나온다.

## 5. 근본 원인 축

이번 29건 + 실측 8건을 묶으면 원인이 다섯 갈래다.

### S1 · "한쪽 진입점만 막았다" (7건)

8차 수정의 지배적 실패 모드다. update 를 막고 insert 를 열어 두거나(`P0-D05-001`), 행 조회를 막고 `count` 를 열어 두거나(`P0-D01-D03`, `D1-08`), insert 정책만 보고 upsert 를 안 본다(`D1-03`).

> **교훈**: 가드를 붙일 때 "이 테이블에 쓰는 경로가 몇 개인가"를 먼저 세야 한다. 정책 레지스트리가 op 별 조회(`cfg.guards?.[args.op]`)라 빠뜨리기 쉽다.

### S2 · 가드가 정상 사용자까지 막았다 (3건 — 이번 브랜치가 만든 회귀)

반대 방향 실패다. `board_posts` 를 작성자 본인으로 좁혀 **투표·좋아요·업무가이드 완료 토글이 403** 이 됐고(`D1-01`), `approvals` status 가드에 관리자 예외가 없어 **모바일 증명서 승인이 관리자에게도 항상 실패**한다(`D1-02`). `staff_members.permissions` 를 관리자·본인에게만 열면서 **비관리자에게는 타인 아바타가 전부 사라졌다**(`D1-07`).

> `D1-07` 은 이 세션에서 "복구했다"고 보고했던 건이다. **정정한다** — 조회 목록에 `permissions` 를 되살린 것은 맞지만, 게이트웨이가 비관리자·비본인에게 그 컬럼을 지우므로 **일반 직원 화면에서는 여전히 안 보인다.** 관리자 계정으로만 확인한 결과였다.

### S3 · 타임스탬프 형식 혼재 (6건)

운영 D1 의 **38개 컬럼**이 공백형과 T형을 함께 담고 있다. `new Date()` 는 공백형을 로컬(KST), T형을 UTC 로 읽어 **9시간이 어긋난다.** 문자열 비교에서도 `'T'` > `' '` 라 같은 날짜 안에서 대소가 뒤집힌다.

발현 확인된 곳: 채팅 보관정책이 **메시지를 하루 일찍 영구 삭제**(`TZ-05`), 공지 SLA 가 올리자마자 초과(`TZ-01`), 모바일 결재함이 15시간 만에 "24h 초과"(`TZ-06`), 감사 로그가 "오늘" 집계에서 누락(`TZ-04`).

> 채팅 읽음 판정만은 전체 이력 47,768쌍 대조에서 **오판정 0건**이다. 처음에 그것만 보고 "잠복"으로 적었으나 다른 소비 지점에서 이미 터지고 있었다 — **판단을 정정했다.**

### S4 · KST/UTC 를 런타임 로컬시각으로 계산 (3건)

Workers 런타임은 UTC 인데 `setHours(18)` 같은 로컬 API 를 쓴다. 결근 크론의 퇴근 미체크 판정이 종료 경계를 KST 03:00(익일)으로 잡아 **근무시간이 약 9시간 부풀고**, 그 값이 급여 화면의 미지급 연장수당 경보로 이어진다(`TZ-02`). 공유캘린더는 날짜를 UTC 로, 달 경계를 로컬로 파싱해 **말일 연차가 통째로 사라진다**(`FB-02`·`M03`).

### S5 · 유일성·멱등성이 서버에 없다 (4건)

1:1 방 중복(`P-07`)은 유일성이 클라이언트에만, 그것도 조회 후 생성이라 레이스에 열려 있다 — 실제로 1초 차이로 생긴 쌍이 있다. 계약서 서명완료(`R06`)에 멱등 처리가 없어 두 번 호출되면 사본이 중복 생성되고, `annual_leave_promotion_logs` 는 UNIQUE 가 PK 하나뿐인데 두 곳이 서로 다른 컬럼 조합으로 upsert 한다(`D1-05`).
