## P-01 · 공휴일 1행이 캘린더 구독을 전 직원에게서 죽인다 — **P0**

### 관측된 값

```
company_holidays 총 6행 중 1행:
  id            = bb4408ad-b28f-41f3-80d0-d50dd73f27da
  holiday_date  = "5/1"          ← 날짜 형식이 아니다
  name          = 근로자의날
  company_name  = 전체            ← 모든 직원의 조회에 포함된다
```

### 무슨 일이 벌어지는가

[app/api/calendar/feed/route.ts:213](../../../app/api/calendar/feed/route.ts#L213) 의 루프:

```ts
for (const h of holidays) {
  if (!h.holiday_date) continue;                       // "5/1" 은 truthy — 통과한다
  const [hYear, hMonth, hDay] = h.holiday_date.split('-').map(Number);
  //   "5/1".split('-')  ->  ["5/1"]  ->  map(Number)  ->  [NaN]
  //   hYear = NaN, hMonth = undefined, hDay = undefined
  const hDate = new Date(Date.UTC(hYear, hMonth - 1, hDay));   // Invalid Date
  ...
  const dtStart = formatICSDateOnly(hDate);
```

그리고 [route.ts:18](../../../app/api/calendar/feed/route.ts#L18):

```ts
function formatICSDateOnly(date: Date): string {
  return date.toISOString().split('T')[0].replace(/-/g, '');
}
```

`new Date(NaN).toISOString()` 은 값을 반환하지 않는다 — **`RangeError: Invalid time value` 를 던진다.** (실행 확인함)

`company_holidays` 조회를 감싼 try/catch 는 [route.ts:108–136](../../../app/api/calendar/feed/route.ts#L108) 의 **질의 부분만** 덮는다. 예외가 터지는 루프는 그 밖이라 [route.ts:248](../../../app/api/calendar/feed/route.ts#L248) 의 최상위 catch 로 떨어지고:

```ts
return new NextResponse('Internal Server Error', { status: 500 });
```

### 영향

`company_name = '전체'` 이므로 이 행은 **모든 직원의 조회 결과에 포함된다.** 즉 `/api/calendar/feed?token=…` 는 **구독한 전 직원에게 항상 500** 이다.

공유캘린더 화면의 "구독" 버튼([공유캘린더.tsx:333](../../../app/main/기능부품/공유캘린더.tsx#L333))으로 이 URL 을 받아 구글/애플 캘린더에 등록한 사람은, 캘린더 앱이 조용히 동기화를 멈춘다. **에러 화면이 없어 사용자는 "일정이 안 올라온다"로만 인지한다.**

> 화면 안의 공유캘린더 자체는 죽지 않는다 — [공유캘린더.tsx:230](../../../app/main/기능부품/공유캘린더.tsx#L230) 은 `.gte/.lte` 문자열 비교라 `"5/1"` 이 모든 월 범위에서 그냥 빠진다. 그래서 **근로자의날이 캘린더에 안 보이는 것**은 별개의 증상으로 계속 있었다.

### 반증 조건 (falsifier)

- `holiday_date = "5/1"` 인 행이 실제로는 조회되지 않는다면 → 확인함, `company_name='전체'` 조건에 걸려 조회된다.
- `formatICSDateOnly` 앞에 유효성 검사가 있다면 → 확인함, 없다.
- `new Date(NaN).toISOString()` 이 던지지 않는다면 → 확인함, `RangeError` 를 던진다.

### 수정 (난이도 S)

두 가지를 **함께** 해야 한다. 데이터만 고치면 다음에 누가 또 잘못 입력했을 때 같은 일이 난다.

1. **데이터**: 해당 행의 `holiday_date` 를 `2026-05-01` 로 교정 (반복 공휴일 개념이 없으므로 연도별 행이 필요한지 별도 판단).
2. **코드**: 루프 안에서 파싱 결과를 검증하고, 잘못된 행은 이벤트를 건너뛰되 나머지 피드는 정상 반환한다.

```ts
const [hYear, hMonth, hDay] = h.holiday_date.split('-').map(Number);
if (!Number.isFinite(hYear) || !Number.isFinite(hMonth) || !Number.isFinite(hDay)) {
  console.warn('[calendar/feed] 잘못된 holiday_date, 건너뜀:', h.id, h.holiday_date);
  continue;
}
```

같은 방식으로 `nurse_schedules`·`leave_requests` 루프도 함께 방어하는 것을 권한다 — 한 행이 피드 전체를 죽이는 구조 자체가 문제다.

## P-07 · 중복 1:1 방 때문에 메시지 450건이 화면에서 사라져 있다 — **P0**

### 관측

```
chat_rooms 502개   notice 1 · direct 461 · group 40
  members JSON 파싱 실패 0 · 배열 아님 0 · 멤버 중복 0     (구조 자체는 건강)
  멤버가 1명인 direct 방(나와의 채팅) : 198개 / 461개
  동일 멤버 조합에 방이 2개 이상       : 42쌍
  중복으로 생긴 여분 방                : 159개
```

한 사람에게 자기 자신과의 방이 42개 있다:

```
병동팀1   방 42개 (그중 대화 있는 방 4개)
이나림    방 33개 (그중 대화 있는 방 2개)
외래팀1   방 10개 (그중 대화 있는 방 9개)
외래팀1 ↔ 김정수   방 7개 (그중 대화 있는 방 3개)   ← 실제 1:1 대화가 3개로 쪼개짐
```

### 무슨 일이 벌어지는가

목록은 중복 방을 **표시할 때 합친다.** [data-hooks.ts:206](../../../app/main/모바일/채팅/data-hooks.ts#L206) 의 dedup 은 `getDirectRoomMembersKey` 로 같은 멤버 조합을 묶고 **가장 최근 활동한 방 하나만 남긴다**:

```ts
const roomKey = getDirectRoomMembersKey(room) || `room:${room.id}`;
const previousTime = roomActivityMs(previousRoom);
const currentTime = roomActivityMs(room);
if (!previousRoom || currentTime >= previousTime) dedupedRooms.set(roomKey, room);
```

여기까지는 PC 도 같다. 갈리는 곳은 **방을 열었을 때 메시지를 어떻게 조회하는가** 다.

| | 메시지 조회 | 형제 방 |
|---|---|---|
| **PC** [메신저방데이터훅.ts:1106](../../../app/main/기능부품/메신저방데이터훅.ts#L1106) | `.in('room_id', roomIdsToLoad)` | **합쳐서 보여준다** |
| **모바일** [data-hooks.ts:569](../../../app/main/모바일/채팅/data-hooks.ts#L569) | `.eq('room_id', currentRoomId)` | **대표 방 하나만** |

PC 는 `getConversationRoomIdsByRoomId(roomId, rooms)` 로 형제 방 id 를 모두 펼쳐 `.in()` 으로 한꺼번에 읽는다([:1082](../../../app/main/기능부품/메신저방데이터훅.ts#L1082)). 모바일은 선택된 방 하나만 읽는다.

모바일도 이 함수를 **이미 쓰고 있다** — 읽음 커서를 형제 방까지 일괄 갱신하는 데만 쓰고([data-hooks.ts:662](../../../app/main/모바일/채팅/data-hooks.ts#L662)), 정작 메시지 조회에는 안 쓴다. 안읽음 개수도 형제 방까지 합산한다(`getConversationUnreadCountForRoom`). **개수는 합치고 내용은 안 합치는 상태다.**

> 그래서 증상이 "안읽음 배지는 뜨는데 방을 열면 그 메시지가 없다" 로도 나타난다.

### 이것은 모바일 전용 결함이다

같은 계정으로 PC 에서 보면 450건이 정상으로 보인다. **모바일에서만 사라진다.** PC↔모바일 패리티 깨짐이다.

### 영향 — 실측

```

이나림          보이는 방    0건 / 가려진 방 2개에 229건   ← 열면 빈 화면인데 메모 229건이 있다
백민 ↔ 임귀섭    보이는 방  168건 / 가려진 방 1개에  31건
홍자비          보이는 방    1건 / 가려진 방 3개에  30건
백민 ↔ 정경란    보이는 방    8건 / 가려진 방 2개에  28건
백정민          보이는 방    3건 / 가려진 방 2개에  27건
외래팀1         보이는 방    5건 / 가려진 방 8개에  14건
```

**이나림이 "나와의 채팅"을 열면 빈 방이 뜬다.** 실제로는 다른 방 2개에 메모 229건이 들어 있는데 최근 활동 시각이 낮아 선택되지 않는다.

### 원인 후보 (미확정)

방 생성 전에 기존 방을 찾는 로직은 있다 — [새대화.tsx:561](../../../app/main/모바일/채팅/새대화.tsx#L561):

```ts
async function findExistingDirectRoom(memberIds: string[]) {
  const { data } = await fetchAllChatRooms({ force: true });
  return rooms.find((room) =>
    room.type === 'direct' && haveSameMembers(normalizeMemberIds(room.members), memberIds)) || null;
}
```

`fetchAllChatRooms` 는 LIMIT 없이 `chat_rooms` 전체를 조회하고([chatQueryService.ts:107](../../../app/main/기능부품/chatQueryService.ts#L107)), D1 게이트웨이도 `limit` 미지정 시 LIMIT 절을 붙이지 않는다([query/route.ts:257](../../../app/api/d1/query/route.ts#L257)). 502행은 행 단위 정책의 `MAX_LIMIT`(1000)에도 걸리지 않는다. **즉 "목록을 못 받아서" 는 아니다.**

문제는 **이 검사가 클라이언트에만 있다는 것**이다. 서버 생성 경로 [app/api/chat-rooms/route.ts:164](../../../app/api/chat-rooms/route.ts#L164) 는 `body.id` 가 없으면 그냥 새 UUID 로 insert 한다 — **중복 검사도, UNIQUE 제약도 없다**:

```
1) body.id 가 있으면: insert + onConflictDoUpdate
2) body.id 가 없으면: insert with crypto.randomUUID()      ← 무조건 새 방
```

실제 자기방 id 도 전부 무작위 UUID 다(결정적 id 규약 없음):

```
f7d12913-3c31-4987-af0e-969920047e22   2026-08-26T07:14:52
0b21f2f4-5934-4c9b-a088-dee0374ab885   2026-08-26T04:27:48
12c974b4-5d3a-4e23-962d-7217e3892a70   2026-08-04T09:39:32   ← 1초 차이
ed857b82-d45a-49c2-8bc1-d49524ff2730   2026-08-04T09:39:31   ← 동시 생성 레이스
```

**2026-08-04 09:39:31 과 09:39:32 — 1초 차이로 두 개가 생겼다.** 조회 후 생성 사이에 다른 탭/기기가 끼어든 전형적인 레이스다. PC 쪽에도 별도 생성 경로가 있어([메신저.tsx:1706](../../../app/main/기능부품/메신저.tsx#L1706)) 창을 두 개 열어 두면 재현된다.

즉 원인은 **"유일성이 클라이언트에서만, 그것도 best-effort 로 지켜지고 있다"** 는 것이다. 서버에 제약이 없으므로 레이스·다중 경로·캐시 지연 어느 하나만 겹쳐도 중복이 생긴다.

### 수정 (2단계 — 1번은 난이도 S)

**1. 모바일 메시지 조회를 PC 와 같게 (난이도 S · 즉시 450건 복구)**

데이터를 옮길 필요가 없다. PC 가 이미 하고 있는 것을 모바일도 하면 된다:

```ts
// data-hooks.ts refresh() — 현재
.eq('room_id', currentRoomId)

// 형제 방까지 (PC 와 동일)
const conversationRoomIds = getConversationRoomIdsByRoomId(currentRoomId, roomsData);
.in('room_id', conversationRoomIds.length ? conversationRoomIds : [currentRoomId])
```

같은 변경이 `loadOlder`([:649](../../../app/main/모바일/채팅/data-hooks.ts#L649))·읽음카운트·폴링 구독 필터에도 필요하다. 함수는 모바일에 이미 import 돼 있다.

> **회귀 위험**: 형제 방이 없는 방(대다수)에서는 `[currentRoomId]` 한 개라 동작이 완전히 동일하다. 형제가 있는 51개 방에서만 결과가 달라진다 — 그리고 그 달라짐이 바로 목적이다. PC 에서 이미 같은 방식으로 돌고 있다는 점이 근거다.

**2. 중복 생성 자체를 막기 (난이도 M · 근본 해법)**

1번만 하면 화면은 정상이 되지만 방은 계속 늘어난다. 서버에 유일성을 둔다:
`chat_rooms` 에 정규화된 멤버 키 컬럼 + UNIQUE 인덱스를 추가하고, 생성 경로([route.ts:164](../../../app/api/chat-rooms/route.ts#L164))를 insert 에서 upsert 로 바꾼다.

> **순서 주의**: 2번을 먼저 하면 기존 159개 중복은 그대로 남아 450건이 계속 안 보인다. **1번이 먼저다.**
> 기존 중복 방 병합(데이터 이관)은 1·2 가 끝난 뒤 선택 사항이다 — 1번이 들어가면 화면상 문제가 없어지므로 급하지 않다.

## P-02 · 근태가 두 테이블에 이중 기록되며 어긋나 있다 — **P1**

### 관측

```
attendance  (단수)  3,442행   2026-03-11 ~ 2026-08-26 17:00:15
attendances (복수)  3,222행   2026-03-11 ~ 2026-08-26 17:00:15
```

둘 다 **지금도 같은 크론이 쓰고 있다** (마지막 기록 시각 동일). 스키마는 다르다:

| | attendance (단수) | attendances (복수) |
|---|---|---|
| 날짜 | `date` | `work_date` |
| 출퇴근 | `check_in` / `check_out` | `check_in_time` / `check_out_time` |
| 추가 | — | `work_hours_minutes`, `current_status`, `current_status_at`, `company_name` |

`(staff_id, 날짜)` 기준 차집합:

```
attendance(단수)에만 있는 것 : 337건
attendances(복수)에만 있는 것 : 117건
```

월별로 보면 드리프트는 대부분 과거에 발생했고 최근은 거의 멎었다:

```
2026-08   1건      2026-06  103건
2026-07   5건      2026-05  227건
2026-03   1건
```

### 영향 — 급여정산이 적은 쪽을 읽는다

[급여정산.tsx:568](../../../app/main/기능부품/인사관리서브/급여명세/급여정산.tsx#L568) 이 `attendances`(복수)를 읽어 [:650](../../../app/main/기능부품/인사관리서브/급여명세/급여정산.tsx#L650) 에서 **지각·조퇴 분을 계산**한다. 그런데 급여 대상 월의 행 수가 다르다:

```
2026-06   attendance 614행 · attendances 512행 · 차이 102
2026-07   attendance 726행 · attendances 723행 · 차이   3
2026-08   attendance 667행 · attendances 666행 · 차이   1
```

**2026년 6월 급여정산은 근태 102행이 없는 상태로 계산됐다.** 7·8월은 각각 3행·1행이다.

참조 수도 갈려 있다 — 코드에서 `from('attendance')` 25곳, `from('attendances')` 27곳. 화면마다 읽는 테이블이 다르다:

### 수정 (난이도 L — 단계적으로)

이건 한 커밋으로 끝낼 일이 아니다. 순서대로:

1. **(즉시·읽기전용)** 6월 급여정산 결과가 102행 누락으로 실제 금액 차이를 냈는지 산정한다. 차이가 없다면(해당 102행이 전부 정상 출퇴근이라 지각·조퇴 0분) 소급은 불필요하다.

## P-03 · 타임스탬프 형식이 38개 컬럼에서 혼재한다 — **P1 (잠복)**

151개 테이블의 타임스탬프성 컬럼 348개를 전수 조사했다. 그중 **38개 컬럼**이 한 컬럼 안에 두 형식을 함께 담고 있다.

| 컬럼 | 공백형 `2026-08-26 05:57:54` | T형 `…T05:57:54+00:00` |
|---|---:|---:|
| `messages.created_at` | 13,063 | 10,975 |
| `notifications.read_at` | 1,186 | 7,232 |
| `audit_logs.created_at` | 247 | 5,998 |
| `shift_assignments.created_at` | 2,012 | 1,470 |
| `attendance.created_at` | 2,098 | 1,344 |
| `attendances.created_at` | 1,867 | 1,355 |
| `board_post_reads.created_at` | 1,102 | 726 |
| `message_reactions.created_at` | 688 | 347 |
| `room_read_cursors.last_read_at` | 758 | 211 |
| `approvals.created_at` | 428 | 280 |
| `leave_ledger.created_at` | 143 | 355 |
| `payroll_records.created_at` | 80 | 56 |
| … (그 외 26개 컬럼) | | |

전체 목록은 [`_data/timestamp-format.json`](_data/timestamp-format.json).

### 왜 위험한가

두 가지 경로로 틀린다.

**1. JS 파싱** — `new Date()` 는 공백형을 **로컬(KST)** 로, T형을 **UTC** 로 읽는다. 같은 시각이 9시간 어긋난다:

```
new Date("2026-08-26 05:58:30")        -> 2026-08-25T20:58:30Z
new Date("2026-08-26T05:58:30+00:00")  -> 2026-08-26T05:58:30Z
                                          차이 -9시간
```

**2. SQL 문자열 비교** — `'T'`(0x54) > `' '`(0x20) 이므로 **같은 날짜 안에서 대소가 뒤집힌다.**

### 채팅 읽음 판정에서는 아직 0건이다

이 결함이 **채팅 읽음 판정에서** 실제로 잘못된 결과를 내는지 전수 대조했다:

```
검사 대상 (메시지 × 수신자) 쌍 : 47,768건 (전체 이력, 메시지 23,630건)
  판정 동일                    : 47,768
  안읽음 -> 읽음 (배지 오해소)  : 0
  읽음 -> 안읽음 (과대읽음)     : 0
```

**0건이다.** 형식이 시기별로 갈렸기 때문이다 — T형 메시지는 2026-08-07 에 끊겼고 같은 시기의 커서도 T형이라 서로 짝이 맞는다. 형식이 섞이는 쌍은 날짜가 며칠씩 벌어져 있어 9시간 오차가 경계를 넘지 못한다.

### 그러나 다른 기능에서는 이미 발현 중이다 — 판단 정정

> 처음에 이 항목을 "잠복, 현재 발현 없음"으로 적었다. **틀렸다.** 채팅 읽음만 확인하고 다른 소비 지점을 보지 않은 결과다. 코드 감사(02)가 같은 혼재를 소비하는 지점 4곳에서 **실제 오동작**을 확인했다:

| id | 증상 | 심각도 |
|---|---|---|
| `TZ-05` | 채팅 보관정책 삭제가 T형 커트오프를 공백형 `created_at` 과 사전순 비교해 **커트오프 날짜의 메시지를 최대 하루 일찍 영구 삭제**한다 | **데이터 손실** |
| `TZ-01` | 메신저운영센터의 공지 SLA 가 공백형을 raw `new Date()` 로 읽어 경과시간을 **항상 +9시간**으로 계산 — 올리자마자 "SLA 초과" | P2 |
| `TZ-06` | 모바일 결재함 경과일도 같은 +9시간 — **기안 15시간 만에 "24h 초과" 배지** | P2 |
| `TZ-04` | 메시지 수정·삭제 감사 로그가 공백형으로 저장되는데 감사 요약 API 는 T형 커트오프로 필터 → **"오늘 로그" 집계에서 누락** | P2 |

상세는 [`02_코드감사.md`](02_코드감사.md) 의 시간대 도메인 항목을 볼 것.

**따라서 이 항목은 잠복이 아니라 활성 P1 이다.** 특히 `TZ-05` 는 되돌릴 수 없는 삭제라 우선순위가 높다.

### 수정 (난이도 M)

읽는 쪽 정규화가 이미 있다 — `lib/chat-read-cursors.ts` 의 `toUtcSqlTimestamp()` 는 두 형식을 모두 올바르게 UTC 공백형으로 바꾼다. 채팅 읽음 계산은 커밋 `ebf295b5` 에서 이 함수로 통일했다(동작 변화 0건임을 위 47,768쌍 대조로 확인).

남은 것:

1. **쓰는 쪽 통일** — 어느 코드가 아직 T형을 쓰는지 확정하고 한 규약으로 모은다. (단, `notifications.read_at` 은 ISO 가 규약이다 — 커서와 규약이 다르므로 섞지 말 것. `data-hooks.ts` 주석 참조.)
2. **데이터 정규화** — 38개 컬럼 일괄 `UPDATE`. 다만 **`messages` 24k행 등 대형 테이블을 운영 중에 건드리는 일**이라, 읽는 쪽 정규화가 끝난 뒤에 하는 것이 안전하다. 지금은 필요하지 않다(위 0건).

## P-08 · 결재자가 없는 연차 결재 31건이 영원히 대기 상태 — P2

### 관측

```
approvals 상태 분포        승인 437 · 회수 178 · 대기 71 · 반려 22

NULL 인 31건은 **전부 같은 성격**이다:

```
type = 연차/휴가 · doc_type 없음 · 31건 · 2026-06-01 ~ 2026-07-16
approval_line 이 있는 건 : 0건    ← 결재선 자체가 비어 있다

```
승인 437건 중 NULL   0
반려  22건 중 NULL   0
회수 178건 중 NULL 178   ← 회수 시 비우는 것은 정상
대기  71건 중 NULL  31   ← 이 31건만 비정상
```

제목은 전부 `[연차/휴가] {이름} - 연차 신규 부여` 또는 `- 도입 전 사용 소급` 형태다. **연차 원장 도입 시 만들어진 이력성 문서**로 보인다.

### 영향

결재선이 비어 있어 **누구의 결재함에도 뜨지 않고, 승인도 반려도 불가능하다.** 다만 기안자 본인의 "내 기안" 목록에는 계속 **대기**로 남는다. 31명이 각자 영구 미결 문서를 하나씩 이상 보고 있다.

2026-07-16 이후로는 새로 생기지 않았다 — 생성 경로는 이미 고쳐졌거나 더는 쓰이지 않는다.

### 반증 조건

- 이 문서들이 화면에 안 보인다면 → **미확인.** 기안자 목록 필터를 읽어 확인해야 한다.
- 연차 자체는 원장에 정상 반영됐고 문서만 남은 것이라면 → 그럴 가능성이 높다(제목이 소급/부여). 그렇다면 잔여연차 값에는 영향이 없다.

### 수정 (난이도 S)

기능 결함이 아니라 데이터 잔재로 보인다. **연차 값에 영향이 없음을 먼저 확인한 뒤**, 31건의 상태를 `승인`(이미 반영된 이력이므로) 또는 별도 상태로 정리한다. 코드 수정보다 담당자 판단이 먼저다.
