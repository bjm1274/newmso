## 분류별 발견

### SEC 보안 (권한·업로드·XSS)
- **SEC-1 [높음] 회수 API가 구(舊) Supabase 스택 사용 — D1 환경에서 동작 불가.**
  `app/api/approval/recall/route.ts:14,18-22,57` — `import { createClient } from '@supabase/supabase-js'` 로 실제 Supabase 클라이언트를 만들고 `NEXT_PUBLIC_SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`/`auth.getUser()` 사용. 그러나 `lib/supabase.ts:4` 주석대로 "Supabase 런타임 의존 제거(D1 컷오버 완료)" — Supabase Auth/REST는 더 이상 존재하지 않음. 따라서 `auth.getUser()`는 항상 실패→`401 인증이 필요합니다`. 결재상세의 [회수] 버튼은 사실상 전부 실패(롤백). 모바일 회수 기능 전체가 죽은 경로(의심: 환경변수 잔존 시 다른 프로젝트로 오작동 가능).
- **SEC-2 [높음] 회수 API actor 매핑 컬럼 오류.**
  `recall/route.ts:68` — `.eq('user_id', actorAuthId)` 로 staff 조회하나 `staff_members`에 `user_id` 컬럼 **없음**(정본 schema.ts:2036 `auth_user_id`). 설령 Supabase가 살아있어도 actorStaffId=null → `403 기안자 본인만 회수`.
- **SEC-3 승인/반려 권한 — 서버 검증 양호(정상).**
  `lib/server-approval-transition.ts:414` `if (!actor.isAdmin && String(effectiveCurrentApproverId) !== String(actor.id)) {...}` 로 현재 결재자 본인/관리자만 처리. `app/api/approvals/transition/route.ts:10-13` 세션 인증. 클라(결재상세.tsx:213 `canApprove`)는 UI 게이트일 뿐 서버가 재검증 → OK.
- **SEC-4 첨부 MIME/크기 — 클라+서버 이중 검증(양호).**
  클라 `AttachmentPicker.tsx:89-114`(50MB·image/pdf/text/application), 서버 `app/api/approval/upload/route.ts:19-44`(50MB·BLOCKED_MIMES exe 차단). 단 `isDoc = mime.startsWith('application/')`(라인 104)은 사실상 모든 application/* 통과 — 서버에서 exe 3종만 차단하므로 zip 등 광범위 허용(의심: 정책 검토 권장).

### D 중복 (데스크톱 ↔ 모바일)
- **D-1 transition/recall API 공유(정상적 재사용).** 모바일 `data-hooks.ts:256,230` 와 PC `useApprovalActions`/`useApprovalBulkActions` 모두 `/api/approvals/transition` 호출 — 서버 로직 단일화. 중복 아님(양호).
- **D-2 doc_number 생성 로직 부분 재구현.** `data-hooks.ts:312 generateMobileDocNumber` 가 PC `createStructuredDocNumber` 패턴을 별도 구현(approvals count 쿼리). `buildApprovalDocNumber`/`resolveApprovalDocNumberConfig`는 공유하나 시퀀스 쿼리는 중복(의심: 동시 상신 시 시퀀스 충돌 가능 — P 항목과 연계).

### Q 유사기능 (정합성)
- **Q-1 [높음] 모바일 첨부가 approvals와 연결 안 됨(데이터 유실).**
  `AttachmentPicker.tsx:121-133` — `enqueueUpload(...onSuccessAction:{kind:'insert',table:'approval_attachments',...})`. `approval_attachments` 테이블은 정본 schema.ts에 **없음**(Grep 확인). 반면 PC는 첨부를 `approvals.meta_data.attachments`에 저장(`useApprovalSubmit.ts:602-617,659`), 상세도 거기서 읽음(`결재상세.tsx:518 normalizeApprovalAttachments(meta_data.attachments)`). 게다가 `연차신청폼.tsx`는 `attachments` state를 **meta_data에 절대 기록하지 않음**(라인 260는 queued 개수 toast용으로만 사용). 결론: 모바일 첨부는 ①존재하지 않는 테이블 insert로 무음 실패, ②설령 성공해도 approval과 미연결 → 상세에서 영원히 안 보임. 기능 사실상 무효.
- **Q-2 필터 type 값과 실제 저장 type 불일치 의심.**
  `필터시트.tsx:41-54` TYPE_OPTIONS=`'연장근무','물품신청','출결정정'...` vs 작성하기 슬러그/연차폼 type=`'연차/휴가'`. 필터는 `결재함.tsx:113 filter.types.includes(rowType)` 로 `row.type` 정확 일치 비교. PC가 저장하는 type 라벨과 다르면 해당 필터 무효(의심: PC type 라벨 대조 필요).

### S 문법/런타임
