### [SEC/D1/높음] 중간정산 record_type 충돌 회피 꼼수
`중간정산.tsx:549` `const yearMonth = settlementDate.slice(0,7) + '-I';` 로 `year_month`에 `-I` 접미사를 붙여 정규(regular) 레코드와의 PK 충돌을 회피.
- record는 `record_type:'interim'`(L578)을 가지지만 conflict target은 `staff_id,year_month`(L584).
- 정본 unique가 record_type 포함이므로, `-I` 꼼수 없이 동일 `year_month`로 저장하면 정규 급여를 덮어쓸 위험이 있어 우회한 것으로 보임. → 정본 헬퍼(record_type 포함 target) 사용 시 `-I` 꼼수 제거 가능하며, `year_month`가 실제 정산월과 달라 조회/집계 로직(`급여대장월별요약` 등 `eq('year_month')`)에서 누락될 소지.

### [급여정산 무음실패 위험]
`@/lib/supabase` D1 프록시는 잘못된 컬럼/충돌 타깃에서 무음 실패 가능. 급여정산은 `withMissingColumnsFallback`로 컬럼 누락은 방어하나, **conflict target이 레거시라 record_type 분리 미적용 환경에서 동일 (staff,월) 정규/중간 레코드 간 덮어쓰기 가능**. 정본 헬퍼는 이 경우 `PAYROLL_RECORD_TYPE_MIGRATION_REQUIRED_ERROR`로 명시 차단(`payroll-record-upsert.ts:196-202`)하므로 안전.

## 3. 금액 계산 정확성 (반올림/소수)

- **지방소득세 절사 일관성**: 급여정산 L1210·중간정산 L473·일용근로정산 L110은 `Math.floor(incomeTax*0.1/10)*10`(10원 절사, 국고금관리법 §47). 그러나 **급여상세.tsx:295 폴백은 `Math.floor(incomeTax*0.1)`** (절사 없음) — 미세 불일치(Q).
- **급여상세 소득세 폴백 산식 상이(Q/중)**: `급여상세.tsx:294` record 없을 때 `incomeTax = Math.floor(taxable*0.03)` (3% 단순), 보험은 `calculateEmployeeInsuranceDeductions`(고정 2026 요율). 실제 정산(`calculateMonthlyIncomeTax` 간이세액표)과 다른 숫자를 미리보기로 노출 → 마이페이지 급여명세서(record 없는 신규월)에서 실제 확정액과 괴리. 폴백임을 UI에 명시 권장.
- 그 외 `Math.floor`(공제는 절사) / `Math.round`(지급액) 사용은 일관적.

## 6. 문법/런타임 (S)

- **[S-1/중] 급여정산 "연장/상여" 입력 필드 버그**: `급여정산.tsx:1731-1734`
  ```
  label="연장/상여"
  value={Number(data.overtime_pay) + Number(data.bonus)}   // overtime+bonus 합으로 표시
  onChange={(nextValue) => updateData(s.id, 'overtime_pay', nextValue)}  // overtime_pay에만 기록
  ```
  표시는 `overtime_pay+bonus` 합이지만 편집은 `overtime_pay`에만 반영. 기존 `bonus>0`인 직원의 값을 사용자가 조정하면 합계가 overtime_pay로 흡수되고 bonus는 별도 잔존 → 다음 표시에서 이중 계상되거나 사용자 의도와 불일치. 계산(`calculateSalary` L1147)은 overtime+bonus 둘 다 과세에 더하므로 금액 자체는 보존되나, bonus가 영구히 "보이지 않는" 상태로 남음.
