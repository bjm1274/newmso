## SEC 보안

### [SEC-1] 높음 — 납품확인서 인쇄 XSS (document.write 미이스케이프)
`납품확인서.tsx:68-100` `printDelivery()`. 사용자 입력(supplier_name, receiver_company, notes, item.name, item.spec, supplier_rep 등)을 이스케이프 없이 새 창 HTML에 삽입.
```
// 91: items.map -> `<td>${item.name}</td><td>${item.spec || '-'}</td>...`
// 95: ${d.notes ? `<p>...<strong>비고:</strong> ${d.notes}</p>` : ''}
// 83: 문서번호: ${d.doc_number} ... 발행일: ${d.issue_date}
```
`window.open()` + `win.document.write()`로 동일 출처 새 창에 렌더되므로, 품목명/비고에 `<img src=x onerror=...>` 또는 `<script>`가 저장돼 있으면 인쇄 시점에 실행됨. 저장형 XSS. → 모든 보간 값에 HTML escape 적용 필요.

### [SEC-2] 높음 — 명세서관리 특별임무: "HTML 렌더 XSS"
특별임무 지목과 달리 `명세서관리.tsx` 자체에는 `dangerouslySetInnerHTML`/`document.write`가 **없음**(`window.print()`만, 585행). 실제 명세서/거래처 문서 XSS 위험은 위 SEC-1(납품확인서)에 존재. 동일 메뉴군(거래처/명세서 워크스페이스)의 인쇄 경로 위험으로 통합 관리 권장.

## DB 정합성 (정본 schema.ts 대조)

### [DB-1] 높음 — suppliers에 없는 컬럼 insert/update (reg_num, ceo) → D1 무음 실패
정본 `suppliers`(schema.ts:2134-2151) 컬럼: name, contact, phone, address, email, contact_name, business_number, category, contract_start, contract_end, payment_terms, notes, created_by, created_at, updated_at. **reg_num·ceo 컬럼 없음**(ceo는 companies.ceo_name만 존재, schema.ts:411).

- `명세서관리.tsx:75` `supabase.from('suppliers').insert([supplierForm])` — supplierForm에 `reg_num`,`ceo` 포함(43-51).
- `명세서관리.tsx:112-121` update payload에도 `reg_num`,`ceo` 포함.
- 조회 측도 `supplier.reg_num`(277), `supplier.ceo`(280), `s.reg_num`/`s.ceo`(433-438, 475-480) 참조 → 항상 undefined.

→ 거래처관리.tsx는 올바른 컬럼(`contact_name`,`business_number`)을 쓰는데, 명세서관리.tsx는 사장된 컬럼명(reg_num/ceo)을 사용. 사업자번호·대표자가 저장도 표시도 안 됨(무음 실패).

### [DB-2] 높음 — AS반품관리: 존재하지 않는 테이블 (as_repair_records, return_records)
`AS반품관리.tsx`가 `as_repair_records`(75,121,126,204,242), `return_records`(91,165,171,219,263)를 `.from()`. 정본 schema.ts에 두 테이블 **없음**. `lib/db/auth/policies.ts:516-517`가 자체 audit 주석으로 명시: "클라이언트가 from() 호출하지만 테이블이 실제 존재하지 않음(PGRST205) … 현재도 동작하지 않는 미완성/사장 기능".
→ Supabase 분기는 항상 실패 → `catch`로 localStorage 폴백(85,101,...). 즉 AS/반품 데이터는 전부 브라우저 localStorage에만 존재(기기간 미동기, 서버 백업 없음). 실질 기능 결함.

### [DB-3] 높음 — 발주관리: 카드 하이라이트 키가 항상 null (정합성 깨짐)
`발주관리.tsx:50-53` `normalizePurchaseOrderRecord`가 `items[0].source_supply_approval_id`/`source_supply_request_index`를 읽음. 그러나 purchase_orders.items는 발송 시 `{item_id,name,qty,unit_price}`만 저장(PurchaseOrderModal.tsx:108-113, 발주관리.tsx:232-237). 즉 items 요소에 source_* 필드가 없어 sourceApprovalId가 항상 null → 결재 연동 발주의 카드 하이라이트/scrollIntoView(146-156)가 purchase_order 레코드에는 절대 매칭 안 됨. (approval 레코드 경로 71-99만 동작.)

### [DB-4] 중 — 명세서관리 invoice는 영속화 없음
`명세서관리.tsx`의 거래명세서(invoiceData)는 저장 API가 없고 `window.print()`만(585). delivery_confirmations 같은 저장 테이블 미사용. 의도된 사양일 수 있으나, "명세서 관리"라는 이름과 달리 이력이 남지 않음(거래처 추가/수정만 영속). U/설계 확인 필요.

## Q 유사기능 / D 중복

### [Q-1] 중 — 거래처 CRUD 이중 구현 (거래처관리 vs 명세서관리)
동일 메뉴(SupplierDocumentWorkspace 탭)에서 두 컴포넌트가 suppliers를 각자 CRUD.
- `거래처관리.tsx`(SupplierManagement): contact_name/business_number 사용(올바름), ResponsiveTable.
- `명세서관리.tsx`(InvoiceManagement): 동일 거래처 추가/수정/삭제 UI를 중복 보유(68-158) + reg_num/ceo 잘못된 컬럼(DB-1).
→ 거래처 추가/수정/삭제 로직이 두 곳에 분산. 명세서관리는 명세서 작성에 집중하고 거래처 CRUD는 거래처관리로 단일화 권장.

### [Q-2] 중 — 발주서 insert 로직 중복 (발주관리 vs PurchaseOrderModal)
특별임무 지목. 두 곳이 거의 동일한 `purchase_orders.insert` 패턴(supplier_name/items/status:'대기'/total_amount/created_by/notes).
- `발주관리.tsx:247-256` (자동발주 생성)
- `PurchaseOrderModal.tsx:116-127` (거래처별 발송)
PurchaseOrderModal은 부서별물품장비현황/DeptInventoryTable/모바일에서 사용 중(죽은코드 아님). 공통 `createPurchaseOrder(supplierName, items, opts)` 헬퍼로 추출 시 중복 제거 + 누락 컬럼(supplier_id 등) 일관 적용 가능. PurchaseOrderModal은 supplier_id를 그룹에서 보유(SupplierGroup.supplierId)하나 insert에 안 넣음 → supplier_id가 항상 null로 저장(FK 미설정, schema.ts:1691).

### [Q-3 / D] 중 — 물품등록 데스크톱 vs 모바일
특별임무 지목(D). `재고관리서브/물품등록.tsx`와 `모바일/재고/물품등록.tsx`는 같은 `inventory` 테이블에 insert하나, 모바일은 오프라인 큐(enqueueSupabaseMutation), 카테고리/단위 매핑 테이블(CATEGORY_TO_DB/UNIT_TO_DB) 보유로 분기 정당. 다만 두 곳의 카테고리 옵션 집합이 상이(데스크톱: 의료기기/소모품/약품/사무용품/기타 vs 모바일: 의료소모품/영상의학/의약품/멸균소독/사무용품)해 입력 일관성 저하 — 카테고리 상수 공유 권장.

## 특별임무 결론 요약
- 발주관리 vs PurchaseOrderModal 중복: **확인**(Q-2). PurchaseOrderModal은 타 화면에서 사용 중이라 삭제 대상 아님 → 공통 헬퍼 추출. 추가로 supplier_id 미저장(DB FK 미연결) 발견.
- 명세서관리(591) HTML 렌더 XSS: **해당 파일엔 없음**. 실제 인쇄 XSS는 납품확인서.tsx printDelivery(SEC-1). 동일 메뉴군 보안 통합 권장.
- AS반품관리(675) 단일책임: Grid는 분리 양호. 단 **테이블 자체 부재(DB-2)** 로 Supabase 경로 전부 사장 → localStorage 전용으로 실질 동작. 단일책임보다 데이터 영속성이 더 큰 문제.
- 물품등록 vs 모바일물품등록 중복(D): 분기 정당(오프라인큐), 카테고리 상수만 공유 필요(Q-3).
- purchase_orders/suppliers 정합성: suppliers reg_num/ceo 무음실패(DB-1), purchase_orders source_*·supplier_id 미저장(DB-3, Q-2).
