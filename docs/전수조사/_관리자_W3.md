## ★특별임무 결론 (먼저)

1. **전자결재 preview-builder XSS — 해당 없음(오탐).** `preview-builder.ts`는 전부 정적 한글 더미 데이터를 반환하는 순수 함수이며, 렌더는 `DocumentPreviewCanvas.tsx`의 **JSX 텍스트 보간**으로만 처리된다. `dangerouslySetInnerHTML`/`innerHTML`/`document.write`/`eval`은 이 그룹(및 관리자전용서브 전체)에 **0건**(Grep 확인). React 자동 이스케이프로 XSS 경로 없음. 단, `design.backgroundLogoUrl`/`sealImageUrl`이 사용자 입력 `<img src>`로 들어가나(전자결재양식관리.tsx:801,810 입력 → Canvas:34,48,133) `javascript:` URI는 `<img src>`에서 실행되지 않으므로 위험 낮음.

2. **데이터백업/초기화 위험작업 — SEC 발견 있음(아래 SEC-1·2·3).** SQL 인젝션은 없음(D1 라우트가 drizzle `sql` 파라미터 바인딩 사용). 권한·확인절차에 허점 존재.

3. **감사로그뷰어 vs 접근감사로그 중복 — 오탐(중복 아님).** 서로 다른 테이블(`audit_logs` 데이터변경 이력 vs `access_logs` 접근 이력)을 보는 상호보완 화면. UI만 비슷(Q-1).

4. **데이터초기화 실제 삭제 범위(파괴적) — 아래 SEC-1에 전수 정리.**

## SEC 보안 (파괴작업·권한·인젝션)

### SEC-1 [높음] 데이터초기화 — 위험작업이 클라이언트 측 잠금만으로 직접 D1 삭제 실행
`데이터초기화.tsx:213-276` `runReset`. 잠금 해제(`handleUnlock`, :197-210)는 서버 `/api/admin/verify-unlock`으로 bcrypt 검증하지만, **해제 후 실제 삭제는 클라이언트가 직접 `supabase.from(...).delete()`를 호출**한다. 즉 `isUnlocked` state만 우회하면(또는 API를 직접 호출하면) 비밀번호 없이 전 테이블 삭제 가능.
- 서버 재검증을 거치는 것은 `staff`(`/api/admin/reset-staff`, :237) 뿐. 나머지 8종은 모두 클라 직접 삭제.
- 특히 `force_logout`(:258-263)은 `system_configs.min_auth_time` upsert로 전체 강제 로그아웃을 일으키는데 **비밀번호 재검증 자체가 없음**.
- 실제 삭제 범위(파괴성):
  - chat: `messages`, `message_reads`, `room_notification_settings`, `chat_rooms` 전건 (:218-223)
  - inventory: `inventory_logs`, `inventory` 전건 (:224-227)
  - board: `posts` 전건 + `board_post_comments` 전건 + `board_posts`(수술/MRI 제외) (:228-232)
  - schedule: `board_posts` 중 수술일정/MRI일정표/mri (:233-235)
  - system_logs: `audit_logs` 전건 (:248-250)
  - expired_contracts: `employment_contracts` status=pending & 30일 경과 (:251-254)
  - expired_popups: `popups` is_active=false (:255-257)
- 권고: 모든 reset type을 서버 API로 이관하고 매 호출 비밀번호(또는 세션 권한) 재검증.

### SEC-2 [중간] 데이터초기화 — `is_active=false` 비교 (D1 정본은 integer)
`데이터초기화.tsx:256` `.eq('is_active', false)`. 정본 `popups.is_active`는 `integer().default(1)` (schema.ts:1661). D1 mutate 라우트가 boolean→0/1 변환(`route.ts:110,168`)을 하므로 동작은 하나, 스키마상 정수 컬럼에 boolean 비교를 의존하는 패턴은 취약. `0` 사용 권장.

### SEC-3 [낮음] 감사로그뷰어 — LIKE 와일드카드 미이스케이프
`감사로그뷰어.tsx:71-75` `.or("...ilike.%${keyword}%...")`. 값은 D1 라우트에서 파라미터 바인딩되어 **SQL 인젝션은 아님**(query/route.ts:136 `sql\`${col} LIKE ${value}\``). 다만 사용자가 입력한 `%`/`_`가 LIKE 메타문자로 그대로 해석되어 검색결과가 왜곡될 수 있음(기능적 결함). 이스케이프 처리 권장.

## X 죽은코드

### X-1 [중간] 팝업창관리자 `isAllowedFile` (export, 미사용)
`팝업창관리자.tsx:31` `export function isAllowedFile`. 프로젝트 전체 Grep 결과 **정의부 1곳 외 참조 0건**. 게다가 메시지 오류: 본문 `'파일 크기는 25MB 이하여야 합니다.'`(:42)인데 실제 상한은 `MAX_VIDEO_BYTES = 200 * 1024 * 1024`(:10). 삭제 권장.

### X-2 [중간] 알림자동화설정 — `runCron`/setInterval 빈 동작
`알림자동화설정.tsx:269-281`. `setInterval(runCron, 24h)` 등록하나 `runCron` 본문(:272-277)은 주석만 있고 아무 동작 없음("백그라운드 자동 실행 logic (조용히 수행)"). 24시간 간격 클라이언트 타이머는 실제 cron 역할도 못 함. 죽은 코드.

### X-3 [낮음] 데이터백업 — `AuditRowProps`/미사용 인터페이스 패턴은 아니나 `isMissingTableError(error, 'system_settings')` 분기 등 D1 환경에서 절대 미도달 가능
`store-utils.ts:9-14 isMissingTableError`는 Postgres 코드 `PGRST205` 검사 — D1 전환 후엔 발생 불가한 코드. `데이터백업.tsx:149-153 isMissingRestoreRunSchema`도 `42P01`(Postgres) 검사로 D1에선 미도달. 폐기/대체 검토.

## E 에러처리

### E-1 [중간] 데이터초기화 — chat/inventory/board 다중 delete가 부분 실패 무시
`데이터초기화.tsx:218-235`. 연속 `await supabase...delete()` 호출들이 각 결과의 `error`를 확인하지 않음. 첫 단계 성공·둘째 실패해도 throw되지 않아 "성공" 토스트(:265)가 뜰 수 있음. 부분 삭제 상태로 데이터 정합성 깨질 수 있음.

### E-2 [낮음] 알림자동화설정 — 루프 내 throw가 이미 발송된 건 롤백 불가
`알림자동화설정.tsx:227 if (notifError) throw notifError`. 다건 루프(:176~) 중간에서 throw하면 이미 INSERT된 `notifications`/로그는 남고 카운트만 유실. 부분 성공 안내 부재.

## P 성능

### P-1 [중간] 데이터백업 복원 — 테이블별 전건 롤백 스냅샷 직렬 읽기
`데이터백업.tsx:459-472`. 복원 전 모든 대상 테이블을 `readAllRows`(1000행 페이지네이션)로 **직렬** 전건 조회해 메모리에 적재 후 다운로드. 대용량 테이블에서 메모리/시간 급증. 복원 본 루프(:494-525)도 직렬.
