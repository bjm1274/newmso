## 3. 런타임 권한 검증 — 396케이스

`node scripts/verify-policies.mjs` (로컬 D1 시드 + dev 서버, 원격 차단 설계)

```
총 396건 · 통과 392건 · 실패 4건
테이블별 실패:  staff_evaluations  4
```

| 테이블 | 행위자 | 동작 | 기대 | 실제 |
|---|---|---|---|---|
| staff_evaluations | admin | 본인 update | 허용 | ERR 500 |
| staff_evaluations | admin | 타인 update | 허용 | ERR 500 |
| staff_evaluations | admin | insert | 허용 | ERR 500 |
| staff_evaluations | hr(001) | insert | 허용 | ERR 500 |

**이 4건은 정책 결함이 아니다.** 하네스가 주석으로 "픽스처 한계"라고 주장하는데, 그 주장을 그대로 믿지 않고 직접 재현했다:

```
POST /api/d1/mutate {op:'insert', table:'staff_evaluations', values:[{id, staff_id, company_name}]}
→ 500  {"error":"Failed query: INSERT INTO \"staff_evaluations\" (\"id\", \"staff_id\") VALUES (?, ?)"}
```

운영 DDL 확인 결과 `category TEXT NOT NULL` · `content TEXT NOT NULL` 이고 픽스처가 그 둘을 안 채운다. 게이트웨이가 스키마에 없는 `company_name` 을 버린 뒤 NOT NULL 위반으로 실패한 것이다. **접근 통제 판정 자체는 396건 전부 기대와 일치한다.**

> 부수 확인: 운영 `staff_evaluations` 에는 저장소 마이그레이션에 없는 `CHECK (score BETWEEN 1 AND 5)` 가 붙어 있다 — 스키마 드리프트(S2)의 또 다른 증거다.

**이 게이트의 의미**: 9차 FB1·FB4 가 넣은 가드(`approvalsInsertGuard`·`boardPostsOwnerGuard`·`approvalsUpdateGuard` 관리자 예외)가 **정상 사용자를 막지 않는다**는 것이 런타임으로 증명됐다. 8차 수정이 만든 회귀 3건과 같은 유형은 이번에 없다.

## 5. 운영 D1 실측 — 9차 미확정 축 정리

전부 **SELECT 전용**으로 조회했다.

### 5-1. `leave_ledger` ↔ `leave_balances` 정합 — **정합으로 확정**

9차가 "미확정"으로 남긴 축이다. 단순 합산으로 비교하면 전원이 11~31일씩 어긋나 보이지만, **비교의 형태가 틀린 것이지 데이터가 틀린 게 아니다.**

```
백정민 원장 전문:
  auto_annual  annual:1   +15   2024-11-01
  auto_annual  annual:2   +15   2025-11-01
  use          request:…   -8   2026-07-29
  use          request:…   -2   2026-07-31
  expire       expire:…    -5   2026-07-31
  manual_*                 +9   2026-08-19 (엑셀 재동기화)
  auto_annual  annual:3   +16   2026-11-01   ← 미래 발생분
  ────────────────────────────────────────
  원장 합계 40  ≠  미러 remaining_days 9
  9 = 현재 주기(annual:2) 분만: 15 -8 -2 -5 +9
```

**원장은 생애 전체, 미러는 현재 주기다.** 구조가 그렇게 설계돼 있다. 정합 문제 없음.

- `leave_ledger` 500행 / 46명 / 중복 0건
- 유니크 인덱스 `idx_leave_ledger_staff_type_period (staff_id, entry_type, period_key)` **존재**
- 운영 인덱스 총 411개 — 과거의 "복원 시 인덱스 소실" 사고는 재발하지 않았다
- 미래 발생분은 8건 / 순 +9.5일로 소규모

> 단, **소비하는 화면 2곳이 주기 필터 없이 원장 전 이력을 합산**해 잔여를 과다 표시한다(모바일 연차관리자·PC 연차소멸알림, 재직 25명 최대 31일 과다). 이건 원장의 문제가 아니라 조회부의 문제다 — `LV-02`.

### 5-4. CHECK 제약 vs UI 값

운영 CHECK 제약 전량을 열거해 UI 가 보내는 값과 대조했다. 어긋난 것:

| 테이블·컬럼 | 운영 CHECK | UI 가 보내는 값 |
|---|---|---|
| `companies.type` | `('MSO','HOSPITAL','CLINIC')` | `의료법인·주식회사·사단법인·개인사업자·지점·진료·경영지원` — **전부 위반** |

기존 3행은 `HOSPITAL`·`MSO`·`HOSPITAL` 로 정상이다. 즉 **지금 화면으로 만든 회사는 하나도 없다** — 만들 때마다 CHECK 위반으로 실패하고 `catch` 가 로컬 상태에만 추가한다.

나머지 CHECK(`todos.priority`·`payroll.status`·`org_teams.division`·`staff_trainings.status` 등)는 UI 기본값이 허용 집합 안에 있어 문제 없다.
