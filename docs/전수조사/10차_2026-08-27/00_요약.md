## 1. 왜 10차인가

9차 전수조사가 **오늘 새벽 03:00** 에 끝났고, 그 수정(FB1~FB8)이 **오늘 오전 내내** 커밋으로 들어왔다. 즉 9차가 조사한 리비전(`ebf295b5`)과 지금 돌고 있는 코드는 **8커밋·40여 파일** 차이가 난다. 그리고 이 저장소의 이력이 반복해서 보여 준 것은 하나다 — **수정이 새 결함을 만든다.** 8차 수정이 회귀 3건을 만들었고 9차가 그것을 찾았다. 9차 수정은 아직 아무도 검증하지 않았다.

그래서 이번 조사는 세 갈래로 갔다:

1. **직전 수정이 새로 깨뜨린 것** (9차 FB1~FB6 커밋 + 미커밋 게이트웨이 변경)
2. **9차가 확정하지 못하고 남긴 15건**을 운영 데이터로 확정/반증
3. **9차가 하지 않은 전 기능 도메인 신규 전수 스캔** — 9차는 델타 감사였지 전면 감사가 아니었다

조사 **도중에** FB7·FB8 커밋 3건(18파일, 읽기·쓰기 게이트웨이와 크론 배선 포함)이 추가로 들어왔다. 움직이는 대상이라 **그 3건을 위한 4번째 감사를 따로 붙였다.**

### A · 퇴사자가 그냥 다시 들어온다

`app/api/auth/master-login/route.ts:99-110` 의 사번 조회에 **재직 필터가 없다.** 재직 판정 헬퍼(`isActiveStaffForLogin`)는 동명이인 분기에서만 쓰이고, `:248` 은 이름 경로에서도 퇴사자를 통과시킨다. 비밀번호 검증부터 세션 발급까지 재직 확인이 **한 번도** 없다.

`force_logout_at` 은 `forceLogoutTime > payload.iat` 비교라 **새로 로그인하면 항상 통과**한다 — 설계상 "기존 세션 무효화"이지 재로그인 차단이 아니다. 오프보딩은 `role='inactive'` 로만 바꾸는데 저장소 어디에도 그 값을 막는 인가 분기가 없고, `permissions` 는 그대로 남는다. **들어오면 재직 시절과 권한이 동일하다.**

```
운영 실측: 퇴사 18명 중 비밀번호 보유 15명
           그중 3명은 관리자가 강제 로그아웃을 찍은 뒤 last_seen_at 이 갱신됐다
             반민정(사번61) force 2026-06-15 → seen 2026-07-15
             윤연이(29)     force 2026-06-15 → seen 2026-06-25
             유채림(67)     force 2026-05-20 → seen 2026-06-13
           추가 5명은 force_logout_at 이 아예 NULL (인사발령 경로가 세션 회수를 안 한다)
```

`last_seen_at` 을 쓰는 경로는 세션이 필요한 두 곳뿐이다. **강제 로그아웃 이후의 갱신은 새 세션이 발급됐다는 뜻 외에 설명이 없다.** 다만 로그인 감사 로그가 없어 본인 확인은 불가하다 — 재로그인이 *가능하다*는 코드 사실은 데이터와 무관하게 확정이다.

채팅·게시판에 환자명과 차트번호가 오간다.

### B · 9차가 막은 문의 반대쪽이 열려 있다

9차 FB1 은 `approvals` **insert** 에 컬럼 가드를 걸었다. **update 는 그대로다.**

```ts
// lib/db/auth/policies.ts:308
const APPROVAL_TRANSITION_COLUMNS = ['status','sender_id','company_id','doc_number'];
// :305 주석 — "current_approver_id·approver_line·meta_data 는 여기서 막지 않는다 — 별건이다"
```

`APPROVAL_SCOPE`(`:1887`)는 `sender === me` 면 즉시 true 이고 **status 조건이 없다.** 그래서 이미 승인된 자기 기안 문서를 계속 수정할 수 있다.

```

                        meta_data:{ targetStaffId:본인, newSalary:임의 } }   ← 어떤 가드에도 안 걸린다
② process-final → status 는 이미 '승인', canAccess 는 ①이 덮어쓴 current_approver_id 를 본다
                  멱등 마커도 meta_data 안에 있어 ①이 지웠다 → 재집행된다
③ staff_members.base_salary 를 그 값으로 UPDATE
```

검증자가 저장소를 고치지 않고 `canAccess` 를 직접 호출해 확인했다 — `set:{status}` 는 **false**, `set:{type,current_approver_id,meta_data}` 는 **true**. 운영 실측으로 이 조건(자기 기안 승인문서 보유)을 갖춘 재직 비관리자가 **30명**이다.

> 원 finding 은 "결재선에 이름만 올라도 가능"이라고 했으나 검증자가 그 부분을 무너뜨렸다 — `APPROVAL_SCOPE` 는 `approver_line` 이 아니라 `current_approver_id` 만 보고, 승인 449건의 그 값은 5명뿐이며 전원 관리자다. **공격면은 30명으로 정정한다.**

### S4 · 세션 수명이 관리되지 않는다

- 퇴사해도 로그인된다 (P0 A)
- **비밀번호를 바꿔도 기존 세션이 안 죽는다** — 분실한 폰·공용 PC 가 계속 살아 있다. 세션은 30일이고 30분마다 스스로 재연장해 실질 만료가 없다 (`AUTH-02`)
- 관리자가 초기화한 계정은 **먼저 로그인하는 사람이 가져간다** — 지금 재직자 1명이 그 상태다 (`AUTH-03`)

### S5 · 하드코딩된 limit 과 화이트리스트가 실제 데이터와 어긋난다

- 재고 목록이 품목 1,032건 중 500/800/200 건만 (`INV-01`)
- 모바일 결재함 최신 200건 — 그보다 오래된 대기 문서 41건이 모바일에서 안 보임 (PC 는 전체) (`EA-02`)
- 모바일 공유캘린더 게시판 일정 `limit(100)` — 월말 한 주가 통째로 빔 (`M04`)
- 운영 발주 31건이 **전부** `status='draft'` 인데 UI 는 그 값을 어느 분기에도 안 넣는다 → 발주 확인·입고 버튼이 아예 안 뜸 (`INV-02`)
- 증명서 자동발급이 **존재하지 않는 type `'양식요청'`** 을 검사한다 (`EA-04`)

### S6 · 개인정보가 동의·비식별 없이 국외로 나간다

`D10-DS-03` (P1) — 수술상담 녹음과 퇴원심사 환자정보가 Google Gemini 로 전송되는데, **프롬프트가 주민번호를 그대로 포함하라고 명시적으로 지시**한다. 삭제 요청도 `waitUntil` 없이 fire-and-forget 이라 "즉시 제거" 주석과 달리 실제로는 삭제되지 않는다(`D10-DS-04`). 개인정보보호법 판단이 필요한 사안이라 기술 결함과 분리해 둔다.

## 7. 이 조사가 확인하지 못한 것

정직하게 남긴다.

- **모바일 E2E 미실행.** 46스펙이 스킵됐고, 확정 결함의 상당수가 모바일이다. 브라우저 설치(`test:e2e:install`)가 필요하다.
- **P0 A·B 의 실제 실행 미실시.** 운영 시스템이라 공격을 재현하지 않았다. 대신 A 는 운영 데이터 정황(강제 로그아웃 이후 `last_seen_at` 갱신 3건), B 는 `canAccess` 런타임 직접 호출로 확인했다. 스테이징이 없어 end-to-end 재현은 못 했다.
- **로그인 감사 로그가 없어** 퇴사자가 실제로 재로그인했는지 본인 확인이 불가하다.
- **PLAUSIBLE 24건은 확정 못 했다.** 고치기 전에 확인이 먼저다.
- **조사 중 코드가 움직였다.** 1·2단계는 `db16022a` 기준으로 시작했고 그 뒤 `4bbbc984`·`07f599e8`·`d81a056d` 가 들어와 3단계를 따로 붙였다. 1·2단계 결과 중 그 3커밋이 이미 고친 것이 섞여 있을 수 있다 — 수정 착수 전 해당 파일의 현재 상태를 다시 확인할 것.
