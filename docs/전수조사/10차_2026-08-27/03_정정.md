# 10차 전수조사 — 정정

> 작성: 2026-08-27 (수정 단계에서 발견) · 대상: [`00_요약.md`](00_요약.md) §5 S2 · [`01_확정결함.md`](01_확정결함.md) 스키마 드리프트 계열
> **이 문서가 앞선 서술을 덮어쓴다.** 결함 자체는 실재하지만 **인과와 증상 서술이 틀렸다.**

---

## 1. 무엇이 틀렸나

00_요약.md §5 S2 와 01_확정결함.md 의 스키마 드리프트 항목들은 이렇게 적었다:

> "코드가 운영에 없는 컬럼을 select 하면 쿼리가 SQLITE_ERROR 로 죽고, 호출부가 error 를 삼켜 **화면이 통째로 빈다**"

**이 인과는 성립하지 않는다.** 수정 단계에서 한 조사관이 반증했고, 운영 D1 에 직접 던져 확인했다.

### 근거 — 운영 D1 실측 (2026-08-27)

```sql
SELECT "id", "company_id", "company_name" FROM work_shifts LIMIT 1
```
```json
[{"id":"0101aa6d-…","\"company_id\"":"company_id","company_name":"박철홍정형외과"}]
```

**에러가 나지 않는다.** `"company_id"` 라는 **문자열 리터럴**이 그 이름의 키로 돌아온다.

```sql
SELECT "id", "duty", "rank" FROM staff_members LIMIT 1
→ {"id":"011d7d79-…", "\"duty\"":"duty", "\"rank\"":"rank"}

SELECT "id", "name", "unit" FROM inventory LIMIT 1
→ {"id":"00192b56-…", "name":"ANTEROLATERAL FIBULA PLATE…", "\"unit\"":"unit"}
```

원인은 SQLite 의 **double-quoted string 관용 동작**이다. 큰따옴표 안의 이름이 컬럼으로 해석되지 않으면 SQLite 는 오류를 내는 대신 **문자열 리터럴로 강등**한다. Drizzle 의 SQLite dialect 는 식별자를 큰따옴표로 감싸므로(`escapeName`), 게이트웨이를 통과한 모든 select 가 이 동작을 탄다.

> 이 관용 동작은 이 저장소가 이미 알고 있던 것이다 — `lib/staff-query-columns.ts` 의 8차 FB4 주석이 같은 현상을 기록해 두었다. 10차 감사가 그 기록을 놓쳤다.
>
> 감사 당시 재현에 쓴 명령은 따옴표 없는 `SELECT id, company_id FROM work_shifts` 였다. 그건 실제로 SQLITE_ERROR 를 낸다. **재현 방식이 실제 코드 경로와 달랐다.**

## 2. 무엇이 여전히 맞나

드리프트 자체와 **읽기/쓰기의 피해는 서로 다르다.** 셋으로 갈라 정리한다.

### (A) 없는 **테이블** — 확정 유지, 정정 없음

`no such table` 은 관용 동작이 없다. 진짜 에러다.

`op_consultations` · `generated_contracts` · `early_leave_records` · `message_templates` · `external_integrations` 등 — **저장이 100% 실패한다**는 서술 그대로다. 마이그레이션 `0027` 이 이것을 다룬다.

### (B) 없는 **컬럼에 쓰기(INSERT/UPDATE)** — 확정 유지, 다만 기전 정정

실패하는 것은 맞다. 다만 기전이 SQLITE_ERROR 가 아니라 **게이트웨이의 조용한 컬럼 폐기**다 — `app/api/d1/mutate/route.ts` 가 허용 컬럼을 Drizzle 스키마에서 뽑기 때문에, 스키마에 없는 컬럼은 D1 에 도달하기 전에 버려진다.

- `attendance.current_status` UPDATE → **SET 절이 통째로 비어** 아무 일도 일어나지 않는다 (D10-Z-02, 확정)
- `approval_form_types.base_slug` INSERT → 스키마에는 있고 운영에만 없어 D1 까지 내려가 거부된다. 운영 0행이라는 실측이 이를 뒷받침한다 (확정)

### (C) 없는 **컬럼을 읽기(SELECT)** — **정정 대상**

쿼리는 성공한다. 그 컬럼 값만 쓰레기 문자열로 오고, 코드는 `undefined` 를 본다.

**따라서 "화면이 통째로 빈다"는 이 원인으로 설명되지 않는다.** 아래 세 건의 증상 서술을 철회한다:

| id | 철회하는 서술 | 실제 |
|---|---|---|
| `SD-A01`·`M02` | "두 쿼리가 모두 500 → 전 직원이 항상 미출근, KPI 항상 0" | 쿼리는 성공한다. `location` 값만 못 얻는다. 게다가 **`attendances.current_status` 는 운영에 실재한다** — 1차 조사관의 "없다"가 틀렸다. 없는 것은 `location` 과 `attendance.current_status` 뿐이다 |
| `D10-Z-01` | "`work_shifts.company_id` 미존재 → 월별 근태 목록이 전 직원 공백" | 쿼리는 성공한다. **월별 목록이 실제로 비어 있다면 원인이 따로 있다 — 재조사 필요** |
| `SD-A03` | "`unit` 컬럼 때문에 품목 1,032건이 하나도 안 나온다" | 쿼리는 성공한다. 검색이 안 되는 원인은 `unit` 이 아니라 **`.limit(300)`** 쪽이다 |

## 3. 심각도 재판정

| 계열 | 원래 | 정정 후 |
|---|---|---|
| 없는 테이블 (A) | P1~P2 | **유지** |
| 없는 컬럼 쓰기 (B) | P1 | **유지** |
| 없는 컬럼 읽기 (C) | P1 | **P2 로 하향** — 값이 안 오는 위생 결함이지 화면을 죽이지 않는다 |

00_요약.md §5 S2 표의 9종 중 `attendances.location` · `work_shifts.company_id` · `inventory.unit` 행은 (C) 로 재분류한다.

---

## 4. 이 정정이 남기는 숙제

1. **마이페이지 출퇴근기록의 월별 목록이 실제로 비는지 재확인해야 한다.** 비어 있다면 원인은 아직 모른다.
2. **모바일 근무현황이 실제로 "전 직원 미출근"인지 재확인해야 한다.** `attendances.current_status` 가 실재하므로, 비어 있다면 다른 원인이다.
3. `.limit(300)`·`.limit(200)` 같은 상한이 실제 절단 원인이므로 그쪽이 본체다(수정 반영됨).

## 5. 부수 발견 — 같은 함정을 밟은 select 가 더 있을 수 있다

수정 중 확인된 별개 함정이다.

`SAME_COMPANY_TEAM_VISIBLE` 정책 테이블(`attendance`·`attendances`·`leave_requests` 등)을 select 할 때 **컬럼 목록에서 `staff_id` 를 빼면, 게이트웨이가 본인 행까지 통째로 버린다**:

```ts
// lib/db/auth/policies.ts — filterTeamVisibleRows
if (rowStaff === null) continue;   // staff_id 가 없으면 그 행은 사라진다
```

에러도 토스트도 없이 **빈 배열**이 된다. 이것이야말로 "화면이 조용히 빈다"의 진짜 기전이며, 위 (C) 로 오귀속된 증상 중 일부가 실제로는 이쪽일 수 있다.

같은 구조가 `filterMessagesByChatRoomMembership` 에도 있었고(그쪽은 `room_id`), **그것이 이번 P0 D 의 원인이었다.** 즉 이 패턴은 이미 한 번 P0 을 만들었다.

> **다음 조사에서 이 축을 전수로 훑을 것**: 정책이 행 필터를 거는 테이블마다, 그 판정에 쓰이는 키 컬럼(`staff_id`·`room_id`·`company_id`)이 **모든 select 컬럼 목록에 포함돼 있는지.**
