## 1. 한 줄 결론

1. **권한 체계가 구조적으로 무효다.** `/api/d1/mutate` 는 정책을 *합성한 가상 행*에 대해 검사하면서 SQL 은 *클라이언트가 보낸 WHERE* 를 그대로 실행한다. 이 한 가지로 결재 문서 탈취·기본급 변경·채팅방 침투·재고 수량 조작이 전부 성립한다.
2. **같은 권한 파일이 한쪽은 과잉 차단, 한쪽은 전면 개방.** `policies.ts` 가 85개 테이블을 관리자 전용으로 강등해 **일반 직원 화면이 에러 없이 백지**가 되는 동시에, 게시판·계약서양식·징계기록은 `PUBLIC_ALL` 이라 아무나 수정·삭제할 수 있다.
3. **알림은 "인앱에는 뜨는데 단말에는 안 온다".** 푸시 팬아웃 단일 지점을 거치는 경로가 3곳뿐이고, 클라이언트에서 알림 row 를 만드는 20여 곳은 전부 푸시가 나가지 않는다. 채팅은 큐 회수 계층이 **구조적으로 100% 무동작**이다.
4. **DB 에 없는 컬럼·테이블을 읽는 화면들이 조용히 죽어 있다.** 급여 워크센터 13모듈 전부, 근태이상 감지, 계약 현황 KPI, 연차 원장 폴백 — 실제 D1 스키마 대조로 확정했다.
5. **관리자 화면 상당수가 실데이터가 아니라 장식이다.** 법인카드 사용액은 `charCodeAt` 시드로 생성되고 사용자명은 코드에 박힌 6명 명단이며, DR 훈련 이력·백업 정책·AI 분석은 하드코딩이다. 감사 로그는 클라이언트가 actor 를 정하고 admin 이 수정·삭제할 수 있어 **증거로서 무효**다.
6. **정적 게이트는 통과하지만 게이트가 아니다.** `tsc --noEmit` 은 에러 0이고 `app/`·`lib/` 린트 에러도 0인데, CI 에 타입체크·린트 잡이 없고 `npm run lint` 는 잡동사니 디렉터리 때문에 항상 실패한다. E2E 는 로컬 D1 이 비어 결과 해석이 제한적이다.

## 2. P0 — 근본 원인별 정리

같은 뿌리에서 나온 지적을 묶었다. **[직접확인]** 은 이번 통합 과정에서 감사관 보고와 별개로 코드/DB 를 직접 열어 재확인한 항목이다.

### R1. `/api/d1/mutate` — 정책 판정 대상과 실제 SQL 대상이 다름 **[직접확인]**

가장 심각. 앱 전체 쓰기 무결성이 무너진다.

- [`mutate/route.ts:585`](../../../app/api/d1/mutate/route.ts) 는 `where` 의 eq 필드 + 클라이언트 `set` 을 합성한 **가상 행**에 정책을 적용한다.
- [`:625`](../../../app/api/d1/mutate/route.ts) 의 실제 SQL 은 **클라이언트 WHERE 를 그대로** 실행한다.
- DB 정본 대조([`:239-241`](../../../app/api/d1/mutate/route.ts))는 `where` 에 `id eq` 가 있을 때만 작동하고, 그때조차 [`:252-256`](../../../app/api/d1/mutate/route.ts) 이 강제하는 필드는 `id`·`staff_id`·`company_id`·`sender_id`·`user_id` **다섯 개뿐**이다.
- [`d1-api-helpers.ts:66`](../../../lib/d1-api-helpers.ts) 이 `neq`·`gt`·`like` 를 허용한다.

## 4. 횡단 테마

### 4-1. 권한 정책 파일 1개가 양방향으로 틀렸다

`lib/db/auth/policies.ts` 는 2026-05~06 사이 "Default Deny" 하드닝(`:894` 주석)을 하면서 목록 이름(`ADDITIONAL_PUBLIC_TABLES`)과 정반대 정책을 부여했다. 결과적으로 **기능은 조용히 죽고**(R2), **정작 열려 있어야 할 자리는 그대로 `PUBLIC_ALL`**(R3)이다. 게다가 정책 판정 자체가 `/api/d1/mutate` 에서 가상 행 상대로 이뤄져(R1) 아무리 정책을 잘 써도 우회된다. **정책 표현·정책 적용·정책 대상 세 층이 모두 어긋나 있다.**

### 4-2. 실패가 사용자에게 보이지 않는다

이번 조사에서 가장 반복된 패턴이다.

- 권한 실패 → HTTP 200 + 빈 배열 (R2)
- 컬럼 부재 → catch 후 빈 배열 (R7)
- 저장 실패 → 성공 토스트 (A10-06, A10-12, A3-34)
- 첨부 유실 → 배너에도 안 뜸 (A13-01)
- 푸시 유실 → 인앱에는 있으니 정상처럼 보임 (R6)
- 감사 로그 미기록 → 빈 화면이 "이상 없음" 으로 읽힘 (A10-03)

**단일 수정으로 가장 큰 효과를 내는 지점**: 권한 거부를 빈 배열이 아니라 명시적 403 으로 바꾸면 R2 에 걸린 54개 테이블·289개 호출 지점의 고장이 즉시 드러난다.

### 4-3. PC ↔ 모바일 이중 구현

`page.tsx` 의 `isMobile` 분기가 트리를 통째로 교체하므로 도메인 로직이 두 벌이다. 이번에 확인된 실제 피해:

- 연차 잔여가 **PC(회계연도 로컬 계산)와 모바일(입사일 사이클 서버 SSOT)에서 다르게 표시**(A7-05)
- 수술상담이 PC 는 `localStorage`, 모바일은 `op_consultations` 테이블 — **데이터 전혀 미공유**(A3-06)
- 퇴사자 차단이 PC 에만 있어 **모바일에서 퇴사자가 출퇴근·할일·서류제출 전부 사용 가능**(A2-07)
- 비밀번호 재확인이 PC 에만 있어 모바일은 계좌번호 변경까지 무인증(A2-12)
- 업무공유 게시판을 PC 는 팀 워크스페이스, 모바일은 일반 리스트로 다뤄 **상호 작성 글이 깨져 보임**(A5 D절)
- 결재 상신 시 모바일은 **알림 자체가 0건**(A6)

| 08 | 재고 워크센터 (hidden 2 포함) | 6 | 0 |

부수 확인: `MAIN_MENUS` 는 10개가 맞고, **`SUB_MENUS.인사관리`(7개, `abnormal` 포함) ≠ `HR_TABS`(6개)** 불일치도 소스에서 실재를 확인했다.

### 6-2. 알림 도달 판정에 모순이 없는가 — **일치**

푸시 팬아웃 `dispatchPushForNotificationRows` / `dispatchNotificationPush` 의 호출자는 **정확히 3곳**이다.

- `app/api/admin/force-logout/route.ts:95`
- `lib/inapp-notification-jobs/types.ts:144`
- `lib/notification-utils.ts:427`

반면 클라이언트에서 `notifications` 에 insert 하는 지점은 **20개 파일 21곳**이다(전자결재·메신저·재고 불출·급여명세·계약관리·연차소멸·연차촉진·교육·자격면허·오프보딩·모바일 인사/결재 등). 이 둘의 차이가 01·02·03·06·07A·07B·08 문서가 각각 "푸시 미발송" 으로 판정한 집합과 정확히 대응한다. **문서 간 모순 없음.**

### 6-3. P0 직접 재확인

§2 에서 **[직접확인]** 으로 표시한 항목은 감사관 보고와 별개로 코드·실제 D1 스키마를 열어 재확인했다: R1(mutate 정책/SQL 불일치), R2(85개 강등 + 54개 실사용 산출), R4(무인증 라우트 104개 중 1건으로 범위 확정), R7(컬럼·테이블 부재 5건 `PRAGMA table_info` 대조), A4-41(채팅 큐 in-flight), A9-02(마감 회사 미검증), A11-01(data-reset 게이트), A12-02(오라클 대상 컬럼 실재), A13-05(assetlinks 부재).

이 과정에서 **최초 스캔의 오탐 1건을 정정**했다 — `/api/admin/audit/*` 6개 라우트를 "인증 없음" 으로 잡았으나 `guardSystemMaster`/`guardAuditAdmin` 로 정상 보호됨을 확인하고 무인증 라우트를 1건으로 좁혔다.

## 7. 이 조사의 한계

- **정적 분석 중심**이다. 개발 서버 브라우저 실조작은 하지 않았다(사용자 선택). 지적 중 `의심` 등급은 각 문서의 해당 표에 그대로 표시돼 있다.
- **E2E 결과를 코드 결함 근거로 쓰지 않았다.** 로컬 D1 공백으로 신뢰할 수 없기 때문이다. 예외는 실행 로그가 직접 노출한 2건(레이트리밋 fail-open, 강제 로그아웃 검사 실패 삼킴).
- **P0 중 [직접확인] 표시가 없는 항목은 담당 감사관의 보고를 그대로 실은 것**이다. 조치 착수 전 해당 `파일:라인` 을 한 번 더 열어볼 것을 권한다.
- 각 문서 말미의 **「미확인 항목」 절**에 시간·접근 제약으로 확인하지 못한 것이 정직하게 나열돼 있다.
- 6차(2026-07-15) 이전 감사의 지적이 해결됐는지는 **재검증하지 않았다**(사용자가 "신규 전수조사만" 선택). 따라서 이 문서의 지적 중 일부는 이전 문서에도 있을 수 있다.
- 조사 중 하위 조사 결과 하나가 **오류로 판명**되어 정정했다(재고 월마감 잠금이 무효라는 보고 → 실제로는 `lib/inventory-movement-service.ts:115-140` 이 정상 검사). 해소 과정은 [08](./08_재고관리.md) I절 참조.
