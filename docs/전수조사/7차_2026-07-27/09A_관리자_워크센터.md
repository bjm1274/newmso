# 09A. 관리자 — 워크센터(영문 경로) 전수조사 (7차, 2026-07-27)

## 요약

- 6개 워크센터 26개 내부 탭 중 **실동작 12 / 반쪽 8 / 껍데기 6**. 라우팅·권한 게이팅 자체는 정상 동작하나, 탭 내부로 들어가면 "저장은 되는데 아무도 읽지 않는 설정", "저장 실패를 초록 배지로 성공 표시", "DB에 없는 값을 해시 시드로 만들어 실데이터처럼 표시"가 반복된다.
- **가장 심각한 것은 법인카드 탭**이다. 사용액·한도·사용률·상태·실사용자명이 전부 `id` 문자 코드 기반 시드로 생성되며, 사용자명은 코드에 박힌 6명 명단에서 뽑힌다(`CompanyCardTab.tsx:50-66`). 금액 KPI 4개가 전부 이 가짜값의 합계다.
- **감사 로그는 내부자 감사 증거로서 효력이 없다.** 브라우저가 `audit_logs`에 직접 INSERT하고 행위자는 localStorage에서 읽으며(`lib/audit.ts:115-129,153-168`), admin은 update/delete가 열려 있고, 데이터 초기화가 감사 로그를 전량 삭제하면서 그 사실을 기록하지 않는다. 게다가 **`access_logs`에 기록하는 코드가 저장소에 단 한 줄도 없어** "접근 감사 로그" 탭은 영구 공백이다.
- 권한 상승: 완전한 시스템마스터 탈취는 `isNamedSystemMasterAccount`(9999) 가드로 차단되지만, `/api/admin/staff-permission`에 **자기 자신 대상 제한도, permissions 키 화이트리스트도 없어** admin이 스스로에게 `system_master: true`를 부여해 시스템마스터센터 UI에 진입할 수 있다. 또 "비밀번호 초기화"는 확인창·본인 통지 없이 임의 직원 계정 탈취 수단이 된다.
- 관리자 세부 권한(`admin_*`)만 부여받고 `role !== 'admin'`인 사용자는 6개 워크센터 UI가 전부 열리지만 서버 API·D1 정책이 전부 `isAdminSession`/`ADMIN_ONLY`를 요구해 **읽기조차 실패**한다. 세부 권한 체계가 사실상 무의미하다.
- PC 전용 가드(`isMobile` → `DesktopOnlyNotice`)는 **100% 도달 불가 죽은 코드**다. 768px 미만은 `page.tsx`가 이미 MobileShell로 분기하며, 모바일 관리자는 같은 워크센터 컴포넌트를 props 없이 렌더한다.

## C. 권한 상승 가능성 점검

### C-1. 서버 게이트 실태

`isAdminSession`(`lib/server-session.ts:444-452`)의 기준은 `is_system_master || role==='admin' || permissions.admin || permissions.mso || permissions.system_master`이다.

### C-2. 확인된 상승 경로

1. **admin → 시스템마스터센터 UI 진입 (P1, A10-20).**
   `/api/admin/staff-permission`에 자기 `staffId` + `{"permissions": {..., "system_master": true}}`를 POST하면 그대로 저장된다(키 필터 없음, 자기 대상 차단 없음). 이후 `hasSystemMasterPermission`(`lib/system-master.ts:7-9`)이 true가 되어 `관리자전용.tsx:145,157`의 게이트를 통과, 시스템마스터센터 사이드바가 노출된다. UI만으로도 "권한 빠른 복사"가 `system_master`/`admin`/`mso` 키를 제외하지 않으므로(`직원권한통합.tsx:20-81`은 사진·계좌·면허 등 개인정보 키만 제외) 소스 직원이 해당 키를 갖고 있다면 동일 결과가 된다.
   **완전 탈취는 차단됨**: `isPrivilegedUser` → `isNamedSystemMasterAccount`(`system-master.ts:11-32`)가 `system_master` 권한 **+ 식별자 '9999'**를 동시에 요구하므로, 9999가 아닌 계정은 `guardSystemMaster`(복구 API)와 `canAccessMainMenu`의 특권 우회를 통과하지 못한다.

2. **admin → 임의 직원 계정 탈취 (P1, A10-21).**
   권한 관리 화면의 "비밀번호 초기화"(확인창 없음) → `password_reset_required=1` → 로그인 화면에서 **아무 비밀번호나 입력하면 그것이 새 비밀번호로 설정되며 로그인 성공**(`master-login/route.ts:327-364`). 대상자에게 통지가 없고 원 비밀번호는 복구 불가. 대상 제한이 없어 다른 admin 계정에도 적용된다.
   다만 실제 시스템마스터 계정은 `staff_members` 행이 아니라 환경변수(`MASTER_ID`/`MASTER_PASSWORD_HASH`, `lib/admin-credentials.ts:13-18`) 기반이라 이 경로로는 탈취되지 않는다.

3. **admin → 무제한 admin 증식.**
   역할 드롭다운(`직원권한통합.tsx:608-619`)으로 누구든 `admin`으로 승격 가능하며 승인 절차·2인 확인이 없다. 서버는 role 값을 검증하지 않아 `'superadmin'` 같은 임의 문자열도 저장된다.

### C-3. 차단이 확인된 것

- 비-admin이 `staff_members.role/permissions`를 직접 UPDATE하는 경로: `staff_members` 정책이 write를 제한하고(`policies.ts:388-391`), 워크센터 UI는 반드시 `/api/admin/staff-permission`을 경유한다 — **SEC-1 가드 유효**.
- 비-admin의 `audit_logs` INSERT: `ADMIN_ONLY`로 차단(`policies.ts:949-961`).
- 자동 DB 복구: 시스템마스터 + 확인 토큰을 모두 통과해도 501로 거부(`audit/restore/route.ts:52-63`) — 안전 측 설계.

### C-4. 권한 변경 후 세션·캐시 무효화 (A10-19)

무효화 로직이 **없다**. 세션 JWT(수명 30일, `server-session.ts:15`)에 role/permissions가 박혀 있고, 갱신은 `app/main/page.tsx:651-657`의 30분 주기 폴링 또는 포그라운드 복귀 시 `/api/auth/session` 호출로만 일어난다(`auth/session/route.ts:36-48`이 DB 최신값으로 재발급). 즉 **권한 회수 후 최대 30분간 구권한이 서버 API에서 유효**하다. 즉시 무효화 수단은 같은 화면의 "기기 전체 강제 로그아웃"(`force_logout_at` + `isStaffForceLoggedOutInDb`, `server-session.ts:361-418`)뿐이며, 이는 관리자가 별도로 눌러야 한다. 이 강제 로그아웃 행위 자체는 감사 로그에 기록되지 않는다(A10-22).

### C-5. UI 권한과 서버 권한의 불일치 (A10-03 관련, 실질 P1)

`ADMIN_PERMISSION_ITEMS`(`lib/feature-permissions.ts:194-221`)는 워크센터별 세부 권한 14종을 제공하고 `canAccessAdminSection`이 이를 존중해 사이드바·워크센터 진입을 허용한다. 그러나 **서버는 세부 권한을 전혀 보지 않는다**:

- `admin_직원권한`만 가진 `role='staff'` 사용자 → `canAccessMainMenu(user,'관리자')` 통과(`access-control.ts:234` `menu_관리자` 별칭 확장) → `canAccessAdminSection(user,'roles')` 통과 → **권한 관리 화면이 전부 렌더**되지만, 토글을 누르면 `/api/admin/staff-permission`이 `isAdminSession` 실패로 403 → "권한 변경 중 오류가 발생했습니다."만 반복된다.
- 동일하게 `admin_감사센터`만 가진 사용자는 `/api/admin/audit/*`가 전부 403, `admin_회사관리`만 가진 사용자는 `company_payroll_policies`·`backup_restore_runs`·`approval_form_types` 등이 `ADMIN_ONLY`(`policies.ts:892-897`)라 **조회조차 실패**한다.

결론: 세부 권한 부여는 "메뉴는 보이지만 아무것도 못 하는" 상태를 만든다. 서버 게이트를 세부 권한 인지형으로 바꾸거나, 세부 권한 UI에서 "role=admin 필요"를 명시해야 한다.

### E-4. 무결성 (A10-02)

- **행위자 위조 가능(admin 한정).** `readClientAuditActor`(`lib/audit.ts:115-129`)가 `localStorage`의 user를 그대로 쓰고, `/api/d1/mutate`가 행 본문의 `user_id`/`user_name`/`created_at`을 세션 값으로 덮어쓰지 않는다. admin 세션이면 임의 actor·임의 시각의 행을 삽입할 수 있다.

- **비-admin 행위는 오히려 기록되지 않을 수 있다.** 매니저·일반 직원이 수행하는 클라이언트 `logAudit`(휴가 승인, 급여 확정, 직원정보 수정 등)은 ADMIN_ONLY 정책에 막혀 `console.warn`만 남기고 조용히 실패한다(`lib/audit.ts:165`). — 의심(실제 실행 주체의 역할 분포 확인 필요)
- **이중 기록 불일치.** 권한/비밀번호 변경은 서버·클라 양쪽이 각각 행을 남기며 액션명이 다르다(A10-31).

## I. 미확인 항목

1. **`popups` 실제 소비자** — 앱 내 소비처는 0건이며 미리보기 iframe이 `www.pchos.kr`을 가리킨다. 외부 병원 홈페이지가 `popups`를 읽는지는 이 저장소에서 검증 불가. (A10-17)
2. **`MASTER_ID` 환경변수 값** — `isNamedSystemMasterAccount`는 식별자 `'9999'`를 요구하는데(`lib/system-master.ts:1`) 환경변수 마스터 로그인은 `employee_no: '0'`, `login_id: <MASTER_ID>`로 세션을 만든다(`master-login/route.ts:279-296,300-317`). `MASTER_ID`가 `'9999'`가 아니면 **실제 시스템마스터조차 `guardSystemMaster`(복구 API)와 `isPrivilegedUser` 우회를 통과하지 못한다**. `lib/d1-api-helpers.ts:12`가 `login_id === '9999'`를 확인하는 것으로 보아 '9999'로 운영 중일 가능성이 높으나 배포 환경 확인 필요.
3. **`staff_members`에 `permissions.system_master`를 가진 행의 존재 여부** — 코드상 이 키를 staff 행에 저장하는 경로는 없으나(환경변수 로그인만 부여), 과거 수동 삽입 데이터가 있으면 "권한 빠른 복사"를 통한 상승이 UI만으로 성립한다. D1 실데이터 확인 필요. (A10-20)
4. **비-admin 역할이 실제로 수행하는 클라이언트 `logAudit` 실패율** — ADMIN_ONLY 정책상 조용히 실패할 것으로 보이나, 매니저 계정이 `permissions.admin`을 갖는 운영 관행이 있으면 문제가 되지 않는다. 운영 데이터 확인 필요. (E-4)
