## 요약

메시지 전송의 **서버측 권한 골격은 견고**하다 (`messagesInsertGuard`가 sender_id 위조와 비멤버 전송을 모두 차단). 그러나 **`chatRoomsInsertGuard`가 "이미 존재하는 방 id"를 검사하지 않는데 `/api/d1/mutate`의 insert가 UPSERT(`ON CONFLICT DO UPDATE` / `INSERT OR REPLACE`)를 허용**하므로, 일반 직원 세션만으로 임의 채팅방의 `members`·`created_by`를 덮어써 방에 침투 → 전체 대화 이력 열람·전송·기존 멤버 강퇴까지 가능하다. 실 익스플로잇 체인이 성립하는 **P0**이다.

알림 경로는 큐(`chat_push_jobs`)·재시도·dead-letter·조용시간이 잘 설계되어 있으나 **큐 소진 경로 전체가 무동작**이다. `processPendingChatPushJobs`가 dispatch 호출 직전에 `processing_started_at`을 기록하는데 dispatch 진입부가 그 값을 보고 "다른 워커가 처리 중"으로 판단해 즉시 반환하므로, 5분 cron·flush·관리자 수동 드레인이 **전부 0건 발송**이고 잡은 `attempt_count`만 무한 증가한다. 즉시 디스패치가 놓친 메시지의 푸시는 영구 유실된다 (**P0**). 또한 **멘션 토큰 포맷이 송신측(`@홍길동` 평문)과 수신측(`@[名](staff:id)` 정규식)에서 서로 달라 멘션 기능 전체가 무동작**이고, 방 뮤트 토글은 D1의 정수 `0`을 `!== false`로 비교해 **항상 "알림 켜짐"으로 표시**된다.

첨부는 `NEXT_PUBLIC_R2_PUBLIC_BASE_URL=https://r2.pchos.kr`로 **공개 도메인 URL을 그대로 `messages.file_url`에 저장**하므로 멤버십 게이트가 사실상 없고, 프록시 라우트의 ACL은 객체 키 포맷(`chat/<ts>_<uuid>.<ext>`)과 어긋나 정상 멤버에게도 403을 내는 죽은 검사다. 메시지 삭제·보관정리 어느 쪽도 R2 객체를 지우지 않아 고아 객체가 영구 누적된다.

PC↔모바일은 전송 진입점이 8곳으로 갈라져 있고, 모바일에는 재시도 큐·전송상태·공지방 쓰기 가드·타이핑·멘션·예약공지가 전부 없다. 모바일은 5초 폴링이 메시지 배열을 통째로 교체해 낙관적 버블·페이지네이션·검색 점프를 파괴한다.

예약공지·알림모드/키워드 필터·강퇴투표·멘션인박스·사이드바 스레드인박스는 UI만 있고 실제로는 동작하지 않는다.

### A4-01 상세 (P0 — 방 침투)

`chatRoomsInsertGuard`(`lib/db/auth/policies.ts:307-319`)는 `_db` 인자를 **사용하지 않는다**. 즉 `row.id`에 해당하는 방이 이미 존재하는지 전혀 확인하지 않고, 요청 본문의 `created_by`·`members`만 보고 통과시킨다.

```ts
async function chatRoomsInsertGuard(
  _db: D1Client,                                   // ← DB 조회 없음
  claims: ErpClaims, row: Record<string, unknown>,
): Promise<boolean> {
  if (erpIsAdmin(claims)) return true;
  const me = claimsStaffIdRaw(claims);
  if (me === null) return false;
  if (isNoticeRoomType(getField<string>(row, 'type'))) return false;
  const createdBy = getField<string>(row, 'created_by');
  if (createdBy !== null && String(createdBy).trim() !== me) return false;
  return isRoomMember(parseMembersField(row.members), me);   // ← 공격자가 보낸 배열
}
```

그런데 `/api/d1/mutate`의 insert는 UPSERT를 지원한다 (`app/api/d1/mutate/route.ts:462-468`의 `ON CONFLICT(...) DO UPDATE SET`, `:471-473`의 `INSERT OR REPLACE`). `chat_rooms.id`는 PK(`lib/db/schema.ts:356`)라 충돌 대상이 된다. `updateCols`는 conflict 컬럼과 `id`만 제외하므로 **`members`와 `created_by`가 그대로 덮어써진다**.

재현(일반 직원 세션 쿠키만 필요):

1. `POST /api/d1/query` → `{"table":"room_read_cursors","columns":["room_id","user_id"],"limit":1000}` — `select:'PUBLIC'`(`policies.ts:462-469`)이라 전사 방 id·참여자 덤프 (A4-22).
2. `POST /api/d1/mutate` → `{"op":"insert","table":"chat_rooms","values":[{"id":"<R>","name":"...","type":"group","created_by":"<나>","members":["<기존 멤버들>","<나>"]}],"conflict":{"columns":["id"],"action":"update"}}` — 가드 통과, 방 멤버·소유자 교체.
3. `POST /api/d1/query` → `{"table":"messages","where":[{"field":"room_id","op":"eq","value":"<R>"}],"limit":1000}` — 이제 정상 멤버로 판정(`policies.ts:1197-1222`)되어 **본문·file_url 전부 반환**.
4. `messagesInsertGuard`(`policies.ts:283-304`)도 통과 → 해당 방에 메시지 전송 가능.
5. `created_by`까지 뺏었으므로 `canChangeChatRoomMembers`(`lib/chat-room-membership.ts:146-150`)상 **원 멤버 전원 강퇴** 가능.
6. 3에서 얻은 `file_url`을 `GET /api/download?url=...`로 다운로드 (멤버십 검사 없음, A4-17).

전용 라우트 `POST /api/chat-rooms`는 같은 동작에 대해 기존 방 소유자 검사를 한다(`app/api/chat-rooms/route.ts:146-148`). 즉 **가드된 라우트와 가드되지 않은 제네릭 라우트가 공존**하는 구조적 문제다.

**수정**: ① `chatRoomsInsertGuard`가 `loadChatRoomMembership(db, row.id)`로 기존 방 존재를 확인하고 존재 시 `chatRoomsUpdateGuard`와 동일 규칙 적용(또는 거부). ② `/api/d1/mutate`에서 `chat_rooms`·`messages`에 대한 `conflict`/`onConflict` 자체를 거부하거나 upsert를 `update` 정책으로 평가.
