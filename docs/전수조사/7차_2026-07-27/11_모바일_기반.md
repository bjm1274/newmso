# 11. 모바일 기반 전수조사 (7차, 2026-07-27)

감사관 A13 — 모바일 전용 기반(셸·바텀탭·공통 킷·오프라인·PWA/TWA/Electron·횡단 문제).
각 주메뉴 화면 내용은 담당 감사관 보고서 참조. 본 보고서는 **기반·횡단**만 다룬다.
근거 등급: `확인` = 코드에서 직접 확인, `의심` = 코드상 개연성 높으나 런타임 재현 미실시.

---

## 요약 (6줄)

1. **오프라인 첨부 유실이 무통지로 발생한다.** `offline-upload-queue`의 `status:'failed'` 항목은 큐 카운트에서 제외되고(`getUploadQueueSize`), 실패 배너(`오프라인실패배너`)는 D1 mutation 큐만 구독하므로 재시도·삭제 UI가 아예 없다. 사용자는 첨부가 사라진 사실조차 모른다. (A13-01, P0)
2. **`subscribeUploadQueue`의 리스너가 단 한 번도 호출되지 않는다.** `uploadListeners` set에 add만 있고 emit이 없다 → 오프라인배너의 "N개 첨부" 카운트는 마운트 시점 값에서 영원히 멈춘다. (A13-02, P1)
3. **채팅방에서 알림 딥링크로 다른 탭으로 이동하면 바텀탭이 영구히 사라진다.** `activeRoomId`가 채팅 언마운트 시 null로 리셋되지 않아 `{!activeRoomId && <MobileBottomTab/>}`가 계속 false. 새로고침 전까지 네비게이션 불가. (A13-03, P1)
4. **안드로이드 하드웨어 back이 앱을 종료시킨다.** MSheet(17개 화면 사용)와 셸의 탭/서브 라우팅 어디에도 history 연동이 없다. `useSheetHistory`는 존재하지만 2곳만 쓴다. TWA 배포 기준 치명적. (A13-04, P1)
5. **TWA는 현재 상태로 설치해도 "신뢰된" 앱으로 뜨지 않는다.** `public/.well-known/assetlinks.json`이 저장소에 없고, `strings.xml`의 `asset_statements`는 `"`를 이스케이프하지 않아 Android 문자열 리소스 파싱 시 따옴표가 제거된다. `POST_NOTIFICATIONS` 권한도 누락(targetSdk 35). (A13-05/06/07, P1)
6. **Electron 권한 게이트가 `origin.includes('pchos.kr')` 부분문자열 비교이고 `will-navigate` 잠금이 없다.** `https://pchos.kr.evil.com` 류 오리진에 카메라·마이크·알림이 그대로 허용된다. (A13-08, P1)

기타: 데스크톱 브라우저 창을 768px 미만으로 줄이면 전체 트리가 교체되어 입력 중인 폼·모달·스크롤이 전부 소실된다(A13-09). 재무회계는 PC 사이드바가 스스로 "(PC 전용)"이라 라벨하므로 의도된 제약, 공유캘린더는 모바일에서 **추가기능 탭 권한에 종속**되어 접근 결손이 발생한다(A13-12).

## E. 오프라인·캐시·재시도 분석

**Q3 (오프라인 동작)**
- 배너: `오프라인배너.tsx`는 `useOnlineStatus`(navigator.onLine) + D1 큐 + 업로드 큐 카운트를 표시한다. D1 큐 부분은 `OfflineQueue.subscribe`가 즉시 + 변경마다 emit 하므로 정상 동작. **업로드 큐 부분은 A13-02로 인해 갱신되지 않는다.**
- 실패 큐: `오프라인실패배너.tsx`는 D1 mutation 영구 실패만 다룬다. 재시도(`retryFailed`)·삭제(`dismissFailed`)·전체 재시도까지 잘 구현되어 있으나 **업로드 실패는 커버하지 않는다(A13-01).**
- PTR: 3개 화면(`게시판목록`, `근태이상`, `채팅목록`)만 적용. 내정보 홈·결재함·재고 현황·관리자 허브는 PTR 없음. 오프라인 상태에서 PTR을 당기면 `onRefresh`가 조용히 실패하고 인디케이터만 복원(`usePullToRefresh.ts:68-69` 무음 catch) — 사용자는 갱신 실패를 알 수 없다.
- **유실**: A13-01(첨부 영구 실패 무통지) → **P0**.
- **중복**: A13-13(D1 replay 멱등성 부재), A13-14(업로드 후속 mutation 실패 시 R2 PUT + insert 전체 재실행) → **P1 둘 다**.
- 이중 flush 방지는 잘 되어 있다 — `MobileShell.tsx:358-359` 주석대로 D1 큐 flush는 `PwaBootstrap`에만 등록하고 셸은 업로드 큐만 초기화한다.
- 다만 `initUploadQueueFlush()`는 **`MobileShell.tsx:362-365`에서만 호출**된다. 데스크톱 분기(`page.tsx:1291~`)에는 없다. 현재 `enqueueUpload` 호출처가 모바일 3파일(`게시판/글작성.tsx`, `결재/AttachmentPicker.tsx`, `채팅/업로드.ts`)뿐이라 실피해는 없으나, 데스크톱에서 업로드 큐를 쓰는 순간 flush가 영영 안 도는 구조적 함정이다. (P3 · 확인)

**Q4 (서비스워커 캐시 전략)**
- 전략: 정적 확장자(`js|css|woff2?|ttf|png|jpg|svg|ico|webp`) 동일 오리진 GET에 대해 stale-while-revalidate이되 실제로는 `cached || fetchPromise` = **캐시 우선**(`sw.js:54-64`). HTML 문서는 캐시하지 않는다.
- **구버전 JS가 뜨는가**: Next.js 청크는 파일명에 해시가 박히고 HTML은 항상 네트워크에서 오므로 **구버전 번들이 뜨지는 않는다.** 다만 `sw.js:1`의 `SW_VERSION` 주석과 `STATIC_CACHE = 'erp-static-v1'`(:43)은 배포마다 바뀌지 않고, `activate`(:161-176)의 `CURRENT_CACHES`에 항상 포함되어 **무효화 경로가 사실상 없다** → 캐시 무한 증식(A13-21).
- `install`에서 precache가 없고 navigation fallback도 없어 **콜드 스타트 오프라인은 지원되지 않는다**(A13-22).
- `/share-target`: `sw.js:46-52`의 if/else-if/else 구조는 읽기 어렵지만 동작은 맞다 — POST /share-target이면 빈 if 블록을 통과해 :70 이후 로직으로 흐른다. 파일을 `erp-share-target-v1` 캐시에 저장 후 클라이언트에 `postMessage` + `/main?open_menu=채팅&share_id=...`로 303 리다이렉트. **그러나 `MobileShell.tsx:120-125`의 shareTarget 처리는 채팅 탭으로 전환하고 즉시 `onConsumeShareTarget()`을 부를 뿐, `share_id`로 캐시에 저장된 파일을 읽어오는 코드가 저장소 어디에도 없다**(`/share-target-file/` grep 0건). 즉 **공유된 파일은 캐시에만 남고 채팅에 첨부되지 않는다.** (P2 · 확인 — 상세는 채팅 담당 감사관과 중복 가능)
- Firebase SDK를 gstatic CDN에서 `importScripts`(`sw.js:14-15`)하므로 SW 설치가 외부 CDN 가용성에 의존한다(try/catch로 치명적이지는 않음).
- `app/manifest.json/route.ts`: Samsung Internet에는 `share_target`을 제거하는 UA 분기가 있고 `Vary: User-Agent` + `no-store`가 정확히 설정되어 있다. 정상.

## F. Electron / TWA / PWA 노출면

**Q5 (Electron IPC 노출면)** — `electron-app/preload.js:8-29`
- 노출 API는 3개뿐: `isElectron`(bool), `showNotification(payload) → ipcRenderer.invoke('allerp:show-notification')`, `onNotificationClick(cb)`. `ipcRenderer`·`require`·fs 접근은 노출되지 않는다.
- `contextIsolation: true`, `nodeIntegration: false` (`main.js:58-59`) — 기본 하드닝은 정상.
- 핸들러(`main.js:106-223`)는 payload를 전부 `String()`으로 강제 변환하고 `data`는 object 검증 후 그대로 렌더러에 에코할 뿐 파일시스템/셸을 건드리지 않는다. **IPC 표면 자체는 P0급 위험 없음.**
- 위험은 **누가 호출할 수 있는가**다: `will-navigate` 핸들러가 없어 메인 창이 임의 오리진으로 항해할 수 있고, 그 문서에도 preload가 적용된다. 결합하여 A13-08(부분문자열 오리진 비교)로 임의 오리진이 카메라·마이크·알림 권한을 획득할 수 있다 → **P1**.
- `setWindowOpenHandler`(`main.js:95-102`)는 http/https만 외부 브라우저로 보내고 `blob:`/`data:`는 `action:'allow'`로 Electron 내부 창을 연다. 새 창은 부모 webPreferences(=preload 포함)를 상속하므로, 페이지가 만든 `blob:` 문서에도 `allerpDesktop`이 노출된다. (P2 · 의심)
- `sandbox: true` 미설정. (P3)

**Q6 (TWA)** — `android-twa/`

## I. 미확인 항목

1. **실기기 검증 미실시** — iOS Safari 입력 확대(A13-19), 노치 겹침(A13-29), 안드로이드 back 동작(A13-04), TWA 알림(A13-07)은 코드 근거만으로 판정했다. 실기기 1회 검증 필요.
2. **Android 빌드 미실시** — A13-06(문자열 리소스 따옴표)은 aapt2 출력으로 확정해야 한다.
3. **`assetlinks.json`이 CDN/Cloudflare 레벨에서 별도 서빙 중일 가능성** — 저장소·`wrangler.toml`·`middleware.ts`(matcher가 `/main/:path*`뿐)에서는 근거를 찾지 못했으나, Cloudflare Pages 대시보드 설정은 확인하지 못했다.
4. **오프라인 중복 전송 빈도** — A13-13/A13-14의 코드 경로는 확인했으나 실제 발생률(서버 커밋 후 응답 유실 비율)은 로그 없이 판단 불가. 중복 행 존재 여부를 D1에서 샘플 조회하면 확정 가능.
5. **`/share-target` 파일 소비 경로** — `share_id`로 저장된 캐시 파일을 읽는 코드를 찾지 못했으나, 채팅 업로드 담당 감사관 영역과 겹치므로 교차 확인 필요.
6. **`electron-app/AllERP-Windows-Updated/` 및 `dist/`** — 빌드 산출물(git 미추적)이라 소스 감사 대상에서 제외했다. 배포 중인 바이너리가 현재 `main.js`/`preload.js`와 동일한지는 확인하지 못했다.
7. **Playwright `mobile-320` 프로젝트의 실제 통과 여부** — 스펙 3종(`mobile-overflow`, `mobile-components`, `mobile-sheet-history`)이 등록되어 있으나 읽기 전용 원칙상 실행하지 않았다. A13-18(활성 탭 오프스크린)은 `mobile-overflow` 스펙이 잡지 못하는 종류의 결함으로 보인다.
