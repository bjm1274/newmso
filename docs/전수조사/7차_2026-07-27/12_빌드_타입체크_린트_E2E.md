## 3. E2E — 환경 결함으로 결과 해석에 주의 필요

```bash
npm run test:e2e -- --reporter=list
```

`playwright.config.ts` 기준 `fullyParallel: false`, `workers: 1`, 프로젝트 6종(desktop-chromium / mobile-chromium / mobile-android-chromium / mobile-iphone-webkit / mobile-320 / a11y-chromium). `npm run test:e2e` 는 `--grep-invert @real-db` 로 실DB 태그를 제외한다.

### 3-1. 치명적 환경 문제 — 로컬 D1 이 비어 있음

개발 서버 로그에 **`no such table` 이 2068회** 기록됐다. 누락 테이블:

- `staff_members`
- `approvals`
- `notifications`
- `rate_limit_attempts`

`.wrangler/state/v3/d1/miniflare-D1DatabaseObject/` 에 sqlite 파일이 2개 있는데 하나는 163테이블·62MB, 현재 바인딩이 붙은 쪽은 **0테이블**이다. `wrangler.toml:53-57` 의 `database_id` 가 과거 값에서 바뀌면서 로컬 상태가 갈린 것으로 보인다(정확한 원인은 미확인).

**따라서 desktop-chromium 실패 대부분은 코드 결함이 아니라 로그인조차 불가능한 환경 탓이다.** 예: `api-authorization.desktop.spec.ts` 7건 실패는 전부 `staff_members` 부재로 세션 생성이 실패한 결과이며, **권한 검사가 실제로 뚫렸다는 증거가 아니다.**

`playwright.config.ts` 에는 DB 시드 단계가 없다(`webServer` 는 `npm run dev` 만 띄운다). → `12-03` (P1 · 기능작동 — E2E 가 검증력을 갖도록 시드 픽스처 필요)

### 3-3. 더 중요한 신호 — 테이블이 통째로 없는데도 43건이 통과했다

`staff_members`·`approvals`·`notifications` 가 존재하지 않는 DB 상대로 43개 스펙이 "ok" 로 통과했다. 이는 **상당수 스펙이 데이터 정합이 아니라 "화면이 렌더되는지"만 검사**한다는 뜻이다. 예를 들어 `approval-form-submissions.desktop.spec.ts` 의 "supply request stats stay collapsed by default", "chat org view keeps department cards collapsed by default" 같은 항목은 DB 없이도 통과한다.

즉 이 스위트는 **회귀 방지용 UI 스모크 테스트에 가깝고**, 01~11 문서가 지적한 권한 우회·수량 정합·알림 도달 같은 결함을 잡아낼 설계가 아니다. → `12-04` (P1 · 테스트 커버리지)

## 4. 실행 로그에서 새로 발견된 코드 결함

정적 분석에서는 드러나지 않았고 **E2E 실행 로그가 노출시킨** 항목.

### 12-05 · P1 · 버그 — 레이트리밋 fail-open

`lib/rate-limit.ts:136-138`

```
} catch (err) {
  console.error('[rate-limit] checkRateLimit D1 오류, 레이트리밋 건너뜀:', err);
  return { allowed: true };
}
```

D1 조회가 실패하면 **차단이 아니라 허용**을 반환한다. `lib/rate-limit.ts:46-52` 의 `resolveD1()` 도 바인딩 획득 실패 시 `undefined` 를 반환해 같은 경로로 흐른다.

실행 로그에 `[rate-limit] consumeRateLimit D1 오류, 레이트리밋 건너뜀` 이 반복 기록됐다 — 즉 이 분기는 이론상 경로가 아니라 **실제로 밟히는 경로**다. D1 장애·마이그레이션 미적용·테이블 손상 시 로그인 무차별 대입 방어가 조용히 사라진다.

**수정 방향**: 인증·비밀번호 검증 경로는 fail-closed(429 반환)로, 부수적 경로만 fail-open 으로 분리.

### 12-06 · P2 · 오류 — 강제 로그아웃 검사도 동일하게 실패를 삼킴

로그에 `[isStaffForceLoggedOutInDb] check failed` 가 반복 기록된다. 강제 로그아웃 대상 여부를 확인하지 못했을 때 세션을 유지하는 방향으로 흐르면, 관리자가 강제 로그아웃시킨 계정이 DB 장애 중 계속 활동할 수 있다. (정확한 폴백 방향은 미확인 — `12-미확인-01`)

## 5. 이 문서의 한계 (정직한 고지)

- E2E 는 **desktop-chromium 프로젝트 진행 중 시점의 수치**이며 mobile 3종·mobile-320·a11y 프로젝트는 실행되지 않았다.
- 로컬 D1 공백 때문에 **개별 E2E 실패를 코드 결함의 근거로 쓸 수 없다.** 위 §4 의 두 건만 로그 원문에 근거한 실제 결함이다.
- `npm run build` 는 실행하지 않았다(타입체크·린트로 대체). `build:cloudflare`/`deploy:cloudflare` 는 Cloudflare API 접근이 필요해 이번 감사 범위 밖.
- `dupcheck`(jscpd) 는 npm 레지스트리 접근이 필요해 실행하지 않았다.

5. 잡동사니 디렉터리를 git 에서 제거하고 `.gitignore` 정리 — `docs/REPO_HYGIENE.md` 의 기존 정책과 실제 상태를 일치시킨다.
