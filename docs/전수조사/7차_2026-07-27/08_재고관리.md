# 08. 재고관리 전수조사 (7차, 2026-07-27)

감사관 A9 · 대상: PC(`재고관리통합.tsx` + 6 워크센터 + 재고관리서브 리프) + 모바일(`모바일/재고/`) + 서버 API(`app/api/inventory/*`) + 권한(`lib/access-control.ts`, `lib/db/auth/policies.ts`)

## 요약

재고 수량 엔진의 **정상 경로는 잘 설계돼 있다**. `postInventoryMovement`(`lib/inventory-movement-service.ts:244-259`)는 `WHERE ... AND quantity = prevQty` compare-and-set + 부족가드 + 월마감잠금 + 유통기한가드를 갖추어, **stock-post 를 통한 동시 출고로는 음수 재고가 발생하지 않는다**(경합 시 `STOCK_CONFLICT` 409). 그러나 **같은 보호가 이관(stock-transfer)에는 없다** — 절대값 무가드 write 라 동시 이관 시 재고 총량이 늘어나거나 사라진다(A9-01, P0). 또한 월마감 API 가 호출자가 보낸 `company` 를 검증 없이 신뢰해 **타 회사 월마감을 잠그고 풀 수 있다**(A9-02, P0).

전표 엔진을 우회하는 뒷문도 열려 있다. `POLICY_REGISTRY` 가 `inventory` 테이블에 `update: INVENTORY_SCOPE` 를 부여하고 **컬럼 가드가 없어**, 인증된 사용자가 `/api/d1/mutate` 로 `quantity` 를 임의 값으로 직접 쓸 수 있다 — 이력 0건, 마감잠금 무시(A9-03, P1). 회사 격리 자체는 `filterByPolicy`/`assertInventoryItemCompanyScope` 로 서버에서 강제되어 **교차 회사 데이터 유출은 없다**(모바일 훅의 클라이언트 필터 누락도 서버가 막는다).

알림은 재고 부족만 정상이다. `check-inventory.ts` 크론이 in-app + 푸시까지 보낸다. 반면 **유효기간 임박 알림 잡은 존재하지 않고**, 불출완료/발주진행/불출취소 3종은 클라이언트 `d1.from('notifications').insert` 로 끝나 **푸시가 나가지 않으며**, 자동 발주 기안은 `current_approver_id` 를 안 넣어 **결재 알림 자체가 0건**이다.

ABC 분석·수요 예측은 실제 계산을 하나 화면에 표시되는 기여도(70/20/10)와 신뢰도(90/78/62%)는 **하드코딩된 장식**이고, 단가 누락 시 1원 대체·이력 없는 품목에 임의 계수 부여로 **데이터가 없어도 등급표가 정상처럼 채워진다**. 실사 대시보드는 존재하지 않는 컬럼을 읽어 **진행률 항상 100%·차이 항상 0** 을 표시하며, 실사 입력 화면(audit)은 hidden 인데 「실사 시작」 버튼이 그리로 연결되지 않아 **UI 경로가 없다**. 자산 QR 대여/반납과 UDI 공급내역 보고는 **껍데기만 있고 동작하지 않는다**. 모바일은 전 구간 **읽기 전용**이며 월마감 버튼은 토스트만 띄우는 더미다.

**결론(Q1)**: `stock-post` 경로는 read-modify-write 가 아니라 **조건부 SQL UPDATE(CAS)** 이므로 동시 출고 시 음수 재고가 발생하지 않는다. 그러나 **이관 경로에는 같은 가드가 없어 수량 보존이 깨진다**(A9-01). 낙관적 UI 는 PC·모바일 모두 사용하지 않아(서버 응답 후 refresh) 롤백 이슈는 없다.

**결론(Q2)**: 불출 워크플로의 상태 전이는 **서버에서 전혀 검증되지 않는다** — 클라이언트가 `approvals.meta_data.inventory_workflow` 를 통째로 덮어쓰는 구조다(A9-07). 취소 시 수량 원복은 `reverseInventoryIssue` 로 수행되나 목적지 매칭 폴백 결함이 있다(A9-12).

**결론(Q7 · 월마감 소급 차단)**: **월마감 잠금은 실제로 동작한다** — `postInventoryMovement` 가 `assertNotClosedMonth`(`lib/inventory-movement-service.ts:115-140, 188`)에서 `inventory_closing_snapshots` 를 조회해 `locked`/`closed`/`마감` 이면 `INVENTORY_PERIOD_LOCKED` 를 던지고, 라우트가 423 으로 변환한다(`stock-post/route.ts:178-183`). 따라서 **입고·출고·소모·실사조정·발주입고는 마감 후 차단된다**. 다만 차단이 미치지 않는 3개 구멍이 있다: ① 이관(`stock-transfer`)은 검사 자체를 안 한다(A9-05), ② `/api/d1/mutate` 직접 UPDATE 는 우회한다(A9-03), ③ 품목 `company` 가 비면 검사가 통과된다(A9-30). 그리고 마감 **재실행은 이중 반영되지 않고 스냅샷을 덮어쓴다**(멱등이지만 이력 소실, A9-29). 잠금 자체는 같은 권한으로 해제 가능하다(A9-04).

**결론(Q3)**: 회사/부서 격리는 **서버에서 정상 강제**된다 — 쓰기는 `assertInventoryItemCompanyScope`(`lib/inventory-scope-guard.ts:52-74`), 읽기는 `filterByPolicy`(`app/api/d1/query/route.ts:321, 385`). 다만 **월마감 API 만 격리가 빠졌고**(A9-02, P0), `quantity` 컬럼 가드가 없어 전표 엔진 우회가 가능하다(A9-03).

## I. 미확인 항목

1. **런타임 재현 미실시** — A9-01(이관 경합)·A9-06(동시 입고)은 코드 정적 분석 결과다. D1 의 실제 동시성 스케줄링에서 재현 빈도는 측정하지 않았다. 다만 **가드 부재 자체는 확인**이다.
2. **A9-02 실제 익스플로잇 미검증** — `assertInventoryCompanyScope` 호출이 closing 라우트에 **없다는 것은 확인**했으나, 실제 타사 `company` 문자열로 요청을 보내 200 이 오는지는 실행하지 않았다(읽기 전용 감사 원칙).
3. **A9-03 우회 실증 미실시** — `POLICY_REGISTRY.inventory.update = INVENTORY_SCOPE` 이고 컬럼 가드 grep 이 0건인 것은 확인. 실제 `/api/d1/mutate` 호출로 `quantity` 가 바뀌는지는 미실행.
4. **`suppliers` 테이블 회사 격리** — `use-io-data.ts:146` 이 회사 필터를 걸지 않는다(주석상 "company 컬럼 없음"). `POLICY_REGISTRY` 에 `suppliers` 정책이 있는지 확인하지 못했다 — 있으면 정상, 없으면 거래처 정보 교차 노출 가능.
5. **`.limit(1000)` 초과 시 재고 부족 알림 누락**(`check-inventory.ts:133`) — 실제 품목 수가 1000 을 넘는지는 데이터를 조회하지 않아 미확인.
6. **`inventory_count_sessions` 컬럼 실재 여부** — A9-41 은 `lib/db/schema.ts:898-908` 의 drizzle 정의 기준이다. 실제 D1 테이블에 `counted_count` 등이 마이그레이션으로 추가돼 있을 가능성은 배제하지 못했다(스키마 파일과 실 DB 대조 미실시).

### 조사 중 해소된 상충 주장

- 하위 조사에서 "**월마감 잠금이 아무것도 차단하지 않는다**(`inventory_closing_snapshots` 를 참조하는 API 가 closing 라우트 하나뿐)"는 보고가 있었으나, **직접 확인 결과 오류**다. `lib/inventory-movement-service.ts:115-140` 의 `assertNotClosedMonth` 가 해당 테이블을 조회하고 L188 에서 호출되어 `stock-post` / `po-receive` / `po-inspect` 전 경로에 잠금이 적용된다. 해당 보고는 `app/api` 범위만 grep 한 데서 비롯된 것으로 보인다. 본 보고서는 **잠금이 동작한다**는 전제 위에서 우회 경로 3건(A9-03·05·30)만 지적한다.
