## 분류별 발견

### D — 중복

**D-1 [높음] `메신저검색이동훅.ts` 전체가 `메신저검색훅.ts`와 중복 + 죽은 코드**
- 근거: `메신저검색이동훅.ts:31-61`의 `openGroupFromGlobalSearch`/`openRoomFromGlobalSearch`/`openMemberFromGlobalSearch`와 `transientHighlightQuery` 로직이 `메신저검색훅.ts:340-370, 620-624`에 거의 동일하게 재구현됨.
- 참조확인: `Grep "useChatSearchNavigation|메신저검색이동훅"` → 코드 import 0건 (docs 2건 + 자기정의 1건뿐). `메신저.tsx`는 `transientHighlightQuery`/`openRoomFromGlobalSearch`를 검색훅(`useChatGlobalSearch`)에서 받아 사용(`메신저.tsx:2333,2888,3504`).
- 결론: **파일 전체가 미사용 죽은 코드이자 중복.**
- 조치: `메신저검색이동훅.ts` 삭제. (정본은 검색훅 내부 구현)

**D-2 [높음] `메신저패널.tsx`가 `메신저미디어아카이브`/`메신저전역검색`을 통째 중복 (교차확인)**
- 근거: `메신저패널.tsx:9,22-40,86-92`(MediaArchivePanel·MessengerMediaFilter), `:126-182`(GlobalSearchModal)이 `메신저미디어아카이브.tsx`·`메신저전역검색.tsx`와 동일 컴포넌트를 다시 정의.
- 참조확인: 실사용 import는 모두 분리 파일 쪽 — `메신저.tsx:64-65`, `MessengerModalHost.tsx:5,7`이 `./메신저미디어아카이브`·`./메신저전역검색`에서 import. `Grep "from '...메신저패널'"` → 0건.
- 결론: `메신저패널.tsx` 전체가 미사용 죽은 중복 파일. (별도 그룹 G1에서 이미 보고됨 — 본 그룹은 교차확인만)
- 조치: 다른 그룹 결정에 위임. 중복 사실 재확인.

**D-3 [의심/낮음] 리마인드 알림 payload 빌드 패턴 3중 반복 (Q와 경계)**
- 근거: `메신저예약공지훅.ts:127-145`, `useChatNoticeAdmin.ts:88-105`, `메신저운영센터.tsx:365-380` 세 곳이 `notifications.insert` payload(`user_id/type:'message'/title/body/read_at/metadata=buildChatNotificationMetadata({reminder_kind...})`)를 거의 같은 형태로 각각 작성.
- 결론: 완전 중복은 아니나(대상·문구 상이) 공통 헬퍼(`buildNoticeReminderPayload`)로 추출 여지. → Q로 분류.

> 특별임무 검증: "공지스케줄 vs 예약공지훅 vs NoticeAdmin 중복(D)" 가설은 **대체로 거짓**. 세 파일은 각각 (영속 계층 / 디스패처 / 현재공지 읽음통계)로 책임이 다름. 공통점은 D-3의 payload 패턴뿐.

### SEC — 보안

**SEC-1 [중간/의심] 드라이브 링크 href에 URL 스킴 검증 없음 (저장형 XSS 여지)**
- `메신저운영센터.tsx:858` `<a href={link.url || '#'} target="_blank" rel="noopener noreferrer">`, 동일하게 `:670` 파일 최신본 `href={group.latest.file_url}`.
- 근거: `link.url`은 DB(`messenger_drive_links.url`)에서 그대로 렌더. `javascript:` 스킴 입력 시 클릭 실행 위험. `rel`은 있으나 스킴 필터 없음. `jm5` 권고 위반.
- 조치: 저장/렌더 시 `http(s):`만 허용하는 sanitize. (입력 주체가 운영자라 위험도 중간)

### P — 성능

**P-1 [낮음] 검색 멀티컬럼 N×페이지 순차 쿼리**
- `메신저검색훅.ts:149-203`: 텍스트 검색 시 `content/sender_name/file_name/file_url` 컬럼별로 각각 페이지네이션 루프(`ilike` OR를 못 써 컬럼 수만큼 전체 스캔 반복). 5년 lookback × 200건 페이지.
- 근거: D1/프록시 제약상 불가피한 면이 있으나 대화량 많은 방에서 요청 폭증 가능. `jm2` 관점 주의.
- 조치(의심): 서버측 FTS 또는 단일 OR 쿼리 가능 여부 확인.

**P-2 [낮음] 운영센터 초기 4쿼리 병렬은 양호하나 읽음커서 추가 1쿼리 직렬**
- `메신저운영센터.tsx:160-198`: Promise.all 4건 후 `room_read_cursors` 1건을 직렬 추가. 허용 범위.

### U — 불필요/구조

**U-1 [중간] 예약공지 시스템이 localStorage + 브라우저 폴링 기반 (정본 DB 테이블 미사용)**
- 근거: 정본 스키마에 `scheduled_messages`(schema.ts:1908, room_id/sender_id/content/scheduled_at/is_sent/reply_to_id)와 서버 push 큐 `chat_push_jobs`(:337)가 이미 존재. 그러나 예약공지는 `메신저공지스케줄.ts` 전체가 `window.localStorage`(`:100-125`)에 저장하고 `메신저예약공지훅.ts`가 **권한자가 앱을 열어둔 동안에만** 발송(`:47-48` `canManageNoticeOps && roomPrefsUserId` 가드, UI도 `운영센터:692`에서 "앱이 열려 있을 때 자동 발송" 명시).
- 영향: (a) 디바이스 종속(다른 PC/브라우저에서 안 보임), (b) 탭이 닫혀 있으면 미발송, (c) `scheduled_messages` 인프라와 기능 중복. 신뢰성 낮은 설계.
- 조치(의심): `scheduled_messages` + 서버 cron/`chat_push_jobs` 경로로 이관 검토. 최소한 한계 문서화.

**U-2 [낮음] 컬럼 정합성은 양호**
- `messages`의 `is_deleted/file_kind/file_name/file_url/sender_name`(schema:1225-1235), `room_read_cursors.last_read_at`(:1828), `messenger_drive_links`(:1249-1264), `attendances.status/work_date`(:185-188), `shift_assignments.shift_id/work_date` 모두 정본과 일치. 검색훅의 `omittedColumns` 폴백도 적절. **무음실패 컬럼 오타 미발견.**
