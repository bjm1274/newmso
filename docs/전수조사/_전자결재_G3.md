## ★특별임무 결론

1. **양식 10여종 공통 패턴 중복(D/Q)**: 폼들이 `setExtraData`/`setFormTitle` props 계약을 공유하나 각 양식의 필드 구조가 달라 **상태/검증 로직의 복붙 중복은 없음**. 단 패턴(useState + useEffect로 extraData 동기화)은 반복되나 추상화 불가능한 수준 — 문제 아님.
2. **비품구매양식 vs Supplies* vs useSuppliesForm 중복**: **중복 아님 (가설 반증)**. 하나의 응집된 모듈을 JM 규율대로 view/hook/helper/하위컴포넌트로 정상 분할한 것. 재export로 호환 유지(비품구매양식.tsx L29).
3. **양식빌더.tsx (11줄)**: **죽은코드/스텁 아님**. 관리자 `전자결재양식관리`를 스크롤 래퍼로 감싼 정상 어댑터.
4. **출결정정양식(681) vs AttendanceCorrection***: **심각한 중복 + 죽은코드 확정**. 아래 D-1 참조.

### D 중복

**[D-1] (높음) 출결정정 로직·UI 전면 중복 + orphan 컴포넌트**
- `출결정정양식.tsx`(681줄, 라이브)와 `AttendanceCorrectionDateSection.tsx`(331) + `AttendanceCorrectionSummary.tsx`가 **동일 로직을 통째로 중복**:
  - `isAttendanceCorrectionsLegacySchemaError` — 출결정정양식.tsx:34 ≡ AttendanceCorrectionDateSection.tsx:26
  - `withAttendanceCorrectionsFallback` — 출결정정양식.tsx:44 ≡ DateSection:36
  - `getCorrectionDate` — 출결정정양식.tsx:55 ≡ DateSection:47
  - `getCorrectionStatus` — 출결정정양식.tsx:59 ≡ AttendanceCorrectionSummary.tsx:12
  - `REASON_BADGE` 상수 — 출결정정양식.tsx:63 ≡ DateSection:18 (값은 다름: 인라인은 emoji, split은 LucideIcon)
  - problemDates 산출 ~150줄 — 출결정정양식.tsx:106-270 `fetchProblemDates` ≡ DateSection:68-214 `loadAttendanceProblemDates`
  - 날짜섹션/요약 UI — 출결정정양식.tsx:447-635 ≡ DateSection 컴포넌트 + Summary 컴포넌트

- 영향: 두 곳에 동일 로직 → 한쪽만 고치면 drift. 현재 라이브는 681줄 monolith.
