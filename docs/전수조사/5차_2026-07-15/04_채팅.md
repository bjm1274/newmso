## Critical

### CH-C1. 메시지 INSERT: 서버 멤버십·sender 위조 가능
- **파일:** `lib/db/auth/policies.ts:241-248` (`messages` select/insert **PUBLIC**), `app/api/d1/mutate/route.ts:403-407` (assertAccess만, sender 강제 없음), 클라 `메신저전송훅.ts:95-150`, `모바일/채팅/data-hooks.ts:815-855`
- **증상:** 로그인 사용자가 **미참여 방**에 메시지를 쓰거나, `sender_id`를 타인으로 넣어 **사칭 전송** 가능. 이후 push job도 그 sender로 적재.
- **원인:** D1 정책이 채팅 insert를 인증 공개로 두고, mutate가 세션 id를 payload에 덮어쓰지 않음. 클라이언트 `visibleRoomIds` 검사는 우회 가능.
- **수정:** mutate에서 `messages` insert 시 (1) `sender_id = session staff id` 강제, (2) room members(또는 notice) 멤버십 검증. 참고: `api/chat/quick-reply/route.ts:63-68`.

### CH-C2. `PATCH /api/chat-rooms/[id]` 멤버십 검증 공백
- **파일:** `app/api/chat-rooms/[id]/route.ts:1-12` (주석: 멤버 검증 명시) vs `:49-92` (실제: **where id만 UPDATE**, 멤버 조회 없음)
- **증상:** 임의 방의 `members`/`name`/`type` 변조 — 전원 추방, 멤버 주입, 방 이름 하이재킹.
- **원인:** 주석 설계와 구현 불일치. D1 직접 update.
- **수정:** 기존 members 조회 → 호출자가 기존 멤버(또는 admin)인지 확인. self-leave는 “본인 제거만” 허용. 이름/타입 변경은 생성자·관리자 제한.

### CH-C3. 채팅 테이블 일괄 PUBLIC_ALL (정책 공백)
- **파일:** `lib/db/auth/policies.ts:476-492` (`chat_rooms`, `message_bookmarks`, `message_reactions`, `pinned_messages`, `polls`, `room_read_cursors`, `messenger_drive_links` 등)
- **증상:** 로그인만 하면 **전 직원 채팅방 목록·멤버 구성·메시지 본문** 조회 및 (정책상) 쓰기 가능. soft-delete 소유 가드는 **messages UPDATE**에만 존재.
- **원인:** Phase 8-K “미등록 테이블 PUBLIC 일괄” 회귀 방지 목적 — 보안 후속 phase 미완.
- **수정:** `chat_rooms` select → 멤버십 스코프(또는 서버 필터 API). reactions/bookmarks/pins → self 또는 room-member. `messages` select도 동일.

### CH-C4. 채팅 푸시 알림 type 항상 `message` (멘션 설정 무력)
- **파일:** `lib/chat-push-dispatch.ts:763-769` (`type: 'message'`, metadata `notificationType: 'message'`)
- **증상:** 방 알림 “멘션만” 등 필터가 type/mention에 의존하면 **멘션 메시지도 일반 메시지와 동일**. 5차 알림 보고서 N-C3와 동일 뿌리.
- **원인:** mentionedIds는 **발송 대상 필터(뮤트 우회)** 에만 사용, notification row type 분기 없음.
- **수정:** 멘션 대상 user에 한해 `type: 'mention'` 기록 + metadata 일치.

### CH-C5. `chat_접근` / `chat_방생성` / `chat_파일첨부` 서버·모바일 미강제

  - 모바일: `모바일/**` chat_* **0건**  
  - 업로드 API: `api/chat/upload/route.ts` 권한 키 없음  
  - 방 생성 API: `api/chat-rooms/route.ts` 권한 키 없음
- **증상:** 관리자가 권한 OFF 해도 API·모바일·mutate로 우회 가능. `chat_접근=false`는 메뉴만 숨길 수 있어도 딥링크/직접 API로 접근 가능.
- **수정:** 서버 세션 claims에 feature permissions 로드 후 업로드/방생성/mutate messages에 강제. 모바일 목록·새대화·첨부 동일 게이트.

### CH-C6. 메시지/방 SELECT 전역 노출 (멤버 외 열람)
- **파일:** `chatQueryService.ts:79-106` (`fetchAllChatRooms` 전체), 모바일 `data-hooks` rooms fetch + client `isRoomVisibleToUser` (`:106-114`), policies messages select PUBLIC

- **수정:** 서버/쿼리 레이어에서 `members` JSON 포함 사용자 또는 notice만 반환. 메시지 조회는 room_id + membership.

## Major

### CH-M1. PC/모바일 일반 텍스트 이중 전송(in-flight 락 부재)
- **파일:** `메신저전송훅.ts:83-205` (연속 호출 가드 없음), `메신저컴포저.tsx:293,598` (Enter/버튼 즉시 `onSendMessage`), `모바일/채팅/채팅방.tsx:307-355` (`handleSendText` 전송 중 disabled 없음; 스레드만 `threadSending`)
- **증상:** 더블클릭·더블 Enter·느린 네트워크에서 **동일 내용 2건** insert.
- **원인:** optimistic 후 즉시 composer clear하나, 전송 Promise 완료 전 재호출 차단 없음. (ward quick-reply만 messageId 락 존재)
- **수정:** `sendingRef` / room별 in-flight + UI disabled; idempotency key 옵션.

### CH-M2. `fetchData({ force: true })` 호출되나 구현이 force 무시
- **파일:** `메신저방데이터훅.ts:1225` (`fetchData = async () =>` 무인자), 내부 `fetchAllChatRooms()` **options 미전달** (`:1230,1257`); `메신저구독훅.ts:113` 타입은 force, `:248/272/369/409/452` 등 `{force:true}` 호출
- **증상:** 실시간 재연결 후 **5초 TTL 캐시**로 목록/상태가 stale. 강제 재조회 의도 실패.
- **원인:** 시그니처 불일치.
- **수정:** `fetchData(options?: {force?: boolean})` → `fetchAllChatRooms({ force: options?.force })`.

### CH-M3. `is_announcement` SELECT 컬럼 누락
- **파일:** `lib/chat-query-columns.ts:7-15` (OPTIONAL에 없음), 스키마 `lib/db/schema.ts:360` 존재, `presentRoomRow` API는 반환
- **증상:** 클라 `buildChatRoomSelect()` 경로에서 `is_announcement` 항상 공백/undefined → 공지 채널 분기 오동작 가능.

## 결론

5차 시점 채팅 모듈은 **기능 표면(PC 풀세트 + 모바일 핵심 패리티)** 이 넓고, 3차 대비 **훅 고아·OG SSRF·모바일 나가기/로딩/딥링크/staffId** 등 UX 결함은 상당수 **해소**되었다.  
그러나 데이터 평면은 여전히 **“로그인 = chat PUBLIC”** 에 가깝고, **방 멤버십을 서버가 강제하지 않는 쓰기 API**가 남아 보안 Critical 6건이 최우선이다.  
`quick-reply`에 이미 있는 멤버십 패턴을 **mutate messages · chat-rooms · upload · typing · read-cursors** 로 확산하고, 알림 type=mention 과 권한 키 서버 강제를 묶으면 실사용 리스크의 대부분을 닫을 수 있다.
