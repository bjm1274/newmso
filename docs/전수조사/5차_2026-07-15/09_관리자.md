## 1. 한 줄 요약

| 축 | 판정 |
|----|------|
| **3차 SEC-1 (권한 상승)** | **해소** — `직원권한통합` → `POST /api/admin/staff-permission` (세션+`isAdminSession`, 컬럼 화이트리스트, 서버 감사로그) |
| **3차 SEC-2 (데이터초기화)** | **해소** — `POST /api/admin/data-reset` 서버 D1 삭제 + `verify-unlock` 재검증 |
| **3차 LEGACY admin id '1'** | **해소** — `LEGACY_ADMIN_LOGIN_IDS = []` |
| **워크센터 세부 권한 게이팅** | **개선** — 영문 워크센터 진입 시 `canAccessAdminSection` 적용 (`관리자전용.tsx`) |
| **ExecDashboard staffs=[]** | **개선** — `useAppData()`로 staffs/user 전달 (3차 X-W 상당 부분 해소) |
| **더미·폴백·클라이언트 쓰기** | **잔존** — Ops 일반/외부연동 더미, Company FALLBACK 실법인명, 팝업 insert 클라 직접, calendar/feed 토큰=staff_id |
| **모바일 관리자** | 허브는 `menu_관리자`만 검사. **시스템마스터·세부 admin_* 허브 필터 없음** |

**핵심:** 3차 당시 “관리자 보안 최우선” 항목(권한·초기화·레거시 ID)은 서버 라우트로 상당 부분 이관됐다. 남은 리스크는 **(1) 민감 쓰기의 클라 SDK 잔존 (팝업·감사조회 등)** · **(2) 운영 UI 더미/폴백이 실데이터로 오인** · **(3) 모바일 허브의 세부 권한·시스템마스터 게이트 약함** · **(4) 레거시 한글 탭 경로와 영문 워크센터 이중 구조 유지**.

## 6. 데이터·보안 흐름 (요약)

```
[사이드바 관리자 subView]
    ├─ exec|company|roles|ops|forms|audit
    │     → canAccessAdminSection → getAdminWorkcenter → 서브모듈
    │           ├─ 민감 쓰기: /api/admin/* (권한·초기화·비번·감사 KPI·백업)
    │           └─ 일부 읽기/쓰기: db-client (팝업 insert, 로그 select, 회사/예산 등)
    └─ 시스템마스터센터 (isSystemMaster)
          → /api/admin/system-master + 클라 패널
```

**권장 원칙 (수정 시):** 관리자 쓰기·삭제·권한·백업·초기화는 전부 서버 라우트 + `isAdminSession`/`systemMaster`. 클라이언트는 읽기 전용 또는 서버 프록시만.

## 9. 결론

관리자 영역은 3차 이후 **가장 위험한 권한·초기화 경로가 서버화**되어 보안 바닥이 올라왔다. 구조적으로 6 워크센터 + 권한 키 체계는 정합적이다.  

남은 과제는 “관리자 화면이 **실운영처럼 보이는 더미**”와 “**클라 SDK로 남는 민감 CRUD**”, “**모바일 허브의 거친 권한 필터**”다. 재무회계 본메뉴와 관리자 내 재무 대시보드를 혼동하지 말 것 — 후자는 exec 하위 KPI·마감 성격이며, 전자는 별도 `finance_*` 메뉴(→ `10_*.md`).
