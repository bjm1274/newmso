## 1. 한 줄 요약

| 축 | 판정 |
|----|------|
| **PC 라우팅** | 사이드바 4 WC(`status`/`io`/`item`/`analyze`) → 내부 7대(status·inout·order·audit·udi·master·analyze) 정상 해석. 3차 시절 “io/item 무조건 status 폴백” 버그는 **해소** ✅ |
| **레거시 서브** | 15+ 화면 중 **5개만 잔존**(물품등록·발주관리·자산QR·재고실사·UDI) + 공통 컴포넌트. 워크센터가 **dynamic import로 임베드** — 전면 병행 구조는 축소됨 |
| **수량 SSOT** | 입출고·실사·기초재고가 `postStockMovement` → `/api/inventory/stock-post` 로 수렴. 이관·소모·마감·PO 입고/검수 API 존재 ✅ |
| **모바일 패리티 C1** | **UI 배선은 수정됨** — 4화면 모두 `company` prop → 훅 인자. 다만 훅 내부 `purchase_orders.company` / `suppliers.company` 필터는 **스키마 불일치** → company 전달 시 **IO/발주 KPI 깨질 수 있음** |
| **PC 회사 격리** | 워크센터가 `use*Data()` **인자 없이 호출** → 클라 company eq 없음. RLS(`INVENTORY_SCOPE`)에만 의존. 로그 TOP5·마감·Master fetch 등 **부분 미필터** 잔존 |
| **가장 큰 잔존 리스크** | (1) company 컬럼 불일치로 필터 실패 (2) PC 훅 company 미전달 (3) stock API 로그인-only 권한 (4) 발주 오버레이 빈 props (5) 실사 for-loop 부분 실패 |

## 2. 아키텍처 맵

```
사이드바 재고관리
  status ──► StatusWorkcenter          (KPI·표·공급신청·긴급알림)
  io     ──► IoWorkcenterShell
               ├ tab 입출고 → InoutWorkcenter  (+ 수동등록 → stock-post)
               └ tab 발주   → OrderWorkcenter  (+ 레거시 발주관리 모달)
  item   ──► MasterWorkcenter          (물품등록 | 자산QR | 거래처 목록)
  analyze──► AnalyzeWorkcenter         (ABC | 수요예측 | 월마감)
  (딥링크)
  audit  ──► AuditWorkcenter           (레거시 재고실사)
  udi    ──► UdiWorkcenter             (레거시 UDI관리)
  inout/order/master 개별 진입 가능

모바일 재고관리
  hub → stock | io | item | analyze | form-item | form-asset | form-order
  data-hooks → PC use-status/io/item/analyze-data 재export
```

### 3.2 PC — io (입출고 · 발주)

#### InoutWorkcenter

| 액션 | 경로 | 상태 |
|------|------|------|
| 오늘 입출고 목록 | `useIOData()` → inventory_logs(오늘) | 읽기 |
| 유형 필터 | 입고/출고/이관/반품 | 클라 |
| **수동 등록** | `postStockMovement` → stock-post | **쓰기 ✅** |
| 품목 목록 로드 | `db.from('inventory').select('*')` **company 없음** | **C** 혼입/노출 |

수동 등록 모드: 입고 | 출고 | 조정(absolute) | 반품.  
표시 버그: 매칭 품목 보유고를 `matchedItem.stock`으로 표시 — **quantity SSOT 무시** (m).

#### OrderWorkcenter

| 액션 | 경로 | 상태 |
|------|------|------|
| 발주 KPI/목록 | `useIOData()` orders | 읽기 |
| **+ 새 발주** | `LegacyPurchaseOrderManagement user={{}} inventory={[]} suppliers={[]}` | **C — 빈 props** |
| 상태 필터 | 대기/확정/배송/완료 | 클라 |

**[C-ORD]** `OrderWorkcenter.tsx` 오버레이는 user/inventory/suppliers를 **빈 값 고정**으로 넘김.  
StatusSubViews 발주 오버레이는 정상 로드. 동일 레거시 컴포넌트인데 **진입 경로에 따라 발주 생성 불가**.

레거시 `발주관리.tsx` 실 액션:
- 발주 목록(PO + 비품구매 결재)
- 안전재고 자동 발주 생성 (`purchase_orders` insert)
- 승인 상태 변경
- 입고/검수 연동(로그·API 경로 존재)

### 3.3 PC — item (물품 · 자산) → MasterWorkcenter

| 탭 | 구현 | 액션 |

| 물품 등록 | 레거시 `물품등록` | insert inventory(qty=0) → stock-post **기초재고** |

## 10. 결론

재고관리 5차 기준, **수량 변경의 서버 SSOT(stock-post/transfer/closing/PO 입고)** 는 3차 대비 크게 성숙했다.  
레거시 난립은 **5개 임베드**로 정리되었고, 모바일 더미 KPI·입출고 잘못된 테이블명은 제거되었다.

그러나 **회사 격리**는 “훅에 company 인자를 달았다”는 표면 수정과 달리:

1. **존재하지 않는 컬럼에 eq** (PO/suppliers) → 필터 활성화가 오히려 장애  
2. **PC는 여전히 인자 미전달**  
3. **서버 API·알림·실사 세션·마감 훅**은 스코프 불완전  

패리티 문서의 **C1(재고 회사 필터)** 은 Mobile UI 배선 기준으로는 **부분 해결**, 데이터 정합 기준으로는 **미해결(변형 잔존)** 으로 판정한다.
