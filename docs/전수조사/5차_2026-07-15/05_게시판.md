### 2.2 폐지 보드

| board_type | 상태 |
|------------|------|
| 익명소리함 | `REMOVED_BOARD_TYPES` · 메뉴/칩 제거 · 목록 필터 제외 |
| 직원제안함 | 동일 |

> 3차 SEC「익명소리함 본문 클라이언트 숨김」은 **보드 폐지로 해소**. 자유게시판 익명 옵션은 유지.

### 2.3 권한 모델 (`lib/access-control.ts`)

```
canAccessBoard(user, boardId, 'read'|'write')
  1) isPrivilegedUser → true
  2) 업무가이드 + read → true (공개 읽기)
  3) canAccessMainMenu('게시판') 필수
  4) board_*_read / board_*_write
```

- write 보유 시 read 암시(`PERMISSION_IMPLIES`).
- `board_업무가이드_read` → `board_자유게시판_read` 암시, write → 자유 write 암시 (설계 커플링 잔존).
- **PC**: 메뉴 필터·fetch·canCreatePost·canEdit/Delete에 `canAccessBoard` 적용.
- **Mobile**: 탭은 `canAccessMainMenu('게시판')` 수준. **보드별 read/write 미호출** → 전 카테고리 열람·작성 가능. **[C-1]**

## 4. 엔드투엔드 흐름

### 4.1 PC 목록·상세

1. `canAccessBoard(read)` 실패 시 posts=[]  
2. `board_type` eq · order created_at desc · **limit 500** · **company_id 미필터**  
3. 업무가이드는 fetch 스킵 → GuideLibrary  
4. 예약 공지: `isScheduledNoticePending` → 관리자만 목록 노출  
5. 상세 시 조회수 +1(무음 fail) · `markBoardPostRead` · 댓글 select  

### 4.2 Mobile 목록

1. `resolveBoardSubView`: 미지 subView → **`all`** (07-12 B-C1 **수정 확인**)  
2. **6 board_type 병렬 fetch** · limit 1000 · 모듈 캐시(칩 0 깜빡임 완화)  
3. 예약 글: 미래 시각이면 **작성자만** 노출  
4. 댓글 수: `board_post_comments` post_id chunk 집계 → `comment_count`  
5. 별표: `loadStarSet`  
6. `company` 인자 **미사용** (시그니처만)  

### 4.3 작성·방송

| 경로 | insert | broadcast |
|------|--------|-----------|
| PC 공지/경조 (즉시) | `runBoardPostMutation` | `POST /api/board/notice-broadcast` |
| PC 공지 (예약 미래) | insert + scheduled | create 시점 skip · **cron 없음** |
| Mobile 공지/경조 | `createBoardPost` | **없음** |

`notice-broadcast`: 세션 필수 · 작성자/admin · AUTO={공지,경조} · 공지방 메시지 · 전 재직 알림 `type:board` · 채팅 푸시.  
**부수효과:** 푸시 경로가 message 알림을 추가 적재할 수 있음(3차 D-5 계열, 알림 감사와 연계).

### 4.4 좋아요 / 별표 / 읽음

| 기능 | PC | Mobile |
|------|----|--------|
| 좋아요 | board_post_likes + likes_count 재집계 | 동일 패턴 |
| 별표 | `mso:board:favorites` LS | `board_post_stars` + LS 폴백 |
| 읽음 | board_post_reads upsert | 동일 · 시트 UI |
| 읽음 audience | staff 재직 전사 | 동일 · **회사 미필터** |

### 4.5 업로드

1. JSON → signed URL → 클라이언트 PUT  
2. 실패 시 multipart 폴백, **>50MB면 중단** (동영상 200MB 의도 시 폴백 무효)  
3. 서버 form 경로 magic-byte 검증 vs signed 경로 검증 약함(3차 SEC 잔존 가능)

## 6. 이슈 목록 (5차 신규·잔존)

### 6.1 Critical

#### [C-1] 모바일 보드별 `canAccessBoard` 미적용
- **증상:** `menu_게시판`만 있으면 공지 write 없는 직원도 전 보드 열람·작성.
- **근거:** PC `canCreatePost = canAccessBoard(...,'write')` vs Mobile 글작성/목록에 `canAccessBoard` import 0.
- **조치:** 칩·작성·수정·삭제에 board read/write 배선. write 없는 칩은 숨기거나 read-only.

#### [C-2] 모바일 공지·경조사 등록 시 notice-broadcast 미호출
- **증상:** 모바일에서 올린 공지/경조가 공지방·전직원 알림·푸시에 안 감.
- **근거:** PC `게시판.tsx` fetch `/api/board/notice-broadcast` · Mobile `createBoardPost` 종료 후 호출 없음.
- **조치:** create 성공 후 PC와 동일 조건으로 API 호출 (예약 미래는 skip).

#### [C-3] `board_posts` 전사 노출 (앱+정책)
- **증상:** 멀티테넌트 시 타사 글 조회·수정 가능(클라이언트 필터 없음 + PUBLIC_ALL).
- **근거:** fetch에 `company_id` eq 없음 · `policies.ts` `board_posts: PUBLIC_ALL` · comments/likes/reads/stars도 공개 계열.
- **조치:** (정책) 회사 스코프 또는 (앱) company_id 필터 + 서버 가드. 단일 병원이면 문서화로 수락 가능.

#### [C-4] 예약 공지 도래 시 자동 발행/방송 스케줄러 부재
- **증상:** 예약 시각 지나도 broadcast 안 됨. 목록 노출만 클라이언트 시계 의존.
- **근거:** notice-broadcast는 create 시 미래면 skip · worker cron 목록에 board publish 없음.
- **조치:** cron(또는 폴링 잡)으로 `scheduled_publish_at <= now` 이고 미방송 건 broadcast.

### 6.2 Major

#### [M-1] 수정/삭제 권한 PC≠Mobile
| | PC | Mobile |
|--|----|--------|
| 수정 | write + (작성자 **또는 부서장** position/mso/admin) | 작성자 또는 **isAdminUser/privileged** (부서장 position 약) |
| 삭제 | write + (작성자 또는 privileged) | 작성자 또는 canAdmin |
- 조치: 공통 권한 헬퍼로 통일 + board write 필수.

#### [M-2] 업무가이드 PC(GuideLibrary) ≠ Mobile(일반 글)
- PC: 메타 kind/team · 팀할일 보드. Mobile share: 일반 게시글 카드.
- 추가기능 허브와 board_type 문자열 혼재(`업무가이드`/`guide`/`업무공유`).

#### [M-3] 경조사·일정 작성 패리티
- 경조 PC 전용 폼 vs 모바일 일반 폼.
- 일정 PC 메타 content 임베드 + 비부서장 결재; 모바일 직접 update.

#### [M-4] 별표/즐겨찾기 이중 저장소
- PC: localStorage `mso:board:favorites`
- Mobile: `board_post_stars` (+ LS)
- 기기·플랫폼 간 불일치.

#### [M-5] PC `getCommentCount` 死
- `comments_count`/`comment_count` 스키마 없음 · PostTableView 정렬/표시 항상 0.
- 모바일은 집계로 정상.

#### [M-6] 읽음 audience·방송 대상 전사
- staff_members 전체 재직 · 회사 스코프 없음 (C-3 계열 UX).

#### [M-7] 목록 limit·성능
- PC 500 전체 재fetch + realtime 폴링.
- Mobile 타입당 1000 × 6 + 댓글 행 전량 카운트.
- 좋아요 1회 3 RT.

#### [M-8] 업로드 대용량 폴백 한계
- 직접 PUT 실패 시 50MB 초과 불가 · 동영상 경로 취약.

#### [M-9] 게시판.tsx 거대 단일 파일
- 유지보수·회귀 위험 (목록/작성/상세 분리 권장).

## 12. 결론

5차 기준 게시판은 **“보드 골격과 공통 정규화는 정리된 상태”**이나, **모바일은 여전히 ‘게시판 탭 사용자 = 전 보드 파워 유저’에 가깝고**, **공지 전파 파이프라인은 PC 전용**이다.  
DB는 `board_*`를 PUBLIC_ALL로 열어 두었으므로 **권한·회사 격리는 전부 앱 레이어 책임**이다.  
다음 스프린트는 **C-1~C-4 권한/방송/스케줄/격리**를 묶고, 이어서 **댓글수·별표·업무가이드 패리티**를 처리하는 것이 효율적이다.
