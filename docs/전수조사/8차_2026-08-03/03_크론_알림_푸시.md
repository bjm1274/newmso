### D02-012 · P0 · [7차 A1-03] absent-auto-create 크론 영구 미실행 — wrangler `[triggers]` 에 `'30 15 * * *'` 부재, 워커 매핑만 잔존

- **근본원인 축**: S6 크론·트리거 배선 파손 및 서버에서의 클라이언트 전용 모듈 오용
- **위치**: `wrangler.toml:43-49`, `cloudflare-worker.ts:83-84`, `lib/absent-auto-create.ts:263-267`
- **결함**: 현행 `wrangler.toml` 의 crons 는 `*/5 * * * *`, `0 15 * * *`, `0 17 * * *`, `0 3 * * *`, `0 0 * * *` 5개뿐이고 `'30 15 * * *'` 가 없다. 그런데 `cloudflare-worker.ts:83-84` 는 여전히 `// KST 00:30 매일 ...` 주석과 함께 `'30 15 * * *': ['/api/cron/absent-auto-create']` 매핑을 들고 있다. 워커의 `scheduled()` 는 `CRON_ROUTES_BY_SCHEDULE[controller.cron]`(`:318-319`)으로 라우트를 찾는 구조라 애초에 기동되지 않는다.
- **도달 경로**: **도달 불가.** Cloudflare 는 `[triggers]` 에 등록된 cron 표현식으로만 `scheduled()` 를 기동하므로 이 매핑은 영원히 실행되지 않는다. `runAbsentAutoCreate`(`lib/absent-auto-create.ts:263`)의 유일 호출자는 `app/api/cron/absent-auto-create/route.ts:27` 이며 수동 호출자는 grep 교차 확인 결과 0건이다.
- **영향**: 전날 무단결근·퇴근 미체크가 자동으로 기록되지 않아 근태 데이터 무결성이 훼손된다. 7차 A1-03 지적 이후 2개 커밋 사이클 동안 `wrangler.toml` 은 무변경이다.
- **검증**: V03 은 "저장소 밖 외부 스케줄러(cron-job.org·GitHub Actions)가 Bearer CRON_SECRET 으로 호출한다"는 반증 가설을 검토했으나 저장소 내 근거 0건으로 소진했다. V12 는 같은 사실을 확인하면서도 "데이터 손상·보안 영향이 없고 근태 수기 정정 경로(`attendance_corrections`)가 있다"며 P1 로 낮췄다. V13 재판정 결과 **도달률 0 + 기능 전면 불능**이라는 P0 기준에 해당해 P0 유지. 같은 결함을 D01-023·D08-022 가 각각 crossover 로 보고했고 본 항목으로 병합됐다.
- **수정 방향**: 무료플랜 5개 한도 내에서 `'0 15 * * *'`(KST 00:00 backup) 슬롯에 absent-auto-create 를 함께 매핑해 순차 실행하거나, 한도 상향 후 `'30 15 * * *'` 트리거를 복원한다. (난이도 S · 회귀위험 낮음 · 묶음 FB5)
- **주의**: 같은 기능에 대해 D03-001(크론이 서버에서 클라이언트 전용 `db-client` 의 상대경로 fetch 를 사용해 전면 불능)이 별건으로 존재한다. **트리거만 복원하면 기능은 여전히 살아나지 않는다** — 두 결함을 함께 고쳐야 한다.

### D02-002 · P1 · 미열람 재알림(repush)이 SQL `LIMIT 50` 을 적격성 필터 이전에 적용 — 미열람 채팅 알림이 창을 점유하면 중요 알림이 영구 굶주림

- **근본원인 축**: S6 크론·트리거 배선 파손 및 서버에서의 클라이언트 전용 모듈 오용
- **위치**: `lib/notification-repush.ts:176-189`, `lib/notification-repush.ts:251-282`
- **결함**: 조회 쿼리의 WHERE 절은 `read_at IS NULL` + 12h~7d 창 조건뿐이고 **타입 조건이 없다**. 그 상태로 `orderBy(asc(created_at)).limit(50)`(`:189`)을 걸어 50행을 뜯어온 뒤, 채팅 제외·적격 타입 판정을 JS 루프에서 수행한다 — `:253-256` `if (isChatNotification(row)) { skipped += 1; continue; }`. 적격 타입 Set(`:46`)은 SQL 에 전혀 반영되지 않는다.
- **도달 경로**: `'0 0 * * *'`(KST 09:00) → `/api/cron/unread-notification-repush` → `processUnreadNotificationRepushServer()`. 라우트(`app/api/cron/unread-notification-repush/route.ts:20`)가 인자 없이 호출하므로 `limit=50`, `userIds=null` — **사용자별이 아니라 전사 전역 50행 창**이다. 매일 실행되는 유일 경로다.
- **영향**: 앱을 안 여는 사용자일수록(=재알림이 가장 필요한 대상) 미열람 채팅 알림이 쌓이고, `lib/chat-push-dispatch.ts:844-885` 가 메시지 1건당 수신자 1행씩 `notifications` 를 INSERT 하므로 누적 속도가 빠르다. skip 된 채팅 행은 metadata 패치도 없이 그대로 남아 최대 7일간 매일 같은 창을 재점유하고, 그 뒤의 approval·notice 재알림은 그날 발송되지 않는다.
- **검증**: V03 이 제시된 반증 두 가지를 모두 소진했다. (1) "방 열람 시 채팅 알림이 일괄 read 처리된다" → `app/main/모바일/채팅/data-hooks.ts:629` 는 **해당 방에 대해 최대 50건만** 읽음 처리하고, 미접속 사용자는 아예 실행되지 않는다. (2) "창 내 총량이 50 미만" → 보존 크론(`app/api/cron/push-subscription-cleanup/route.ts:85-92`)은 `read_at IS NOT NULL` 인 행만 삭제하므로 미열람분은 줄지 않는다. 구조적 결함(필터가 LIMIT 뒤)은 코드만으로 확정.
- **수정 방향**: WHERE 에 `type IN (적격타입) OR metadata room_id=공지방` 조건을 내려 SQL 단계에서 필터하거나, LIMIT 을 타입 필터 후 적용하는 2단 조회로 변경한다. (난이도 S · 회귀위험 낮음 · 묶음 FB5)

### D02-004 · P1 · WebPush TTL 60초 — 기기가 1분만 오프라인이어도 푸시가 폐기, 재알림은 시도 1회 제한이라 영구 미도달

- **근본원인 축**: S6 크론·트리거 배선 파손 및 서버에서의 클라이언트 전용 모듈 오용
- **위치**: `lib/web-push-cloudflare.ts:201-210`, `lib/notification-repush.ts:95-97`
- **결함**: 모든 WebPush 발송이 `TTL: '60'`(`lib/web-push-cloudflare.ts:208`, `Urgency:'high'` 와 함께) 고정이며 호출부에서 주입할 파라미터가 없다. 절전·네트워크 단절 상태의 브라우저가 60초 안에 재접속하지 않으면 푸시서비스가 메시지를 버리는데, 발송측은 2xx 성공으로 관측한다. 여기에 재알림 쪽은 `lib/notification-repush.ts:97` `const DEFAULT_MAX_ATTEMPTS = 1;` 이고 `:341-348` 이 **발송 성공 여부와 무관하게** `repush_attempt_count` 를 +1 패치하므로 2차 시도가 불가능하다.
- **도달 경로**: `sendWebPushNotification` 을 거치는 모든 WebPush 발송에서 상시 실행. 특히 KST 09:00 재알림 시 절전 중인 PC 구독이 정확히 이 조합에 걸린다.
- **영향**: 채팅은 인앱 폴백이 있으나, 미열람 중요 알림 재발송은 "최후 안전망"인데 TTL 60초 + 시도 1회 + 실패해도 카운트 증가라 야간 절전 후 아침을 맞은 PC 는 그 알림 푸시를 **영구히** 받지 못한다.
- **검증**: V03·V12 가 독립적으로 CONFIRMED/P1. 반증 가설("짧은 TTL 이 뒤늦은 알림 억제 의도로 문서화됨")을 뒷받침할 주석·문서를 저장소에서 찾지 못했다. 오히려 FCM 경로(`lib/fcm-http.ts:140-152`)는 `ttl` 키가 아예 없어(기본 4주) **채널 간 정책이 실제로 어긋난다**는 반대 증거가 나왔다. V12 는 "실제 폐기율은 푸시서비스 런타임 동작이라 영향 크기는 미확정"이라는 단서를 달았다.
- **수정 방향**: 용도별 TTL 파라미터화 — 채팅 즉시 푸시는 수분~1h, 중요 알림 재발송은 24h 이상으로 상향한다. (난이도 S · 회귀위험 낮음 · 묶음 FB5)

### D02-001 · P1 · 인앱 보강 잡 3종(근태·급여·금지어)의 26h lookback 이 `created_at` 형식 혼재로 무력화 — 하루 중 KST 09:00~12:00 발생분만 스캔됨

- **근본원인 축**: S7 시각 표현 이중화 — created_at 형식 혼재 + UTC/KST 경계 오독
- **위치**: `lib/inapp-notification-jobs/check-attendance.ts:69-83`, `lib/inapp-notification-jobs/check-payroll.ts:33-45`, `lib/inapp-notification-jobs/check-word-filter.ts:85-104`, `app/api/d1/mutate/route.ts:42-53`
- **결함**: 세 잡 모두 cutoff 를 ISO 로 만든다 — `check-attendance.ts:69` `const cutoff = new Date(Date.now() - ATTENDANCE_LOOKBACK_MIN * 60 * 1000).toISOString();` — 그리고 `:82` `gte(attendanceTable.created_at, cutoff)` 로 **문자열 사전순 비교**를 한다. 그런데 대상 세 테이블의 `created_at` 은 `TEXT DEFAULT CURRENT_TIMESTAMP`(공백형식 `'YYYY-MM-DD HH:MM:SS'`)이고, 지배적 write 경로가 `created_at` 을 아예 넣지 않아 DEFAULT 가 들어간다 — `app/main/모바일/내정보/출퇴근체크인.tsx:331` payload 는 `{staff_id, date, check_in, status}` 뿐, `lib/payroll-record-upsert.ts` 도 미설정, `app/main/기능부품/메신저유틸.ts:347-358` `buildChatMessageInsertPayload` 도 미설정. `' '`(0x20) < `'T'`(0x54) 이므로 cutoff 와 같은 달력일(=어제)의 공백형식 행은 전부 cutoff 보다 작다고 판정돼 제외된다. mutate 관문의 형식 보정(`app/api/d1/mutate/route.ts:49` `if (table !== 'notifications') return row;`)은 `notifications` 에만 적용된다.
- **도달 경로**: wrangler `'0 3 * * *'` → `app/api/cron/push-subscription-cleanup/route.ts:273` `runInappNotificationJobs()` piggyback 으로 매일 UTC 03:00(KST 12:00) 1회 실행. 이때 cutoff 는 `'(D-1)T01:00Z'` 이므로 공백형식 행은 날짜부가 D 이상인 것만 통과 → **실제 스캔 창은 UTC 00:00~03:00, 즉 KST 09:00~12:00 3시간**이다. 각 파일 상단 주석의 "lookback: 일 1회 piggyback 누락 방지용 26시간" 의도와 실동작이 정면으로 어긋난다.
- **영향**: KST 09:00 이전 출근 기록, 12:00 이후 급여 확정, 하루 약 21시간분 메시지 금지어가 어느 실행에서도 알림을 만들지 못한다. Phase 8-A 가 복원하려던 알림 3종이 사실상 1/8 만 동작한다.
- **검증**: V03 이 반증 조건("3개 테이블이 전량 ISO 로 백필됐고 모든 write 가 ISO 를 명시")을 `local-d1-schema.json` 과 write 경로 실측으로 소진했다. 다만 `lib/server-approval-processing.ts:390,494` 처럼 ISO 를 **명시하는** 근태 write 는 정상 스캔되므로 "전면 불능"이 아니라 경로별 부분 누락 → P1 유지.

### D02-003 · P1 · 일일 백업이 테이블 일부 실패(skipped)여도 `ok:true` · `cron_success` 로 보고 — 특정 테이블 영구 미백업을 아무도 모름

- **근본원인 축**: S10 실패의 조용한 성공 보고 — 백업·복원·감사로그·오프라인 큐
- **위치**: `lib/backup-cron.ts:181-186`, `lib/backup-cron.ts:237-284`
- **결함**: 테이블별 덤프 실패는 `catch (e) { console.warn(...); skipped.push(...); }`(`:181-185`)로 삼켜지고 루프가 계속된다. 실패 판정은 `if (files.length === 0)`(`:238`) 전멸 케이스뿐이고, 1개 이상 성공하면 `:262-269` 가 `ok: true` / `status: 'completed'` 를 반환한다. 워커는 `cloudflare-worker.ts:255-260` `if (!response.ok) throw` 구조라 HTTP 200 을 받으면 `cron_success` 를 기록하고 관리자 실패 알림(`notifyCronFailure`) 경로를 타지 않는다.
- **도달 경로**: `'0 15 * * *'`(KST 00:00) → `/api/cron/backup` → `runBackup('24h')` 로 매일 실행. 스키마 변경 등으로 특정 테이블만 실패하면 이 분기를 그대로 밟는다.
- **영향**: 부분 실패가 **모든** 관측 지표에서 성공으로 보인다 — HTTP 200, `cron_success`, `status: completed`, 관리자 UI. 특정 테이블이 매일 백업에서 빠져도 재해복구를 시도하는 시점에야 발견된다.
- **검증**: V03 이 반증 두 가지를 모두 소진했다. `skipped` 는 `result_summary`/manifest 에 실리기는 하지만, 관리자 백업 화면(`app/main/기능부품/관리자전용서브/데이터백업.tsx:762-766`)은 `result_summary.failed_tables` 와 rollback 항목만 렌더링하고 **`skipped` 를 표시하는 코드가 없다**. 라우트도 `skipped>0` 에 대해 5xx·부분실패 status 를 반환하지 않는다.
- **수정 방향**: `skipped.length > 0` 이면 `status:'failed'`(또는 `'partial'`) + `ok:false` 로 반환해 워커의 `notifyCronFailure` 경로를 태운다. (난이도 M · 회귀위험 중 · 묶음 FB9)
- **연관**: 같은 축의 D08-003(전체 백업이 162개 테이블 중 52개만 담음, P0)·D08-004(복원이 100행 초과 테이블에서 100% 실패, P0)와 합쳐 보면 **재해복구 경로 자체가 성립하지 않는다**. 세 건은 같은 묶음 FB9 로 함께 다뤄야 한다.
