## 연차 SSOT 단절 구조 — 원장 vs 미러 이중 진실 (S8)

개별 항목을 읽기 전에 이 그림을 먼저 잡아야 한다. 이 도메인 P0·P1 의 절반이 아래 한 장의 결과다.


이 구조에서 실제로 벌어지는 일을 순서대로 쓰면 이렇다.

1. **원장에 `expire` 를 쓰는 코드가 저장소 전체에 없다.** `LEAVE_LEDGER_ENTRY_TYPE.EXPIRE` 는 `unified-leave-ledger.ts:32` 정의와 `:347` 집계 case 에만 등장한다. 소멸 처리는 `leave_balances` 만 갱신한다.
2. 그런데 요약 API 는 호출될 때마다 원장을 다시 집계해 `leave_balances` 를 `onConflictDoUpdate` 로 덮어쓴다. 원장에 `expire` 항목이 없으므로 `expired_days` 는 다시 0 이 되고 **소멸시킨 연차가 부활한다.**
3. 소멸 대상 포착도 막혀 있다. `leave_balances.expiry_date` 를 채우는 유일한 코드는 신규 직원 등록(`lib/db/functions/staff.ts:255-262`)뿐이라 2년차 이후 주기 행은 NULL 이고, `lte(expiry_date, today)` 조건에 영원히 걸리지 않는다.
4. 촉진 크론은 원장이 아니라 미러 A(`annual_leave_total/used`)를 읽는다. 미러 A 는 "직원이 자기 화면을 열었을 때"만 갱신되므로, 화면을 안 여는 직원의 값은 낡은 채로 남아 촉진이 누락되거나 잘못 발송된다.
5. 그 미러 A 를 관리자 sync 라우트가 `year` 인자로 재계산할 때 `asOf` 를 `YYYY-12-31` 로 잡는다. 입사기념일이 오늘 이후·연말 이전인 직원은 그 시점 기준으로 **아직 시작하지 않은 다음 주기**가 잡혀 집계값이 0 에 가까워지고, 그 0 이 미러를 덮는다.
6. PC 워크센터는 역년, 개인·모바일은 입사일 주기로 집계한다. 원장 직접 조회 폴백을 넣어 두긴 했으나 `leave_ledger` 가 `POLICY_REGISTRY` 에 등록돼 있지 않아 `/api/d1/query` 가 403 을 돌려주고, 그 폴백 분기는 처음부터 죽어 있었다.

즉 **"원장이 진실이다"라는 전제로 쓴 읽기 경로와, "미러가 진실이다"라는 전제로 쓴 쓰기 경로가 서로를 계속 덮어쓰고 있다.** FB7(연차 SSOT 통일)이 난이도 L·회귀위험 높음인 이유가 여기 있고, 선행조건으로 FB2(leave_ledger 정책 등록)와 FB4(부재 컬럼 정리)가 붙는 이유도 같다.

## 지적사항

### D03-D09 · P0 · [7차 A7-04] 징계·평가 PUBLIC_ALL — 징계는 닫힘, 평가는 select/insert AUTHENTICATED 로 열람·작성 잔존

- **근본원인 축**: S2 정책 레지스트리 과다개방(PUBLIC/AUTHENTICATED) — 소유권·회사 스코프 미검사
- **위치**: `lib/db/auth/policies.ts:506-532`
- **결함**: 7차에 지적된 두 테이블 중 `disciplinary_committees` 는 `select STAFF_IN_SCOPE` · 쓰기 `ADMIN_OR_MANAGER` 로 정상적으로 좁혀졌다(`:525-532`). 그러나 `staff_evaluations` 는 `update`/`delete` 만 `ADMIN_ONLY` 로 바뀌었을 뿐 `select`·`insert` 가 `'AUTHENTICATED'` 그대로 남아 있다(`:510-516`). 정책 파일의 주석(`:506-509`) 자체가 "extra_직원평가 게이팅은 화면(클라) 기준"이라고 인정하고 있다. `filterByPolicy` 의 AUTHENTICATED 분기는 `erpStaffId` 만 있으면 rows 를 그대로 반환해 행 단위 필터가 **전혀 없다**(`:1863-1866`).
- **도달 경로**: 로그인한 임의 직원이 `POST /api/d1/query {table:'staff_evaluations'}` 로 전 직원 인사평가를 열람하고, `POST /api/d1/mutate` insert 로 임의 평가 행을 생성할 수 있다.
- **영향**: 타인의 인사평가 내용(content)·점수(score) 전량 유출 + 위조 평가 작성. 권한 경계를 넘는 실도달 가능 유출이다.
- **검증**: V04·V11 이 독립적으로 CONFIRMED/P0. 반증조건("평가 테이블이 비어 있거나 STAFF 배치 필터가 select 에 적용된다면")을 검사했으나 `staff_evaluations` 는 실 테이블(로컬 D1 7컬럼)로 존재하며 `content`/`score` 를 담고, AUTHENTICATED 패턴에는 행 필터가 정의상 없다. 델타 판정 PARTIAL — 징계는 CLOSED, 평가는 OPEN.
- **수정 방향**: `select` 를 `STAFF_IN_SCOPE(staff_id)` 로, `insert` 를 평가자 권한 가드로 승격 (난이도 M · 회귀위험 높음 · 묶음 FB2). 선행: FB3(세션 권한 복원) — 압축된 권한 상태로 재분류하면 오차단이 생긴다.

### D03-027 · P0 · 내정보(ESS) 변경 신규 라우트의 payload 계약 불일치 — 클라는 객체, 서버는 문자열만 수용 → 상시 400

- **근본원인 축**: S5 스키마 드리프트 — 실 D1 에 없는 컬럼·테이블을 코드가 참조
- **위치**: `lib/profile-change-request.ts:106-128`, `app/api/profile-change-request/route.ts:44-48`
- **결함**: 7차 A2-01(내정보 저장이 `audit_logs` ADMIN_ONLY 로 항상 403) 을 고치려고 전용 서버 라우트를 신설했는데, 양쪽의 타입 계약이 어긋났다. 클라이언트는 `details` 를 **객체**로 만들어 보낸다 — `const details = { requested_changes: ..., original_data: {...} }` (`:106-115`) → `body: JSON.stringify({ details })` (`:124`). 서버는 `const details = typeof body?.details === 'string' ? body.details : '';` 로 받고(`route.ts:45`) 빈 문자열이면 400 `'details 가 필요합니다.'` 를 반환한다(`:46-48`).
- **도달 경로**: PC `app/main/기능부품/마이페이지/프로필카드.tsx:176` 과 모바일 `app/main/모바일/내정보/정보수정.tsx:253` — 일반 직원의 '내 정보 저장' 버튼 **양 경로 모두**.
- **영향**: 일반 직원의 본인 정보 변경 요청 접수가 100% 실패. 7차 대비 실패 코드만 403 → 400 으로 바뀌었을 뿐 기능 체감은 동일하다.
- **검증**: V04 가 중간 문자열화 경로를 추적했으나 `submitProfileChangeRequest` 가 유일한 호출부이고 fetch 직전 변환도, 객체를 문자열로 바꾸는 미들웨어도 없다. 라우트의 세션·권한 검사(`:32-42`) 자체는 실제로 추가돼 구조 교정은 이뤄졌으므로 델타 판정은 PARTIAL.
- **수정 방향**: 서버에서 객체를 수용해 `JSON.stringify` 후 저장(또는 클라에서 문자열화) — **실질 한 줄 수정** (난이도 L(묶음 기준) · 회귀위험 중 · 묶음 FB4). 영향은 P0 이지만 수정 자체는 이 도메인에서 가장 싸다.

### D03-001 · P0 · absent-auto-create 크론이 서버에서 클라이언트 전용 db-client(상대경로 fetch)를 사용해 전면 불능

- **근본원인 축**: S6 크론·트리거 배선 파손 및 서버에서의 클라이언트 전용 모듈 오용
- **위치**: `lib/absent-auto-create.ts:38-58`, `lib/d1-compat/query-builder.ts:17-21`, `app/api/cron/absent-auto-create/route.ts:27`
- **결함**: `runAbsentAutoCreate` 는 Workers 런타임(서버)에서 호출되는데 내부에서 `fetch('/api/d1/query', { credentials:'same-origin' })` 같은 **상대 URL** 을 쓴다(`absent-auto-create.ts:40`). insert/update 도 `import { db } from '@/lib/db-client'`(`:17`)를 거쳐 `query-builder.ts:17` 의 상대 URL fetch 로 흐른다. 서버 런타임에서 상대 URL fetch 는 즉시 실패하고, 설령 절대화되더라도 세션 쿠키가 없어 401 이다.
- **도달 경로**: `cloudflare-worker.ts:84` 는 `'30 15 * * *'` 에 이 라우트를 매핑하지만 **`wrangler.toml [triggers] crons` 에 `'30 15 * * *'` 슬롯 자체가 없다.** 따라서 `scheduled()` 가 이 cron 으로 호출되지 않아 자동 실행 0회이고, 수동 GET(Bearer CRON_SECRET) 시에만 실행돼 즉시 실패한다.
- **영향**: 결근 자동 생성·퇴근 미체크 자동 처리가 배포 이후 **단 한 건도 동작한 적이 없다.** 결근 행이 생성되지 않아 급여 결근 공제가 전면 누락되고(조용한 급여 과지급), 근태 기록이 성기게 남아 D03-015 의 과대 공제 위험을 동시에 키운다.
- **검증**: V04 가 상대 URL 폴리필 존재 여부를 전역 grep 으로 확인(`globalThis.fetch`/`global.fetch` 대입 0건). 더 결정적으로 `/api/d1/query` 는 `{sql, params}` 형태를 아예 받지 않는다(PayloadSchema 는 `table` 필수) — 절대 URL 이어도 400 Invalid payload 로 죽는다. CRON 우회 경로도 없다(`route.ts:23` Bearer 검사만). 코드 결함과 트리거 미등록이 **이중으로** 성립해 "전면 불능" 결론은 어느 쪽으로도 무너지지 않는다.
- **수정 방향**: `runAbsentAutoCreate` 를 `getD1Binding()` + drizzle 직접 쿼리로 재작성하거나, `queryD1`/db-client 호출을 서버 전용 D1 헬퍼로 교체 (난이도 S · 회귀위험 낮음 · 묶음 FB5). 선행: `wrangler.toml [triggers]` 에 슬롯 추가 + 재배포. **크론 배선(D02-012)과 이 코드 결함은 별건이며 둘 다 고쳐야 기능이 산다.**

### D03-003 · P0 · 연차 소멸 처리가 SSOT(leave_ledger)와 단절 — expire 원장 미기록 + summary 동기화가 소멸 결과를 되돌림

- **근본원인 축**: S8 연차 SSOT 단절 — leave_ledger 원장 vs staff_members 미러 이중 진실
- **위치**: `lib/annual-leave-expiry.ts:49-61`, `lib/unified-leave-ledger.ts:365-398`, `lib/annual-leave-expiry.ts:156-171`
