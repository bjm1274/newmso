## 요약

관리자·감사·백업 28건 중 25건 CONFIRMED, 3건 REFUTED 다. 이 도메인의 P0 3건은 성격이 둘로 갈린다. **운영 위험이 압도적으로 큰 쪽은 백업·복원 2건**이다 — '전체 백업' 이 스키마 162개 테이블 중 52개만 담아 연차 원장(`leave_ledger`)·급여 원본(`payroll`)·인사발령 등 110개가 어떤 백업에도 존재하지 않고, 유일한 복원 수단은 배치 크기 200 vs 서버 상한 100 의 불일치로 100행을 넘는 테이블에서 100% 실패한다. 즉 **백업에 없는 데이터가 절반 이상이고, 있는 데이터도 되돌릴 수 없다 — 재해복구 경로 자체가 존재하지 않는다.** 나머지 P0 는 권한 경계 결함으로, 일반 관리자가 시스템마스터(9999) 계정의 비밀번호를 덮어쓰고 그 계정으로 로그인해 시스템마스터 전용 API 전체를 열 수 있다. P1 계열은 감사 추적의 구조적 무효화에 집중된다 — 가장 파괴적인 '전 직원 삭제' 는 무기록으로 실행되면서 오히려 `audit_logs` 를 지우고, 감사 actor 는 브라우저 localStorage 값이며, `access_logs` 에 INSERT 하는 코드는 저장소 전체에 0건이라 '접근 감사 로그' 화면과 KPI 가 영구히 0 이다. 7차 델타는 A10-01/02/03 이 전부 **OPEN**(미수정), A11-01/02 는 **CLOSED**(실제로 수정 확인)로 갈렸다.

### D08-004 · P0 · 백업 복원이 100행 초과 테이블에서 전부 실패한다 (배치 200 vs 서버 상한 100)

- **근본원인 축**: S10 실패의 조용한 성공 보고
- **위치**: `app/main/기능부품/관리자전용서브/데이터백업.tsx:13-14`, `app/main/기능부품/관리자전용서브/데이터백업.tsx:481-512`, `app/api/d1/mutate/route.ts:173-195`
- **결함**: 복원 화면은 `const RESTORE_BATCH_SIZE = 200;`(`:14`) 로 자르고 `for (const batch of chunkRows(rows, RESTORE_BATCH_SIZE)) { const { error } = await db.from(table).upsert(batch as any[]); … if (error) { failed = true; … break; } }`(`:489-494`) 를 호출한다. 이 upsert 는 `InsertBuilder` → `POST /api/d1/mutate` 로 가는데, 서버 스키마는 `const MAX_ROWS_PER_INSERT = 100;`(`route.ts:173`) 이고 `values: z.array(...).min(1).max(MAX_ROWS_PER_INSERT)`(`:190`) 다. 따라서 200행 배치는 zod 검증에서 **항상** 400 `'Invalid payload'` 로 거부된다(`:404-409`).
- **도달 경로**: 관리자 → 데이터백업 화면 → 복원 실행 → 100행을 초과하는 테이블마다 **첫 배치에서** 400 → `break` → `failedTables` 에 기록. 100행 이하 테이블만 반영되어 '일부만 복원된' 중간 상태가 남는다.
- **영향**: 관리자 화면의 유일한 복원 수단이 의미 있는 규모의 테이블에서 100% 실패한다. D08-003 과 합쳐 보면 **백업 대상이 절반 미만이고 그 절반마저 되돌릴 수 없다** — 재해복구 경로가 사실상 없다.
- **검증**: V02·V12 가 "db-client 가 100행 단위로 재분할할 것" 이라는 반증조건을 시도해 불성립. `lib/db-client.ts:82-99` 의 upsert 는 values 배열을 그대로 `InsertBuilder` 로 넘기고, `lib/d1-compat/mutation-builders.ts:69-81` 의 `then()` 도 `values: rest.values` 를 그대로 body 에 싣는다 — 어디에도 분할이 없다. 서버 측 재분할(`mutate/route.ts:458` `maxRowsPerChunk`)은 zod 검증 **뒤**에 일어나므로 200행은 그 전에 400 으로 떨어진다. V02=P1 / V12=P0 로 심각도가 충돌했고, V13 이 "D08-003 과 합쳐 재해복구 경로 자체가 없음 = 기능 전면 불능" 을 근거로 **P0** 로 재판정했다.
- **수정 방향**: `RESTORE_BATCH_SIZE` 를 100 이하로 낮추거나 `db-client.upsert` 가 100행 단위로 자동 분할하도록 수정한다. 실패 시 부분 복원 상태를 화면에 명시한다. (난이도 S · 회귀위험 중 · 묶음 FB9 · 선행 없음)

### D08-002 · P0 · 일반 관리자가 시스템마스터 계정 비밀번호를 덮어쓸 수 있다

- **근본원인 축**: S11 클라이언트 신뢰 경계 붕괴 — 계산·검증·PII 보호를 브라우저가 수행
- **위치**: `app/api/admin/staff-password/route.ts:42-126`, `lib/system-master.ts:11-32`
- **병합**: D08-001(관리자의 자기 권한 상향)
- **결함**: `staff-password` 라우트는 `if (!session || !isAdminSession(session.user)) { return … 401 }` 만 확인하고, `const staffId = String(body?.staffId ?? '').trim();` 이후 **대상 행이 시스템마스터인지 전혀 검사하지 않은 채** `updateStaffPasswordWithFallback(staffId, password)` 를 호출한다. 최소 길이도 4자리다. 한편 `isNamedSystemMasterAccount`(`system-master.ts:11-32`)는 `employee_no === '9999'` + system_master 권한만 보므로, 9999 행의 비밀번호를 아는 사람은 곧 시스템마스터다.
- **도달 경로**: `permissions.admin` 만 가진 세션 → `POST /api/admin/staff-password` 로 9999 행 비밀번호를 재설정 → 그 계정으로 로그인 → `isNamedSystemMasterAccount` 통과 → 시스템마스터센터·연차수동부여·백업복구·채팅 전수열람 등 전 API 개방.
- **영향**: '일반 관리자' 와 '시스템마스터' 의 권한 위임 경계가 실제로 넘어간다. 화면상 '시스템마스터 전용' 으로 표시된 모든 기능이 일반 관리자에게 열린다.
- **검증**: 반증조건 2개 모두 불성립. (1) 9999 계정은 실재 운영 개념이다 — `시스템마스터센터.tsx:579`, `연차수동부여.tsx:255` 가 "9999 계정으로 로그인한 경우에만" 이라고 화면에 안내한다. (2) 로그인 라우트는 `employee_no` 로 `staff_members` 행을 찾아 그 행의 저장 비밀번호로 검증하므로(`master-login/route.ts:234-236,323-368`) `staff_members.password` 를 무시하지 않는다. 추가 확인: `local-d1-schema.json` 상 `staff_members` 에 `employee_no` UNIQUE 인덱스가 없어, 9999 행이 없더라도 관리자가 `/api/d1/mutate` 로 `employee_no='9999'` + `permissions.system_master` 행을 새로 만들 수 있다. 병합된 D08-001(자기 권한 상향)은 `permissions.system_master` 를 스스로 켜도 서버 라우트가 전부 `isNamedSystemMasterAccount` 를 추가 요구하므로 권한 델타가 0 — P0 → P2 로 강등하고 실제 경계 우회는 이 항목으로 집계했다.
- **수정 방향**: 대상 행의 `is_system_master`/`employee_no` 를 조회해 시스템마스터 계정 대상 변경은 `isNamedSystemMasterAccount` 세션에서만 허용한다. 부여 가능한 permission 키도 화이트리스트로 제한하고 자기 자신 대상 권한 상향은 금지한다. (난이도 S · 회귀위험 높음 · 묶음 FB10 · 선행 FB3·FB1)

### D08-007 · P1 · 비관리자(인사 권한자)의 감사 기록이 403 으로 조용히 전부 유실된다

- **근본원인 축**: S3 정책 레지스트리 누락·과소개방 → 권한 보유자에게 조용한 기능 사멸
- **위치**: `lib/audit.ts:151-168`, `lib/d1-api-helpers.ts:79-95`, `lib/db/auth/policies.ts:1427-1439`
- **결함**: `logAudit` 의 클라이언트 경로는 `db.from('audit_logs').insert` 로 `/api/d1/mutate` 를 타는데 `audit_logs` 정책은 `ADMIN_ONLY_ALL` 이고 `erp_is_admin`(`d1-api-helpers.ts:88`)에는 `perms.hr` 이 없다. 반면 `erp_can_manage_company`(`:89`)에는 hr 이 포함된다 — 즉 **hr 권한자는 `staff_members` 수정은 되는데 그 사실을 감사에 남기는 것만 403** 이 되는 비대칭이다. 실패는 `if (error) { console.warn('[audit_logs] logAudit (client):', error.message); } return;`(`:164-167`) 로 삼켜진다.
- **도달 경로**: `permissions.hr` 만 가진 인사담당자가 구성원현황에서 직원을 수정 → `logAudit` → mutate insert → PolicyDenied 403 → console.warn 후 무시.
- **영향**: 감사로그가 '관리자 계정으로 한 일' 만 담게 되어 인사 데이터 변경 이력이 비어 있고, 이상 감지(`detectAnomalies`)도 그만큼 눈이 먼다. 화면에는 실패가 전혀 드러나지 않는다.
- **검증**: `logAudit` 호출부 12개가 전부 클라이언트 `.tsx`(구성원현황·급여정산·오프보딩·인사발령관리·휴가관리메인·LeaveWorkcenter·StaffDrawer·중간정산·직원권한통합·발령탭·연차관리자)이고, 같은 이벤트를 서버에서 중복 기록하는 라우트가 없음을 확인했다.

- **도달 경로**: 전날 미출근 직원의 결근 자동 생성이 배포 이후 한 번도 실행되지 않았다.
- **영향**: 결근 자동 생성 누락 → 근태 데이터 결손이 누적된다. D08-014 의 `todo-reminders` 미등록과 같은 근본원인(크론 목록 3중 관리: wrangler / worker 매핑 / 운영 패널 하드코딩).
- **검증**: 코드 밖 대시보드 트리거 가능성은 저장소에서 검증 불가하나, `cloudflare-worker.ts:60-61` 주석이 "wrangler.toml `[triggers]` crons 와 정확히 일치해야 한다" 고 명시하고 실제로 불일치하므로 **내부 모순으로 확정**된다. 또한 `wrangler deploy` 는 `wrangler.toml` 의 crons 로 트리거 집합을 치환하므로 대시보드에서 수동 추가한 슬롯은 배포 시 사라진다. 크론 도메인(D02-012)과 결론이 일치했다.
- **수정 방향**: `wrangler.toml` crons 에 슬롯을 추가하고 재배포한다. (난이도 S · 회귀위험 낮음 · 묶음 FB5)
