## 요약

이 저장소의 시각 결함은 **두 개의 축이 겹쳐서** 생긴다. 하나는 `created_at` 계열 TEXT 컬럼에 공백형(`YYYY-MM-DD HH:MM:SS`, UTC)과 ISO(`...T...Z`)가 섞여 들어가는 **형식 혼재**이고, 다른 하나는 서버 TZ 가 UTC 인데 사용자 기준이 KST 라서 생기는 **9시간 경계 오독**이다. 둘이 만나면 단순한 표시 오차가 아니라 **비교 연산 자체가 뒤집힌다** — TEXT 사전순에서 `' '(0x20) < 'T'(0x54)` 이므로 같은 UTC 날짜의 공백형 행은 ISO 행보다 항상 작고, 그 결과 `ORDER BY created_at DESC LIMIT 1` 기반 변경감지가 하루 종일 고착되거나(D10-001) `gte/lt` 날짜 창이 통째로 UTC 로 밀린다(D10-005). 이번 라운드에서 확정된 실피해 중 가장 무거운 것은 **결재 위임 만료가 매일 KST 00:00~08:59 동안 9시간 연장되는 인가 경계 오류**(D10-003)와 **KST 새벽 기안 문서의 문서번호가 중복 발급될 수 있는 채번 창 왜곡**(D10-005)이다. 뿌리에는 공백형 문자열을 UTC(+00:00)/KST(+09:00)/로컬(무접미) 세 가지로 제각각 해석하는 파서 3계열(D10-009)과 규약 없는 날짜 유틸 4종(D10-011)이 있어, 개별 사이트만 고치면 같은 결함이 계속 재생산된다. 실제로 과거 커밋 `0d848382`·`ba80925a`·`c4acdf71` 이 고친 것과 **동일 클래스의 잔존 사이트**가 이번에 4건 새로 발견됐다.

### D10-014 · P1 · [crossover] OP체크 병동 메시지 insert 가 `.select()` 없이 실행 — mutate 후처리가 통째로 스킵

- **근본원인 축**: S1 D1 API 게이트웨이의 판정 != 실행 · fail-open
- **위치**: `app/main/기능부품/OP체크.tsx:1851-1852`
- **결함**: `messages` insert 의 후처리(방 미리보기 갱신·`chat_push_jobs` 적재·즉시 디스패치)는 `app/api/d1/mutate/route.ts:516` 의 `if (payload.table === 'messages' && allResults.length > 0)` 가드 뒤에 있다. `allResults` 는 RETURNING 결과인데, `d1-compat` 은 `.select()` 를 호출했을 때만 `returning` 을 설정한다(`mutation-builders.ts:54,154,175-176`). OP체크는 `.from('messages').insert({...})` 만 하고 `.select()` 가 없으므로 RETURNING 이 비고 후처리 블록 전체가 건너뛰어진다.
- **도달 경로**: OP체크 병동 메시지 일괄 전송 시 **매번**.
- **영향**: 방 목록 미리보기·`last_message` 가 갱신되지 않는 데서 그치지 않고 **푸시 알림 자체가 나가지 않는다**. 수신자는 병동 메시지가 도착한 사실을 인지하지 못한다.
- **검증**: 반증조건은 "d1-compat 이 insert 에 기본 returning 을 붙이는가" 였다. `mutation-builders.ts:175-176` 은 `this.state.returning` 이 있고 길이가 0 이 아닐 때만 `body.returning` 을 부착하며, 같은 라우트의 `:609` 주석이 "`.select()` 없이 `.insert()` 만 하므로 RETURNING 이 비어" 라고 동일 현상을 이미 문서화하고 있다 → 반증 실패. 메신저 도메인 소관이라 crossover 로 기록하되 영향이 푸시 미발송까지 미쳐 **P1 유지**.
- **수정 방향**: 메신저 도메인에서 `.select('id, room_id, created_at')` 을 부여. (난이도 S · 회귀위험 높음 · 묶음 FB1 D1 게이트웨이 하드닝, 선행 FB13 권장)

### D10-001 · P1 · 생일·연차공지 크론이 messages/chat_rooms 에 ISO `created_at` 을 삽입 — 그 UTC 날짜 내내 사전순 max 동결

- **근본원인 축**: S7 시각 표현 이중화 — created_at 형식 혼재 + UTC/KST 경계 오독
- **위치**: `lib/birthday-announcements.ts:99,134-165,214-244`, `lib/leave-notice-cron.ts:213,239-269`, `app/api/realtime/tail/route.ts:41-79`, `lib/realtime/allowed-tables.ts:51-55`
- **결함**: 두 크론이 "항상 KST 09:00 으로 표시" 하려고 ISO 리터럴을 만들어 넣는다.
  ```ts
  // lib/birthday-announcements.ts:98-99
  // 항상 KST 오전 09:00 (UTC 00:00)을 메시지 발송 시간으로 고정하여 지연 시에도 09:00으로 표시되게 함
  const nowIso = `${kstDateStr}T00:00:00.000Z`;
  ```
  이 값이 `messages.created_at`(`:140`, `:220`)과 `chat_rooms.last_message_at`(`:157`, `:236`)에 그대로 들어가고, `leave-notice-cron.ts:213` 도 `${targetDate}T00:00:00.000Z` 를 messages(`:245`)와 `updateChatRoomLastMessage`(`:268`)에 넣는다. 그런데 `messages.created_at` 은 전 행이 SQLite `CURRENT_TIMESTAMP` 공백형이라는 것이 `app/api/d1/mutate/route.ts:42-45` 주석에 명시된 불변식이고, `/api/realtime/tail` 은 컬럼 TEXT 를 `ORDER BY "created_at" DESC LIMIT 1` 로 읽는 **사전순 max** 감지다(`tail/route.ts:48,69`).
- **도달 경로**: 생일·경조사·연차시작 대상자가 있는 날이면 두 크론(`0 0 * * *`, UTC 00:00 = KST 09:00)이 매일 ISO 행을 삽입한다. R2 손 검산 — 2026-08-04 KST 09:00 = UTC 00:00 → `nowIso='2026-08-04T00:00:00.000Z'`. 같은 UTC 날짜의 공백형 행 `'2026-08-04 05:00:00'` 은 11번째 문자 `' '(0x20) < 'T'(0x54)` 이므로 **항상 더 작다** → `ORDER BY DESC LIMIT 1` 은 그 UTC 날짜 내내 ISO 행을 반환한다.
- **영향**: 폴링 폴백 클라이언트에서는 전역 messages 채널·chat_rooms 채널의 max 가 ISO 행에 고정돼 새 메시지가 max 를 올리지 못하고, 미읽음 배지·방 목록 갱신이 그 UTC 날짜 동안 멈춘다. WS 연결 여부와 무관하게 확정되는 실피해는 **공지방 내부 정렬** — `messages ORDER BY created_at` 이 생일메시지를 최신으로 고정하므로 이후 도착한 메시지가 그 앞(과거 위치)에 끼워진다.
- **검증**: 반증 (1) "tail 이 `datetime()` 캐스트로 비교하는가" 는 `tail/route.ts:48,68` 에서 TEXT 원본 비교임이 확인돼 실패. 반증 (2) "클라이언트 갱신이 WS 신호만으로 되는가" 는 **부분 성립**했다 — `polling-bus.ts:707-718` 이 `wsActive || sseActive` 이면 tail 폴링 타이머를 끄고, 일반 메시지는 `mutate/route.ts:86-92` 의 `triggerMutationSignal` 이 채널 신호를 emit 하므로 WS 클라이언트는 tail max 와 무관하게 갱신된다. 또한 `chat_rooms` 는 그 방의 다음 실제 메시지에서 공백형으로 덮여 복구된다. 따라서 '전면 불능' 은 성립하지 않아 **P0 → P1 강등**. 같은 지점을 별도로 보고한 D02-006·D06-002 를 이 항목으로 병합했다.
- **수정 방향**: 두 크론의 `created_at`/`last_message_at` 을 `toUtcSqlTimestamp`(`lib/chat-read-cursors.ts:21`)로 공백형 UTC 정규화. '항상 09:00 표시' 의도는 `` `${targetDate-1일} 15:00:00` `` (UTC 공백형)으로 그대로 유지할 수 있다. (난이도 S · 회귀위험 높음 · 묶음 FB6 시각 정규화, 선행 형식 혼재 마이그레이션 또는 양형식 허용 리더)

### D10-003 · P1 · 결재 위임 기간 검증이 UTC '오늘' 기준 — 만료 다음날 KST 00:00~08:59 에도 대리결재 허용

- **근본원인 축**: S7 시각 표현 이중화
- **위치**: `lib/server-approval-transition.ts:388-399`
- **결함**: SEC-P0-01 수정으로 넣은 위임 기간 검증이 UTC 날짜를 기준으로 삼는다.
  ```ts
  const now = new Date().toISOString().slice(0, 10);
  const startDate = String(delegation.start_date || '').slice(0, 10);
  const endDate = String(delegation.end_date || '').slice(0, 10);
  // SEC-P0-01 fix: 위임 기간 검증 (시작일 ≤ 오늘 ≤ 종료일)
  if ((!startDate || startDate <= now) && (!endDate || endDate >= now)) {
    effectiveCurrentApproverId = String(actor.id);
  }
  ```
  서버 TZ 는 UTC 이므로 KST 00:00~08:59 동안 `now` 는 KST 기준 **어제**다. `start_date`/`end_date` 는 사용자가 KST 달력으로 입력한 날짜다.
- **도달 경로**: actor 가 관리자도 아니고 직접·실효 결재자도 아닐 때만 이 분기에 도달한다(`:371`). 즉 **대리결재자가 결재를 시도하는 정확히 그 경로에서 항상 실행**된다. R2 손 검산 — `end_date='2026-08-03'` 위임을 UTC 2026-08-03 15:30(= KST 2026-08-04 00:30)에 사용하면 `now='2026-08-03'` 이라 `'2026-08-03' >= '2026-08-03'` 이 참 → **만료 위임 통과**. 반대로 `start_date='2026-08-04'` 위임은 같은 시각에 `'2026-08-04' <= '2026-08-03'` 이 거짓 → KST 로는 오늘인데 거부.
- **영향**: 만료된 대리결재 권한이 **매일 최대 9시간 연장**되는 인가 경계 오류. 대칭적으로 당일 시작 위임은 오전 9시까지 결재가 막힌다.
- **검증**: 반증조건은 "`approval_delegation.start_date`/`end_date` 가 UTC 기준으로 저장·해석되는 설계인가" 였다. 스키마상 TEXT 날짜만 저장되고, 저장소 규약(`lib/seoul-time.ts:4-7`)이 "모든 DB insert·cron·통계 키는 이 헬퍼(KST)로 통일" 이라고 명시한다 → UTC 해석 근거 없음, 반증 실패. 정당하게 부여됐던 권한의 기간 초과 사용이라 P0 아닌 **P1**.
- **수정 방향**: `getKoreanTodayString()` 으로 교체(1줄). (난이도 S · 회귀위험 높음 · 묶음 FB6)

### D10-004 · P1 · `approvals.created_at`(UTC 공백형)을 표시 경로 3곳이 KST 로 오독 — 오전 기안 문서의 기안일이 전날로 표시

### D10-005 · P1 · 문서번호 일련 카운트 창이 UTC 날짜로 왜곡 — 같은 문서번호가 중복 발급될 수 있음

- **근본원인 축**: S7 시각 표현 이중화
- **위치**: `app/main/기능부품/전자결재서브/useApprovalSubmit.ts:380-407,416-430` (모바일 사본 `app/main/모바일/결재/data-hooks.ts:294-303` 동일)
- **결함**: `dayStart.setHours(0,0,0,0)` 로 만든 KST 자정을 `toISOString()` 해서 `.gte('created_at', ...).lt(...)` 로 비교한다(`:380-389`). 비교 대상 컬럼은 공백형 UTC 이므로 **TEXT 사전순 비교**가 되고, 경계값만 ISO 라 창이 어긋난다. 그 창의 결과로 `:403` `sequence: (count || 0) + 1` 이 계산되는데, 정작 문서번호의 dateStamp 는 KST 기준이다(`lib/approval-workflow.ts:74` `formatKoreanDateKey`).
- **도달 경로**: R2 손 검산(KST 2026-08-04 02:00 기안) — `dayStart='2026-08-03T15:00:00.000Z'`, `dayEnd='2026-08-04T15:00:00.000Z'`. 공백형 `'2026-08-03 17:00:00'` 은 11번째 문자 `' ' < 'T'` 라 `dayStart` 미만 → **제외**. 결국 창에 걸리는 것은 date-part 가 `'2026-08-04'` 인 UTC 하루뿐이다. 그런데 dateStamp 는 KST `'20260804'`. 따라서 KST 04일 새벽 기안 2건은 둘 다 `count=0` → `sequence 1` → 동일 문서번호이고, KST 09:00 이후 첫 문서도 `sequence 1` 이라 새벽 문서와 충돌한다.
- **영향**: 문서번호 무결성이 깨진다. `approvals` 에 `doc_number` UNIQUE 인덱스가 없어(`idx_approvals_doc_number` 는 비유니크) DB 가 막아주지도 않는다. 같은 창 계산을 쓰는 **중복 물품신청 감지**(`:427-428`)도 오전 제출분을 놓친다.
- **검증**: 반증 (a) "d1 query 라우트가 `gte/lt` 양변을 `datetime()` 정규화하는가" → 값 그대로 바인딩이라 실패. (b) "`created_at` 이 ISO 로 저장되는가" → D10-004 에서 이미 반증. 추가로 모바일 `generateMobileDocNumber` 도 완전히 동일한 코드라 PC 전용 결함이 아님이 확인됐다.
- **수정 방향**: 경계값을 `toUtcSqlTimestamp(KST자정)` 공백형으로 변환해 비교하거나, 서버 라우트에서 날짜키 컬럼(`doc_date`)을 따로 저장. (난이도 S · 회귀위험 높음 · 묶음 FB6)

### D10-006 · P1 · 모바일 채팅 '할 일 등록' `task_date` 가 UTC 날짜 — KST 새벽 등록분이 어제 목록으로
