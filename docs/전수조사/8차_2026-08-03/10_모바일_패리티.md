## 요약

모바일은 화면 껍데기가 아니라 **오프라인 큐라는 고유 쓰기 경로를 하나 더 갖는 두 번째 클라이언트**이고, 이 도메인 결함의 대부분(20건 중 11건)이 그 경로에 몰려 있다. 큐는 "실패를 성공으로 보고"하는 구조가 반복된다 — 오프라인 첨부는 R2 에 올라가지만 문서에 연결되지 않고(D09-001), 재전송에 멱등키가 없어 응답 유실 시 결재·연차가 중복 INSERT 되며(D09-002), 실패 항목은 다음 `online` 이벤트까지 정지하고 '다시 시도' 버튼은 실제로 아무것도 하지 않는다(D09-003). 두 번째 축은 **클라이언트가 최종 심판이 되는 구조**다: 출퇴근 지오펜스·시각이 전부 브라우저에서 결정되고 `localStorage.bypass_gps` 한 줄로 꺼지며(D09-007), 수술상담 PHI 는 여전히 서버로 한 건도 넘어가지 않고 localStorage 평문에만 남는다(D09-D01, 7차 A3-06 미수정). 세 번째는 **PC 사본과의 drift** — 근로계약 서명 플로우 ~90L 가 모바일 셸과 PC 마이페이지에 자구 단위로 복제되어 있고 그 안의 0행 UPDATE 결함까지 똑같이 두 벌이다(D09-005·D09-013). 반면 재고·채팅·관리자 화면군은 훅/서비스 재수출 또는 PC 컴포넌트 dynamic import 로 데이터 경로를 공유해 패리티가 깨지지 않았다(부록 참조).

### D09-D01 · P0 · 수술상담 PHI 가 여전히 localStorage 에만 평문 저장 (7차 A3-06 미수정)

- **근본원인 축**: S11 클라이언트 신뢰 경계 붕괴 — 계산·검증·PII 보호를 브라우저가 수행

- **도달 경로**: 수술상담 '정밀 분석(음성)' 을 쓸 때마다 매 분석분이 저장된다. 로그아웃·세션 만료와 무관하게 잔존하고 만료 정책이 없다.
- **영향**: 공용 단말의 브라우저 프로필 접근만으로 **앱 인증을 우회해** 환자 진단·수술계획을 열람할 수 있다. 기록은 백업·감사 대상 밖이며, 반대로 다른 기기에서는 자기 기록조차 조회되지 않는다.
- **검증**: R2 는 "AI 결과를 DB 로 저장하는 경로가 다른 파일에 추가됐다면 CLOSED" 라는 반증조건을 소진했다. `saveRecord`(`수술상담.tsx:59-72`)는 `setRecords` + `localStorage.setItem` 만 하고 서버 호출이 없으며, 모바일 `수술상담.tsx:176-186` 의 `op_consultations` insert 는 '빠른 기록' 폼 전용 payload(state/note/staff_id)라 AI 결과 필드를 담지 않는다. 인용 라인 4곳이 7차 시점과 동일함도 git log 로 확인(최신 커밋 209f318b 는 7차 기준 커밋 범위 밖). 원격 유출이 아니라 at-rest 노출이라는 점을 감안해도 인증 경계를 넘는 PHI 열람이므로 **P0 유지**.
- **수정 방향**: AI 분석 결과를 `op_consultations`(또는 전용 테이블)로 서버 저장하고 localStorage 는 임시 캐시로만 사용 + 세션 종료 시 삭제. (난이도 M · 회귀위험 높음 · 묶음 FB10 서버 권위 이전, 선행 FB3·FB1)

### D09-001 · P1 · 오프라인 결재·게시판 첨부가 R2 에만 올라가고 문서에 영영 연결되지 않음 (고아 첨부)

- **위치**: `app/main/모바일/결재/AttachmentPicker.tsx:115-146`, `app/main/모바일/결재/기안상신.ts:70-77`, `app/main/모바일/게시판/글작성.tsx:241-266`, `lib/offline-upload-queue.ts:256-277`

- **수정 방향**: `AttachmentPicker`/`글작성` 의 `enqueueUpload` 에 문서 `meta_data` 갱신 update 를 `onSuccessAction` 으로 전달하거나, 상신 시 queued blobId 목록을 meta 에 기록하고 flush 완료 시 치환하는 후처리를 추가. (난이도 M · 회귀위험 중 · 묶음 FB9 실패 가시화)

### D09-002 · P1 · 오프라인 큐 재전송에 멱등키가 없어 응답 유실 시 approvals·leave_requests 등 중복 INSERT

- **근본원인 축**: S10 실패의 조용한 성공 보고
- **위치**: `lib/offline-queue-d1.ts:134-148`, `app/components/PwaBootstrap.tsx:259-278`, `lib/offline-queue.ts:282-287`
- **결함**: `enqueueD1Mutation` 은 `isNetworkError(err)` 이면 동일 payload 를 그대로 재큐잉한다(`offline-queue-d1.ts:139-143`). 서버가 이미 INSERT 를 커밋했고 응답만 유실된 경우도 같은 분기다. replay 측도 `PwaBootstrap.tsx:265-267` `if (!response.ok) throw` → `offline-queue.ts:286` `markAttempted` → 최대 5회 재시도로 같은 payload 를 반복 전송한다. 큐 항목 id 는 서버로 전달되지 않아 서버가 중복을 식별할 수단이 없다.
- **도달 경로**: 온라인 상태에서 fetch 가 TypeError 로 끊기는 경우(커밋 완료 + 응답 유실), 또는 replay 중 5xx 수신 시. 모바일 야외 사용에서 현실적으로 발생한다.
- **영향**: 결재 문서 이중 상신, 연차 이중 신청, 물품·발주 이중 등록이 조용히 발생한다. `attendance` 는 `onConflict` upsert 라 안전하지만 `approvals`·`leave_requests`·`inventory`·`purchase_orders` 는 순수 insert 로 노출된다.
- **검증**: 반증조건은 "호출측 payload 에 고정 UUID PK 가 포함되어 서버 PK 충돌로 걸러지는가" 였고, 성립하지 않았다. `lib/approval-submit-payload.ts:112-138` 이 만드는 row 에 `id` 키가 없고, 연차 경로(`연차신청폼.tsx:176-186`)의 leave_requests payload 에도 없다. 두 테이블의 TEXT PK 에는 DEFAULT 가 없어 서버가 요청마다 새 id 를 생성하며, 기간·문서번호 기준 UNIQUE 인덱스도 존재하지 않는다(`idx_approvals_doc_number` 는 비유니크).
- **수정 방향**: 큐 항목 id 를 payload 에 `client_request_id` 로 포함하고 서버 mutate 에 멱등 검사를 추가하거나, insert payload 에 클라이언트 생성 UUID PK 를 강제. (난이도 M · 회귀위험 중 · 묶음 FB9)

### D09-003 · P1 · 큐 flush 트리거가 마운트 1회+online 이벤트뿐 — 실패 항목·'다시 시도' 항목이 무기한 정지

- **근본원인 축**: S10 실패의 조용한 성공 보고
- **위치**: `lib/offline-queue.ts:246-305`, `lib/offline-queue.ts:204-216`, `app/main/모바일/공통/오프라인실패배너.tsx:155-170`
- **결함**: `startAutoFlush` 의 트리거는 등록 시 `void flush()` 와 window `online` 이벤트 2개뿐이다(`offline-queue.ts:294-299`). `markAttempted`(:311-328)는 백오프 시간이 지나도 재-flush 를 예약하지 않고, `retryFailed`(:204-216)는 항목을 active 큐로 되돌리며 `storageWrite` + emit 만 한다 — flush 호출이 본문에 없다. 실패배너 주석은 `다시 시도 → active 큐로 이동 + flush`(:10) 라고 적혀 있으나 실제 코드는 `:156` `retryFailed(item.id)` 한 줄이다.
- **도달 경로**: 온라인 상태에서 5xx 등 일시 오류로 `markAttempted` 된 항목, 그리고 실패배너 '다시 시도' 를 누른 항목 전부. `PwaBootstrap` 은 SPA 내내 마운트를 유지하므로 재마운트에 의한 우발적 flush 도 일어나지 않는다.
- **영향**: 배너는 '동기화 중 N개' 를 계속 표시하지만 실제 전송은 없다. 사용자가 네트워크를 껐다 켜거나 새로고침하기 전까지 큐가 멈춰 있다.
- **검증**: R2 는 "구독자 중 items 변경 시 flush 를 호출하는 코드" 를 전수 확인했다. `flush` 는 `startAutoFlush` 내부 클로저(`:254-292`)라 외부에 노출되지 않고, 반환값도 stop 함수뿐이다(`PwaBootstrap.tsx:222-296`). 구독자는 오프라인배너(카운트 표시)와 출퇴근체크인(`queue.list()` 읽기 병합) 둘뿐이다. 다만 '영구' 정지는 아니고 네트워크 토글/새로고침으로 해소되므로 **P1 유지**.
- **수정 방향**: `markAttempted`/`retryFailed` 후 `setTimeout` 으로 flush 를 재예약하거나 주기(예: 30s) flush 타이머를 추가. (난이도 S · 회귀위험 중 · 묶음 FB9)

### D09-004 · P1 · 오프라인 출퇴근 체크인/아웃은 attendance(단수)만 큐잉 — attendances(복수) 동기화 누락

- **근본원인 축**: S10 실패의 조용한 성공 보고
- **위치**: `app/main/모바일/내정보/출퇴근체크인.tsx:329-368`, `app/main/모바일/내정보/출퇴근체크인.tsx:384-418`

- **수정 방향**: queued 분기에서 attendances upsert 도 함께 큐잉(groupId 로 순서 보장)하거나, 단수 upsert replay 성공 후 서버에서 dual-write 하도록 mutate 훅을 추가. (난이도 S · 회귀위험 중 · 묶음 FB9)

방법: grep 으로 각 모바일 화면군의 데이터 경로(API/훅/테이블)를 PC 대응 화면과 대조한 뒤 격차 의심 지점만 정독했다. 쓰기 경로는 PC·모바일 공히 `lib/db-client` → `/api/d1/query|mutate` 이므로 "서버 검증" 의 실체는 mutate 정책 계층(별도 도메인)이고, 여기서는 **클라이언트 계층에서 모바일에만 빠진 검증·필터·연결 로직**을 판정했다.

### D. MobileShell 서명 UPDATE 실영향

스키마갭 조사가 지목한 `MobileShell.tsx:196-210` UPDATE(`:202` 는 `receipt_signature_data` 라인)의 실영향은 다음과 같이 확인됐다.

- error 만 검사하고 영향 행수를 보지 않음 → 0행 매칭 시에도 성공 흐름 계속(문서 저장·알림·성공 토스트) 하지만 계약은 '서명대기' 잔존 → 모달 재출현 → 재서명 루프.
- 실패/재시도 경로에서 `document_repository` 선-insert 가 반복 → 암호화 계약서 문서 중복 누적.
- PC 마이페이지에 동일 코드 복제 → 동일 결함 2곳. 상세는 D09-005·D09-013·D09-014.
