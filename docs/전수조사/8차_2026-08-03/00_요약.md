## 3. 근본원인 축 S1~S14

**이 절이 이 문서의 핵심이다.** 267건은 서로 무관한 267개의 버그가 아니라, 14개의 구조적 원인이 각각 여러 지점에 발현한 것이다. 수정 계획(FB1~FB13)도 개별 finding 이 아니라 이 축을 단위로 짰다.

축별 건수는 **병합 전 308건 기준**(축의 실제 무게를 보이기 위함)이고, 괄호 안 CONFIRMED 는 대표 항목 기준이다.

### S1 — D1 API 게이트웨이의 판정 ≠ 실행 · fail-open

`/api/d1/mutate` 는 "정책 판정에 쓸 행"을 D1 에서 SELECT 한 뒤 그 행으로 권한을 따지고, 별개의 문장으로 UPDATE/DELETE 를 실행한다. 문제는 **판정용 SELECT 가 실패하거나 허용 한도를 넘으면 `where` ∪ `set` 를 합성한 가짜 행으로 폴백해 판정을 계속한다**는 것이다. 합성행은 `company_id` 가 없으므로 `rowCompanyIsNull()` 이 true 가 되어 회사 스코프 정책을 그대로 통과하고, 이어지는 실행문은 진짜 행 전체에 적용된다. 같은 fail-open 패턴이 rate-limit(D1 오류 시 `allowed:true`), realtime tail(정책 필터를 통째로 건너뛰는 독립 SQL 경로), read-cursors·typing(바인딩·세션 부재 시 멤버십 검사 스킵)에도 반복된다. **"판정 경로와 실행 경로가 다른 문장"이라는 구조 자체가 원인이며, 개별 라우트를 하나씩 막는 방식으로는 닫히지 않는다.**

- 소속 12건 (CONFIRMED 12 · P0 4 · P1 3 · P2 5) → **FB1**
- 대표: `D01-016`(mutate 폴백으로 타 회사 전 행 DELETE) · `D06-001`(realtime tail 이 민감컬럼 오라클) · `D01-D03`(`daily_closure_items` AUTHENTICATED×4)

### S2 — 정책 레지스트리 과다개방 (PUBLIC/AUTHENTICATED)

`POLICY_REGISTRY` 는 테이블마다 select/insert/update/delete 4연산의 접근 패턴을 지정하는데, 상당수가 `PUBLIC_ALL` 또는 `AUTHENTICATED` 로 등록돼 **"로그인했다"는 사실만으로 소유권·회사 스코프 검사 없이 타인 행을 읽고 쓰고 지울 수 있다**. `board_posts` 는 로그인한 아무 직원이 공지사항을 수정·삭제할 수 있고, `chat_rooms` 는 insert 가드가 요청 본문만 보고 기존 행을 조회하지 않아 방 id 만 알면 UPSERT 로 방을 통째로 탈취할 수 있으며, `staff_evaluations` 는 전 직원 인사평가를 열람하고 임의 평가를 작성할 수 있다. 흥미로운 점은 이 프로젝트가 `messages`·`leave_requests`·`staff_members` 에는 정교한 asyncGuard 와 컬럼 가드를 붙여 놨다는 것이다 — **패턴을 몰라서가 아니라 테이블별로 일관되게 적용되지 않아서 생긴 구멍이다.**

- 소속 18건 (CONFIRMED 17 · P0 6 · P1 3 · P2 9) → **FB2**
- 대표: `D07-010`(board_posts PUBLIC_ALL) · `D06-017`(채팅방 UPSERT 침투) · `D03-D09`(인사평가 AUTHENTICATED)

### S3 — 정책 레지스트리 누락·과소개방 → 권한 보유자에게 조용한 기능 사멸

S2 의 반대 방향이다. 테이블이 아예 등록되지 않았거나 필요 이상으로 좁게 등록돼, **권한을 정당하게 보유한 사용자에게 403 이나 빈 목록이 돌아간다**. `leave_ledger` 는 레지스트리에 없어서 admin 을 포함한 전원이 403 을 받고, 소비처 6곳이 `leave_balances` 폴백을 갖고 있어 에러 없이 "잔여 0일"이 표시된다 — **실패가 오답으로 위장되는 것이 이 축의 가장 나쁜 성질이다.** 비관리자 인사 권한자의 감사 기록은 403 으로 전부 유실되고, 게시판 별표 토글은 PolicyDenied 메시지와 폴백 판별식이 불일치해 에러 토스트 + 롤백으로 끝난다.

- 소속 10건 (CONFIRMED 10 · P0 0 · P1 7 · P2 3) → **FB2**
- 대표: `D01-001`(leave_ledger 미등록) · `D08-007`(인사 권한자 감사 기록 유실) · `D07-011`(별표 토글 완전 실패)

### S4 — 세션 스냅샷·권한 압축으로 서버측 권한 판정 붕괴

세션 토큰은 크기 제약 때문에 권한 키를 **8개 + `menu_*` 접두사만** 남기고 압축한다. 그 결과 `finance_*` 계열은 서버에서 영구 소실돼 `erp_can_manage_finance` 가 항상 false 가 되고 FINANCE_SCOPE 3테이블이 재무 담당자에게 전면 차단된다. 더 나쁜 것은 `mypage_수정 === false` 같은 **명시적 차단**이 압축 후 `undefined` 로 읽혀 fail-open 이 된다는 점이다. 여기에 `/api/auth/session` 은 클라이언트에 DB 원본 권한 전체를 돌려주므로 **"화면에는 메뉴가 보이는데 API 는 거부한다"는 비대칭이 구조적으로 발생한다.** 세션 스냅샷에 존재하지도 않는 `session.user.is_master`/`is_admin` 을 관리자 판정에 쓰는 곳이 3곳 있고, `erpStaffId` 가 UUID 정규식을 요구해 비UUID staff id 계정에서는 SELF_ONLY 계열 판정이 항상 실패한다.

- 소속 14건 (CONFIRMED 12 · P0 0 · P1 4 · P2 10) → **FB3**
- 대표: `D01-004`(finance_* 소실 + `mypage_수정` fail-open) · `D01-018`(비UUID id 판정 실패) · `D12-002`(마스터 세션이 13개 API 에서 401)

### S5 — 스키마 드리프트: 실 D1 에 없는 컬럼·테이블을 코드가 참조

Supabase(Postgres) → D1(SQLite) 이관 과정에서 **코드는 옛 컬럼을 계속 참조하는데 D1 테이블에는 그 컬럼이 없다.** SQLite 는 `no such column` 을 던지므로 해당 쿼리가 통째로 실패한다. `staff_members.agreed_*` 2종 때문에 급여 워크센터의 직원 마스터 SELECT 가 죽어 **13개 모듈이 빈 화면**이 되고, 근로계약서 서명완료 UPDATE 는 미존재 컬럼 2종 때문에 PC·모바일 양쪽에서 100% 실패하는데 **문서보관함 INSERT 가 먼저 성공하므로 재시도마다 미완결 사본이 누적된다**(선저장 → 실패 순서). 복지규정 저장은 존재하지 않는 테이블에 upsert 하면서 실패를 "(로컬 임시저장)"으로 위장한다. R0 의 B5 스키마 갭 스캔이 미존재 컬럼 참조 18개 사이트를 찾아냈고 **P0 2건이 여기서 나왔다**.

- 소속 21건 (CONFIRMED 19 · P0 6 · P1 9 · P2 6) → **FB4**
- 대표: `D04-007`(급여 워크센터 직원 0명) · `D04-005`(계약서 서명 전면 실패 + 사본 누적) · `D03-027`(ESS 저장 payload 계약 불일치로 상시 400)

### S6 — 크론·트리거 배선 파손 및 서버에서의 클라이언트 전용 모듈 오용

`wrangler.toml` 의 `[triggers]` 에는 cron 5개만 등록돼 있는데 `cloudflare-worker.ts` 의 라우트 매핑은 8개 키를 갖고 있다. Cloudflare 는 `[triggers]` 에 있는 표현식으로만 `scheduled()` 를 기동하므로 **매핑만 있고 트리거가 없는 크론은 도달률 0 — 영원히 실행되지 않는다.** 결근 자동 생성(`absent-auto-create`)이 그 상태이며 7차 A1-03 지적 이후 `wrangler.toml` 은 무변경이다. 게다가 같은 기능에 **두 번째 독립 결함**이 있다 — `lib/absent-auto-create.ts` 가 서버 런타임에서 클라이언트 전용 `db-client`(상대경로 fetch)를 쓰기 때문에, 트리거를 등록해도 즉시 실패한다. **하나만 고쳐서는 기능이 살아나지 않는다.** 부수적으로 크론 18개 전부가 `CRON_SECRET` 을 비상수시간 문자열 비교로 검증하고, 시스템마스터 운영 패널의 크론 목록은 실제 트리거와 불일치한다.

- 소속 17건 (CONFIRMED 14 · P0 2 · P1 5 · P2 10) → **FB5**

### S7 — 시각 표현 이중화: `created_at` 형식 혼재 + UTC/KST 경계 오독

## 5. 7차 대비

7차가 P0 로 확정한 42건 전량에 8차 판정을 붙였다. **미판정 0건.** 상세는 [`01_델타_7차P0_현황.md`](01_델타_7차P0_현황.md).

| 판정 | 건수 | 비율 |
|---|---:|---:|
| CLOSED | 11 | 26% |
| PARTIAL | 11 | 26% |
| **OPEN** | **20** | **48%** |

### "7차 지적이 왜 절반 이상 열려 있는가" — 구조적 관찰

1. **"안 건드린 것은 안 고쳐졌다"가 100% 성립했다.** 42건 중 어떤 커밋도 인용 파일을 열지 않은 것이 16건인데, 그 16건은 **예외 없이 전부 OPEN** 이다. 수정 여부는 난이도가 아니라 **파일이 열렸는가**로 결정됐다.

2. **수정된 것은 "한 줄로 닫히는 것"뿐이었다.** CLOSED 11건은 전부 게이트 한 줄 추가(export-csv 관리자 게이트, data-reset bcrypt 재검증) 또는 정책 한 줄 재분류(todos SELF_ONLY, certificate_issuances STAFF_IN_SCOPE)로 닫히는 국소 결함이다. 반면 PARTIAL·OPEN 31건은 **정책 레지스트리 구조(S2/S3) · 상태전이 무결성(S9) · 스키마 드리프트(S5)** 처럼 축을 건드려야 하는 것들이다. 7차 수정은 쉬운 것부터 닫았고 축은 그대로 남았다.

3. **PARTIAL 은 "절반 안전"이 아니라 "경로만 바뀐 동일 피해"다.** PARTIAL 11건 중 6건이 "부모는 닫고 자식은 열어둔" 형태다 — `daily_closures` 는 스코프를 걸었으나 PII 를 실제로 담은 `daily_closure_items` 는 전면 개방(`D01-D03`), 징계는 닫았으나 인사평가는 그대로(`D03-D09`), 지각 감지는 복구했으나 조퇴 감지는 상시 0(`D03-D08`). **7차 피해가 그대로 재현되며 P0 3건이 여기서 나왔다.**

4. **CLOSED 판정에도 재공격이 필요하다.** 가장 위험한 발견이 CLOSED 로 분류된 A12-02 에서 나왔다. R2(V11)가 CLOSED 에 재공격을 걸어, 해시 prefix 오라클이 `query` 에서는 확실히 막혔으나 **`mutate` 에는 동일 오라클이 그대로 남아 있음**을 확인했다(`D01-D05`, P0). **한쪽 진입점만 막는 수정 패턴**이 실증된 사례다.

5. **후속 하드닝 커밋 자체가 새 결함을 만들었다.** `e7ae1756` 이후 11개 커밋 중 7차 P0 를 대상으로 한 것은 `f7f41585` 하나뿐이고 나머지는 스크립트·시간대·백업 하드닝인데, 그중 3건이 8차 Pass B 에서 **PARTIAL 또는 회귀 유발**로 판정됐다. 특히 실행 게이트 커밋 `7a7b7c21` 은 5번째 스크립트를 빠뜨렸고(`D11-002`) 동시에 하위호출이 게이트에 걸려 항상 실패하는 회귀를 만들었다(`D11-003`). **수정 자체를 검증하는 절차가 없다는 것이 이 관찰의 결론이다.**

## 6. 이번 감사가 커버하지 못한 영역

정직하게 적는다. 아래 3가지는 이 감사가 **확인하지 않았거나 확인할 수 없었던** 것이다.

### 6-1. E2E 미실행

Playwright 스위트를 이번 감사에서 돌리지 않았다. 사유는 셋이다.

- **비용**: `workers=1` 로 60분 이상 소요된다. 감사 라운드 안에서 반복 실행이 불가능하다.
- **부작용**: `npm run test:e2e` 는 `seed-e2e-d1.mjs --if-local` 을 선행 실행하며 **로컬 D1 에 쓰기를 한다.** READ-ONLY 원칙을 깬다.
- **신호 대비 잡음**: 이전 실행에서 **테이블이 부재한 상태에서도 43건이 통과**한 이력이 있다. CI(`e2e.yml`)는 `--grep-invert @real-db` + D1 바인딩 없는 `next start` 환경이라 mock 세션 UI 검증으로 한정된다(워크플로 주석이 자인). 즉 **통과가 정합성을 보장하지 않는다.**

대신 R0 의 B6 에서 **스펙-프로젝트 매칭을 정적으로 대조**해, 스펙 105개 중 2개가 영구 미실행임을 확정했다(`D13-019`). E2E 를 신뢰 가능한 게이트로 만드는 것 자체가 FB13 의 과제다.

### 6-2. 운영 D1 실데이터 미조회

운영 D1(`pchos-d1-v2`)에 직접 쿼리하지 않았다. 스키마 비교는 **로컬 D1 introspection 덤프 + 마이그레이션 0000 + `schema.ts`** 3자 대조로 대체했다. 이 때문에:

- **S5(스키마 드리프트) 항목은 "로컬 스키마와 마이그레이션에 그 컬럼이 없다"까지가 근거다.** 누군가 운영 D1 에 수동 `ALTER TABLE` 을 했다면 해당 항목은 오탐이 된다. 실제로 R2 가 `backups/d1_chunks/chunk_0054.sql:53` 에서 문제의 컬럼이 존재하는 흔적을 발견해 `D04-103` 을 PLAUSIBLE 로 강등한 사례가 있다.
- 그래서 **FB4 의 선행조건은 "운영 D1 실 introspection 1회"** 다. 이것이 FB4 착수 전 반드시 필요한 유일한 외부 확인이다.
- 마찬가지로 행 데이터에 의존하는 판정(예: `type='notice'` 방이 2개 이상 존재하는가)은 전부 PLAUSIBLE 로 남겼다.

### 6-3. PLAUSIBLE 6건이 왜 미확정인가

PLAUSIBLE 은 "**코드 사실은 확정됐으나 발현이 저장소 밖 상태에 의존**"하는 것들이다. 코드만 읽어서는 참/거짓을 가릴 수 없으므로 승인 대상에서 분리했다.

### 6-4. 그 밖의 한계

- **동시성 결함은 정적으로만 확인했다.** TOCTOU·CAS 부재(`D07-004`·`D07-007`·`D05-009`)는 코드 구조로 도출했고 실제 경합을 재현하지는 않았다.
- **B6 이 찾은 "main 푸시 시 품질 게이트 0"**(`deploy.yml` 이 `needs` 없이 e2e 와 병렬 → 테스트가 깨져도 배포됨)은 **원장에 독립 finding 으로 등록되지 않았다.** `D13-013` 의 note 가 부수적으로 언급할 뿐이다. 9차에서 신규 등록해야 한다.
