## 요약

### D06-001 · P0 · `/api/realtime/tail` 이 임의 컬럼 등가필터를 허용해 `staff_members` 민감컬럼 존재여부 오라클이 된다

- **근본원인 축**: S1 D1 API 게이트웨이의 판정 != 실행 · fail-open (mutate/query/realtime/rate-limit)
- **위치**: `app/api/realtime/tail/route.ts:41-113`, `lib/realtime/allowed-tables.ts:7-42`, `app/api/d1/query/route.ts:199-212`
- **결함**: tail 라우트는 요청 파라미터를 `table:col=eq.val` 로 파싱한 뒤, 컬럼명이 정규식 `/^[a-zA-Z0-9_]+$/` 를 통과하기만 하면 WHERE 절을 그대로 합성한다 — `:61-64` `if (/^[a-zA-Z0-9_]+$/.test(col) && op === 'eq') { query += ` WHERE "${col}" = ?`; params.push(val); }`. 화이트리스트 검사는 `:97-100` 에서 `t.split(':')[0]` 즉 **테이블명만** 본다. 컬럼 제한도, 정책 필터(`filterByPolicy`·`stripStaffSecrets`)도, rate limit(`consumeRateLimit`) 호출도 전혀 없다. 그런데 `staff_members` 는 `lib/realtime/allowed-tables.ts:26` 에 포함돼 있고, 스키마상 `resident_no`·`phone`·`bank_account`·`password`·`created_at` 이 모두 실재한다. 바로 옆 `/api/d1/query` 는 `findSensitiveFieldUsage`(`:199-212`)로 `staff_members` 의 where/order 에서 민감 컬럼 사용을 403 으로 차단하고 있고, `lib/db/auth/policies.ts:1793-1798` 주석은 "필터·정렬에 쓰면 오라클이 되어 값을 복원할 수 있다"고 스스로 경고한다 — **tail 에는 그 가드가 없다**.
- **도달 경로**: 로그인 세션만 있으면 `GET /api/realtime/tail?tables=staff_members:resident_no=eq.<후보값>` 한 번으로 도달. 응답의 `created_at` 반환/`null` 차이가 곧 일치 여부다. `middleware.ts:39` matcher 는 `/main/:path*` 뿐이라 API 는 미들웨어도 타지 않는다.
- **영향**: 로그인만 하면 임의 직원의 주민등록번호·전화번호·계좌번호를 후보값 대입으로 확정할 수 있다. 특히 생일 공지 크론이 생년월일을 전사에 공개하므로 주민번호 후반 6자리(10^6) 대입이 현실적인 규모다. 채팅 측면에서는 `messages:room_id=eq.<타인 방>` 으로 대입 없이 즉시 타 방의 최신 활동 시각을 관측할 수 있다.
- **검증**: V03 이 반증 세 가지를 전부 소진했다. (1) `staff_members` 는 화이트리스트에 그대로 있다. (2) tail 라우트·미들웨어 어디에도 filterPart 컬럼 화이트리스트가 없다. (3) `local-d1-schema.json` 상 해당 컬럼들이 실재해 쿼리가 예외로 떨어지지 않는다. P0 유지.
- **수정 방향**: tail 의 filterPart 컬럼을 테이블별 허용 컬럼(`room_id`/`user_id` 등)으로 화이트리스트하고 `staff_members` 는 필터 자체를 금지한다. 추가로 `findSensitiveFieldUsage` 를 공용화해 query·tail 두 경로에 함께 적용한다. (난이도 M · 회귀위험 **높음** · 묶음 FB1 · 선행 FB13 정책 회귀 e2e 복구 권장)

### D06-017 · P0 · [7차 A4-01 델타 · OPEN] 채팅방 UPSERT 침투 — 임의 사용자가 기존 방을 통째로 탈취할 수 있다

- **근본원인 축**: S2 정책 레지스트리 과다개방(PUBLIC/AUTHENTICATED) — 소유권·회사 스코프 미검사
- **위치**: `lib/db/auth/policies.ts:358-371`, `lib/db/auth/policies.ts:553-561`, `app/api/d1/mutate/route.ts:426-430`, `app/api/d1/mutate/route.ts:475-501`

- **도달 경로**: 로그인 사용자가 `POST /api/d1/mutate` 에 `{op:'insert', table:'chat_rooms', values:[{id:'<피해자 방>', type:'group', created_by:'<본인>', members:['<본인>']}], conflict:{columns:['id'], action:'update'}}` 를 **한 번** 보내면 성립한다. 방 id 는 실시간 채널명·URL 등에서 노출된다.
- **영향**: 임의 직원이 그 방의 유일한 멤버·생성자가 되어 원 멤버 전원을 축출하고, 그 즉시 `messages` SELECT 의 `CHAT_ROOM_MEMBER` 필터가 공격자에게 열려 **전체 대화 이력이 노출된다**.
- **검증**: V03 이 반증 두 가지를 모두 소진했다. (1) `registry-dump.json` 최종값에서 `chat_rooms` 는 `{select:CHAT_ROOM_MEMBER, insert:PUBLIC, update:PUBLIC, delete:ADMIN_ONLY, asyncGuards:'insert,update'}` 로 확정 — 레지스트리 하단 루프가 `ADMIN_ONLY` 로 덮지 않는다. (2) mutate 의 `InsertSchema` 에 `chat_rooms` 전용 예외 코드가 없다. 7차 대비 델타로는 `git show e7ae1756~1:lib/db/auth/policies.ts` 의 `chatRoomsInsertGuard` 본문이 현재와 **문자열 단위로 동일** — 무변경 OPEN. P0 유지.
- **수정 방향**: `chatRoomsInsertGuard` 가 `loadChatRoomMembership` 으로 동일 id 의 기존 방을 조회해, 존재하면 update 규칙(생성자/특권 + `canChangeChatRoomMembers`)을 적용하도록 바꾼다. 병행해 mutate 에서 `chat_rooms` 의 upsert 자체를 금지하고 `/api/chat-rooms` 라우트로 강제한다. (난이도 M · 회귀위험 **높음** · 묶음 FB2 · 선행 FB3 세션 권한 복원)

### D06-003 · P1 · `room_read_cursors`·`message_reactions` 정책이 `AUTHENTICATED` 라 타인 `user_id` 로 위조 쓰기/삭제가 가능하다

- **위치**: `lib/db/auth/policies.ts:563-593`, `lib/db/auth/policies.ts:1486-1521`, `app/api/d1/mutate/route.ts:82-105`

- **수정 방향**: 두 테이블의 insert/update/delete 를 `SELF_ONLY(staffIdField:'user_id')` 로 바꾸고, 방 대상 행에는 `CHAT_ROOM_MEMBER` asyncGuard 를 추가한다. select 도 최소한 멤버 스코프로 좁힌다. (난이도 M · 회귀위험 **높음** · 묶음 FB2 · 선행 FB3)

### D06-007 · P1 · RealtimeHub 가 클라이언트발 `signal` 프레임을 그대로 전 구독자에게 중계한다

### D06-002 · P1 · 공지봇 크론이 `messages.created_at` 에 ISO 형식을 넣어 tail 의 `max(created_at)` 이 하루 종일 고착된다

- **근본원인 축**: S7 시각 표현 이중화 — created_at 형식 혼재 + UTC/KST 경계 오독
- **위치**: `lib/birthday-announcements.ts:99-165`, `lib/leave-notice-cron.ts:213-269`, `lib/leave-notice-cron.ts:365-392`, `app/api/d1/mutate/route.ts:28-53`
- **결함**: `messages.created_at` 은 TEXT 이고 D1 기본값이 공백형식 `'YYYY-MM-DD HH:MM:SS'` 인데, 두 공지 크론은 ISO 를 넣는다 — `birthday-announcements.ts:99` `const nowIso = \`${kstDateStr}T00:00:00.000Z\`;` → `:140` `created_at: nowIso`, `:157` `last_message_at: nowIso`; `leave-notice-cron.ts:213→:245`, `:365→:372` 동일. `'T'`(0x54) > `' '`(0x20) 이므로 같은 날짜의 ISO 행이 그날 이후 모든 일반 메시지보다 사전순으로 크다. `/api/realtime/tail` 은 테이블별 `max(created_at)` 변화로 갱신을 감지하고(`tail/route.ts:48,69` `SELECT "${column}" ... ORDER BY "${column}" DESC LIMIT 1`), `lib/realtime/allowed-tables.ts:51-55` 의 `REALTIME_TABLE_TIMESTAMP_COLUMN` 에 `messages` 예외가 없어 `created_at` 을 쓴다. `chat_rooms` 는 `last_message_at` 을 쓰는데 그 컬럼까지 같은 ISO 값으로 덮인다. 아이러니하게도 `app/api/d1/mutate/route.ts:42-43` 주석은 "**notifications 에만 적용한다.** messages 는 현재 전 행이 공백 형식이라"라고 그 전제를 명시하고 있다 — 이 세 삽입 경로가 바로 그 전제를 깬다.
- **도달 경로**: 생일자·연차 시작자가 있는 날 `'0 0 * * *'`(KST 09:00) 슬롯의 두 크론(`cloudflare-worker.ts:70-71` 등록 확인)이 삽입하면, 그 UTC 일자 동안 `max(created_at)`/`max(last_message_at)` 이 ISO 값에 고착된다.
- **영향**: 공지 발송일에 새 메시지 팝업·배지가 폴링 폴백 경로에서 뜨지 않는다(커밋 `ba80925a` 가 `notifications` 에 대해 고친 것과 동일 결함이 `messages` 에 잔존). 공지방 안읽음 배지가 그날 내내 지워지지 않고 — `app/main/기능부품/메신저데이터유틸.ts:79-83` 이 커서를 공백형식으로 정규화해 `created_at.gt` 비교를 하므로 ISO 공지행은 항상 커서보다 크다 — 타임라인에서 공지가 이후 메시지보다 아래에 정렬된다.
- **검증**: V03 이 반증을 소진했다 — `REALTIME_TABLE_TIMESTAMP_COLUMN` 에 messages 매핑이 없고, 일반 메시지 INSERT 경로(`메신저유틸.ts:347-358`)가 `created_at` 을 넣지 않아 공백형식이 지배적임을 확인했다. 다만 WS(RealtimeHub)가 살아 있으면 체감이 줄어들고 "전 기능 불능"은 아니므로 **P0 → P1 조정**. tail 폴백 경로의 갱신 감지가 죽는 것과 안읽음 배지 고착·타임라인 역전은 WS 여부와 무관하게 남는다.
- **수정 방향**: 두 크론의 `created_at`/`last_message_at` 을 `toIsoTimestamp` 대신 `'YYYY-MM-DD HH:MM:SS'`(UTC) 로 통일하거나, mutate 의 `fillNotificationCreatedAt` 과 대칭인 정규화 함수를 messages 삽입 공용 경로에 두고 크론도 그것을 쓰게 한다. (난이도 M · 회귀위험 **높음** · 묶음 FB6)
