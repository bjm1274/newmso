## 요약

전자결재 도메인 21건 중 19건이 CONFIRMED, 2건이 REFUTED 로 확정됐다. 이 도메인의 문제는 개별 버그가 아니라 **"승인이라는 상태전이를 서버가 통제하지 않는다"** 는 단일 구조 결함이며, P0 4건이 모두 근본원인 축 S9(상태전이 무결성 붕괴)에 속한다. 결정적 두 경로는 (1) `approvals` 테이블이 POLICY_REGISTRY 에서 컬럼 가드가 0개인 채 `APPROVAL_SCOPE` 로 열려 있어 기안자 본인이 `/api/d1/mutate` 로 `status='승인'` 을 직접 쓰고 곧바로 후속 처리(연차 차감·인사명령·기본급 갱신)까지 실행할 수 있다는 점, (2) 전결 판정이 승인 코멘트 자유 문자열 `'[전결]'` 과 기안자가 심을 수 있는 `meta_data.is_arbitrary` 에만 의존해 잔여 결재선을 통째로 생략할 수 있다는 점이다. 7차가 지적한 A6-01/A6-02 의 "타인 문서 소유권 위조" 벡터는 `loadPolicyRowsForMutation` 재작성으로 닫혔으나, "자기 기안 자기 승인" 은 그대로 남아 절반만 수정된 상태다. 나머지 P1 은 대결(위임) 메타 정합 붕괴로 인한 문서 영구 데드락, 후속 처리 부분 실패의 완료 확정, 낙관적 잠금 부재, PC/모바일 계약 불일치로 갈라진다.

## 지적사항

### D05-001 · P0 · approvals 테이블에 컬럼 가드가 없어 기안자 본인이 `/api/d1/mutate` 로 `status='승인'` 을 직접 써서 전자결재 전체를 우회할 수 있다

- **근본원인 축**: S9 상태전이 무결성 붕괴 — 결재·재고·구매의 권한 가드·원자성·CAS 부재
- **위치**: `lib/db/auth/policies.ts:752-760`, `lib/db/auth/policies.ts:1576-1584`, `app/api/d1/mutate/route.ts:694-728`
- **병합**: D05-019(7차 A6-01 델타), D05-020(7차 A6-02 델타)
- **결함**: `approvals` 정책 항목은 `{ select:'APPROVAL_SCOPE', insert:'SELF_OR_SAME_COMPANY', update:'APPROVAL_SCOPE', delete:'SELF_ONLY', staffIdField:'sender_id', approvalFields:{ sender:'sender_id', approver:'current_approver_id' } }` 로 등록돼 있고 `guards` / `asyncGuards` 키 자체가 없다. `APPROVAL_SCOPE` 의 판정식은 `if (me !== null && (sender === me || approver === me)) return true;`(`policies.ts:1581`) 로, 통과하면 **어떤 컬럼을 바꾸는지와 무관하게** true 를 돌려준다. mutate 라우트는 `guardRow`/`changedKeys` 를 조립해 넘기지만(`route.ts:694-705`) approvals 에는 그것을 소비할 가드가 없고, set 키 필터는 `const setKeys = Object.keys(serializedSet).filter((k) => COLUMN_RE.test(k) && (!knownCols || knownCols.has(k)));`(`route.ts:710`) 즉 "스키마에 존재하는 컬럼인가" 만 본다. `status` 는 실 D1 에 존재하는 TEXT 컬럼이므로 그대로 통과한다. 대조군으로 `leave_requests` 는 `guards:'insert,update'`, `staff_members` 는 `staffPrivilegeGuard` 를 갖고 있어 컬럼 가드가 필요한 테이블 중 approvals 만 비어 있다.
- **도달 경로**(재현):
  1. 임의 직원 계정으로 로그인해 세션 쿠키를 얻는다. 별도 권한은 필요 없다.
  2. 아무 양식이나 기안한다 → `approvals` 행이 `sender_id = 본인 staff id`, `status='대기'` 로 생성된다.
  3. `POST /api/d1/mutate` 에 `{ op:'update', table:'approvals', set:{ status:'승인' }, where:[{ field:'id', op:'eq', value:'<내 문서 id>' }] }` 를 보낸다. `loadPolicyRowsForMutation` 은 DB 정본 행을 읽어 판정하므로(`route.ts:285-286`, 7차가 지적한 set 병합 위조는 여기서 이미 닫혔다) 위조는 불가능하지만, 읽어온 정본 행의 `sender_id` 가 곧 나 자신이라 `policies.ts:1581` 에서 통과한다. `status` 가 실제로 `'승인'` 으로 UPDATE 된다.
  4. `POST /api/approvals/process-final` 에 그 문서 id 를 보낸다. `isFinalizedApprovalStatus(approval.status)` 게이트(`route.ts:101-103`)는 `'승인'` 을 최종 상태로 인정하므로 통과하고, `canAccess` 는 `sessionUserId === String(approval.sender_id||'').trim()` 분기(`route.ts:115-120`)로 기안자를 허용한다.
  5. `processFinalApprovalEffects` 가 실제로 실행돼 연차 차감(`ensureApprovedAnnualLeaveRequest` + `recalculateLeaveBalance`), 인사명령 반영, 증명서 발급, 기본급 갱신이 커밋된다.
  - 이 경로는 UI 조작이 아니라 API 직접 호출이지만, 클라이언트가 실제로 같은 경로를 쓰고 있음이 확인된다 — `useApprovalDelegation.ts:177` 이 `await db.from('approvals').update(effectiveUpdates).eq('id', item.id)` 로 mutate 라우트를 호출한다. 즉 브라우저 콘솔에서 동일 헬퍼로 재현 가능하다.
- **영향**: 결재 통제의 전면 무력화. 임의 직원이 자기가 올린 연차·인사명령·급여인상 평가서를 스스로 최종 승인 상태로 만들고 후속 처리까지 실행할 수 있다. 승인 이력에는 정상 승인처럼 남는다.
- **검증**: R2(V06·V11) 가 반증조건 3개를 모두 시도해 전부 불성립했다. (1) `registry-dump.json` 의 approvals 행이 `guards:""`, `asyncGuards:""` 로 컬럼 가드가 실측 0개다. (2) mutate 라우트에 테이블별 변경금지 컬럼 목록이 없다(`route.ts:709-710`). (3) db-client 가 approvals update 를 그대로 mutate 로 보낸다(`mutation-builders.ts:20`). 병합된 D05-020 은 단독으로는 상태 게이트·멱등 마커 때문에 익스플로잇이 성립하지 않아 독립 심각도 P1 로 조정됐고(V06=P2, V11=P0 충돌 → V13 재판정), 실제 P0 는 중복 계상을 피해 D05-001 하나로 집계했다.
- **수정 방향**: approvals 정책에 `guards.update` 를 추가해 `status`·`current_approver_id`·`approver_line`·`meta_data.server_processing` 변경은 `changedKeys` 기준으로 거부하고(전이는 `/api/approvals/transition` 전용), 클라이언트의 `meta_data` 부분 갱신은 별도 서버 라우트로 옮긴다. (난이도 M · 회귀위험 높음 · 묶음 FB8 · 선행 FB1 — 컬럼 가드가 mutate 판정 경로에 의존)

### D05-002 · P0 · 승인 코멘트에 `'[전결]'` 문자열만 넣거나 기안 시 `meta.is_arbitrary` 를 심으면 남은 결재선을 통째로 건너뛰고 최종 승인된다

- **근본원인 축**: S9 상태전이 무결성 붕괴 — 결재·재고·구매의 권한 가드·원자성·CAS 부재
- **위치**: `lib/server-approval-transition.ts:506-514`, `app/api/approvals/transition/route.ts:31-41`, `lib/approval-submit-payload.ts:78-96`
- **병합**: D05-021(7차 A6-03 델타, 판정 OPEN)
- **결함**: 최종 승인 판정이 다음 두 줄에 전부 걸려 있다.
  ```ts
  const isArbitraryDecision = Boolean((item.meta_data)?.is_arbitrary || approveComment?.includes('[전결]'));
  const isFinalApproval = currentIndex === lineIds.length - 1 || isArbitraryDecision;
  ```
  `approveComment` 는 요청 body 의 자유 입력 문자열이 그대로 전달된 값이고(`transition/route.ts:31` `const reason = body?.reason ? String(body.reason) : null;` → `:41` `approveComment: action === 'approve' ? reason : null`), `meta_data.is_arbitrary` 는 기안 폼의 `extraMeta` 가 `...input.extraMeta`(`approval-submit-payload.ts:95`)로 통째 병합돼 저장된 값이다. 저장소 전체에서 `'전결'`/`is_arbitrary` 를 grep 하면 이 로직 2줄과 `ApprovalLineTimeline.tsx:137` 라벨 문자열, `ModSettlement.tsx:84` 문구뿐 — **전결 권한을 검증하는 상수도 함수도 존재하지 않는다.**
- **도달 경로**(재현):
  - 경로 A — 결재선상의 결재자:
    1. 결재선이 `팀장 → 원장 → 대표` 인 문서에서 1차 결재자(팀장) 계정으로 로그인한다.
    2. `POST /api/approvals/transition` 에 `{ approvalId, action:'approve', reason:'[전결] 확인' }` 을 보낸다. UI 의 승인 사유 입력창에 그대로 타이핑해도 동일하다.
    3. `server-approval-transition.ts:407-423` 의 actor 가드("현재 결재자 또는 실효 결재자/대리자/admin")는 정상 통과한다 — 이 가드는 타인 문서 승인만 막는다.
    4. `:506-510` 에서 `isArbitraryDecision=true` → `isFinalApproval=true` → 원장·대표 단계를 건너뛰고 문서가 최종 승인되며 `processFinalApprovalEffects` 가 즉시 발동한다.
  - 경로 B — 기안자의 사전 예약:
    1. 기안 폼이 `extraMeta` 로 넘기는 메타에 `is_arbitrary: true` 를 포함시킨다(`buildApprovalSubmitPayload` 가 화이트리스트 없이 병합, insert 정책 `SELF_OR_SAME_COMPANY` 에도 가드 없음 — `/api/d1/mutate` 로 직접 심을 수도 있다).
    2. 1차 결재자가 아무 코멘트 없이 평범하게 승인만 눌러도 `item.meta_data.is_arbitrary` 로 `isArbitraryDecision=true` 가 되어 잔여 결재선이 전부 생략된다. 결재자는 자신이 최종 승인을 했다는 사실조차 인지하지 못한다.
  - 확대 경로: `useApprovalBulkActions.handleBulkApprove` 가 하나의 코멘트를 선택된 문서 전부에 적용하므로, `'[전결]'` 코멘트로 일괄 승인하면 다건이 한 번에 결재선을 생략한다.
- **영향**: 1차 결재자(팀장급)가 원장·대표 결재를 건너뛰고 급여 인상·인사명령·연차 차감 후속 처리를 즉시 확정할 수 있다. 기안자는 그것을 사전에 예약할 수 있다. 결재선 자체가 권고 사항이 된다.
- **검증**: R2(V06·V12) 가 반증조건 2개를 모두 반증 실패했다. (1) `transition/route.ts:31-41` 의 actor 객체는 `id/name/company/isAdmin` 4필드만 담고 `permissions` 를 아예 전달하지 않아 서버가 전결 권한을 알 방법이 없다. (2) `meta_data` 는 서버에서 화이트리스트 정규화되지 않는다. 7차 인용 라인 506-510 을 원문 대조한 결과 **문자 단위로 동일**해 델타 판정 OPEN 이 정확하다.
- **수정 방향**: 전결을 별도 요청 필드(예: `action:'approve_arbitrary'`)로 분리하고 actor 의 전결 권한·직급을 서버에서 검증한 뒤에만 `isFinalApproval` 로 승격한다. 코멘트 문자열 파싱과 `meta_data.is_arbitrary` 신뢰는 제거한다. (난이도 S · 회귀위험 높음 · 묶음 FB8 · 선행 FB1)

### D05-003 · P1 · 2차 이후 결재자에게 위임이 설정돼 있으면 결재선에 없는 대리자 id 가 저장돼 문서가 관리자 포함 전원에게 영구 잠긴다

- **근본원인 축**: S9 상태전이 무결성 붕괴
- **위치**: `lib/server-approval-transition.ts:511-514`, `lib/server-approval-transition.ts:324-359`, `lib/approval-shared.ts:59-73`
- **결함**: 단계 진행 시 다음 결재자를 대리자 id 로 치환해 저장한다 — `const nextApproverId = nextLineApproverId ? (resolveEffectiveApproverId(nextLineApproverId, staffMap) || nextLineApproverId) : null;`(`:512-514`) → `current_approver_id: nextApproverId`(`:535`). 그런데 `meta_data` 에 `delegated_from_id`/`delegated_to_id` 를 함께 기록하지 않는다(`applyDelegationMeta` 는 '현재' 결재자에만 적용, `:151-153`). 다음 호출에서 `resolveStoredCurrentApproverId` 는 되돌릴 근거가 없어 대리자 id 를 그대로 반환하고, 그 id 는 `approver_line` 에 없으므로 `const currentIndex = lineIds.findIndex(...); if (currentIndex === -1) { return { … error: 'Current approver is not in approver line.' } }`(`:346-359`) 에서 즉시 실패한다. **이 검사는 `actor.isAdmin` 우회(`:407`)보다 앞에 있어 관리자도 처리할 수 없다.**
- **도달 경로**: 결재선 2번째 이후 결재자의 `staff_members.permissions.approval_delegate_id` 가 설정되고 위임 기간이 유효해야 발현한다(`approval-workflow.ts:270-291` active 조건). 그 구성에서 1차 승인 직후 해당 문서는 승인·반려 모두 `'Current approver is not in approver line.'` 로 영구 정지한다. 회수는 status 가 `'대기'` 라 가능하지만 결재 진행 자체가 불가능하다.
- **영향**: 대결(위임)을 켜둔 조직에서 문서 단위 데드락. 관리자 강제 처리 경로까지 막혀 회수 후 재기안 외에 복구 수단이 없다.
- **검증**: R2 가 반증조건 2개를 모두 반증 실패했다. `resolveApprovalLineIds` 는 `approver_line` 을 우선하고 `current_approver_id` 는 폴백일 뿐이며(`approval-shared.ts:47-53`), 단계 진행 updateData(`:534-541`)에는 `delegated_from_id`/`delegated_to_id` 가 없다. 추가로 PC 의 자동복구 경로(`syncDelegatedApprovalRouting`, `전자결재.tsx:705`)도 이 상태를 고치지 못한다 — 저장된 값이 이미 대리자 C 이고 C 에게 위임이 없으면 `effectiveApproverId === currentApproverId` 라 updates 가 비어 즉시 `return null` 한다. 발현에 대결 설정이라는 운영 구성이 필요해 P0 → P1 로 재조정.
- **수정 방향**: `current_approver_id` 에는 항상 결재선 원본 id 를 저장하고 대결은 판정 시점에만 `resolveEffectiveApproverId` 로 해석하거나, 대리자 id 를 저장할 때 `meta_data.delegated_from_id`/`delegated_to_id` 를 함께 갱신한다. `currentIndex === -1` 일 때 관리자에게는 폴백 경로를 준다. (난이도 M · 회귀위험 높음 · 묶음 FB8)

### D05-004 · P1 · 후속 처리가 부분 실패해도 `'completed_with_warnings'` 를 완료로 확정해 연차 차감·인사명령·증명서 발급 실패가 영구 미반영으로 굳는다

- **근본원인 축**: S9 상태전이 무결성 붕괴
- **위치**: `lib/server-approval-processing-helpers.ts:9-50`, `lib/server-approval-processing.ts:209-248`, `lib/server-approval-processing.ts:772-793`

- **영향**: 같은 사람이 같은 제목으로 올린 반복 기안(주간업무보고 등)이 문서보관함에서 서로를 덮어써 과거 결재 본문이 사라진다. 데이터가 300건을 넘어가면 반대로 같은 문서가 중복 저장된다.
- **검증**: 반증조건 불성립. 폴백 경로는 doc_number 유무와 무관하게 살아 있다 — 매칭 콜백은 양쪽 문서번호가 모두 있을 때만 번호를 비교하고, 후보 쪽 content 에 문서번호 라인이 없으면 곧바로 제목+기안자+회사 비교로 떨어진다. `document_repository` 에 `approval_id` 컬럼도 없어(`local-d1-schema.json`) 결정적 키로 대체할 수단이 현재 없다.
- **수정 방향**: `document_repository` 에 `approval_id` 컬럼(또는 결정적 id `approval-<id>`)을 키로 두고 그 값으로 단건 조회 후 upsert 한다. 제목 기반 폴백은 제거한다. (난이도 M · 회귀위험 높음 · 묶음 FB8)
