## 1. 이 문서의 사용법

**이 감사는 "리포트 먼저, 수정은 승인 후" 원칙으로 진행됐다. 지금까지 저장소 소스는 한 줄도 수정하지 않았다.**

아래 §2 의 각 묶음 앞에는 체크박스가 있다. **체크한 묶음 단위로만 수정이 진행된다.**

- 묶음은 **한 커밋 단위**로 설계했다. 같은 근본원인 축을 공유하고, 따로 고치면 서로를 되돌리거나 반쪽 상태를 만드는 항목들을 한데 묶었다.
- 묶음 안의 개별 항목만 골라 고치는 것도 가능하지만, **"왜 한 묶음인가"에 적힌 이유가 깨진다.** 부분 승인을 원하면 그 사유를 함께 알려 달라 — 부분 수정 시 남는 위험을 다시 산정해 회신한다.
- 각 묶음에는 **선행조건**이 있다. 선행 묶음을 건너뛰고 착수하면 오차단(권한이 있는 사용자가 막히는 것)이나 재작업이 발생한다. §3 의 권장 실행 순서가 이 그래프를 반영한 결과다.
- **§4 즉시 조치**는 승인 대기 없이 지금 할 수 있는 설정 변경만 모은 것이다(코드 로직 무변경 · 회귀위험 낮음). 별도로 체크할 수 있다.
- **§5 PLAUSIBLE 6건은 승인 대상이 아니다.** 추가 확인이 먼저다.
- **§6 REFUTED 24건은 수정하지 않는다.**

**왜 한 묶음인가** — 넷 다 **"게이트가 실패했을 때 무엇을 하는가"** 라는 한 가지 결정의 서로 다른 발현이다. 지금은 전부 fail-open(폴백해서 계속 진행)이고, 이걸 fail-closed 로 바꾸는 것이 유일한 근본 수정이다. 개별로 고치면 `mutate` 만 닫고 `tail` 은 열어 두는 식의 반쪽 수정이 반복된다 — 실제로 7차 A12-02 가 정확히 그렇게 반쪽으로 닫혔다(`D01-D05`). 또한 `findSensitiveFieldUsage` 를 query·mutate·tail 세 경로가 **공유**하도록 만드는 것이 이 묶음의 핵심 리팩터링인데, 이것은 한 번에 해야 한다.

**난이도 M · 회귀위험 높음 · 선행조건: FB13(정책 회귀 e2e 복구) 선행 권장**

> 회귀위험이 높은 이유: fail-closed 로 바꾸면 **지금까지 폴백으로 통과하던 정상 요청도 막힌다.** 어떤 정상 요청이 폴백에 의존하고 있었는지는 테스트 없이 알 수 없다. 그래서 FB13 으로 보안 회귀 스펙을 먼저 살려야 한다.

**검증 방법**
```bash

npm run dev            # 별도 터미널
npm run verify:policies

# 2) FB13 이후 되살아난 보안 회귀 스펙
npx playwright test tests/security.spec.ts tests/security/d1-policies.spec.ts

# 3) P0 4건 재현 시도가 전부 403 으로 실패하는지 수동 확인
#    - mutate delete + where company_id in [타사 × 100]         → 403
#    - query/mutate table: daily_closure_items                  → 403
#    - mutate update staff_members where password like '$2a$%'  → 400 (민감컬럼 사용 거부)
#    - GET /api/realtime/tail?tables=staff_members:resident_no=eq.x → 400
```
