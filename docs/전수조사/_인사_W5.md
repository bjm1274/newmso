## ★ 특별임무 답변

### (1) 근태관리메인(2196) 단일책임 위반 / 죽은코드
**SRP 심각 위반.** 단일 컴포넌트가 다음을 전부 보유:
- 근태 조회/집계 (메인 580~639, 445~636)
- 근무표(roster) 편성: work_shifts/shift_assignments 로드·upsert (641~721)
- 근무 교환(swap) 요청·승인·반려 (798~846)
- 근로기준법 검증(주52h, 연속근무) (849~903)
- 근무표 결재 요청/승인/반려 워크플로우 + 레거시 approvals 폴백 (905~1174)
- 5개 뷰 인라인 렌더 (1184~2196)

`/skill jm` 기준(파일당 단일책임·~500줄)을 4배 초과.

### (2) 근태달력뷰 3파일 분할 적절성
파일 자체의 분할 설계는 **적절**(`근태달력뷰.tsx` 헤더 주석에 책임 분리 명시: orchestrator / .day=일별패널 / .range=주·월별패널, JM SRP 준수). **그러나 트리오 전체가 죽은코드** — 메인이 import하지 않고 자체 인라인 달력(메인 2064줄, 로컬 `buildMonthCalendarCells` 338줄)을 렌더하므로 분할의 적절성과 무관하게 셋 다 미사용.

### (3) attendance ↔ attendances 테이블 혼용
**혼용 없음.** live 코드(메인·일괄수정모달)는 전부 `attendances`(work_date) 사용. 정본 별개 테이블 `attendance`(date)는 이 클러스터에서 미사용. 죽은 뷰 파일들은 DB 쿼리 자체가 없음. → 테이블 혼용 문제 **해당 없음**.

### (4) 자체 roster 로직 vs 별도 roster 클러스터 중복
**`app/main/기능부품/roster/` 클러스터(60+ 파일) 전체가 죽은코드 확정.** 클러스터 밖에서 import하는 파일 0건:
```
rg "기능부품/roster|../roster/|RosterWizardModal|RosterPlannerDashboard" app -g '*.tsx' -g '*.ts' -l | grep -v 기능부품.roster  →  (빈 결과)
```
실제 3교대/자동편성 UI는 `간호근무표.tsx`(NurseSchedule, 526줄)이며 이 또한 roster 클러스터를 import하지 않음(자체구현). 근태관리메인의 roster 결재/swap/검증 로직은 roster 클러스터와 **별개 구현**(중복 아님, 서로 무관). 즉 roster 클러스터 + `근무표자동편성-engine-*.ts`/`근무표자동편성-types.ts`는 통째로 제거 가능한 고아 클러스터.

### SEC 보안
- **SEC-1 [낮음]** 권한 분기는 `user.position`/`role`/`permissions` 클라이언트 값에 의존(723~733, `canCreateRoster`/`canApproveRoster`). 결재 승인 자체는 `/api/roster/approval-request` 및 supabase mutate를 거치므로 서버검증 여부는 API 측 점검 필요(범위 밖). UI 게이팅만으로 충분치 않을 수 있음.

### Q 유사기능
- **Q-1 [중]** 인라인 5개 뷰(메인) vs 분리 뷰 7파일(죽음) = 동일 기능 두 벌. 메인 인라인 달력 ↔ `근태달력뷰` 트리오, 메인 일정뷰 ↔ `근태일정뷰` 페어, 메인 대시보드 ↔ `근태대시보드뷰`/`월간근태통계` 등.

### K 한글깨짐 / U 불필요 / DBG 디버그
- **K**: replacement char(�) 0건. `LEGACY_APPROVAL_*`의 `\uXXXX` 표기(35~37)는 의도적 유니코드 이스케이프(대기/승인/반려), 깨짐 아님.
- **DBG**: `console.log`/`console.debug` 0건(클러스터 전체). `console.error`만 존재(정상 에러 로깅).
- **U**: 죽은 뷰/클러스터 제거 시 자연 해소(X-1·X-2와 중복).

### 정본 검증 노트
- `work_shifts.is_active`는 `integer().default(1)`(schema 2399). 메인 662 `.eq('is_active', true)`는 **안전** — `lib/db/get-binding.ts`:84 `if (typeof p === 'boolean') return p ? 1 : 0;`가 바인딩 단계에서 1/0 변환. 무음실패 아님.
- `shift_assignments` upsert `onConflict: 'staff_id,work_date'`(717·1045)는 정본 `uniqueIndex` 부재 주의: schema 1922~1934 `shift_assignments`에는 (staff_id, work_date) **uniqueIndex가 없음**(비유니크 index만). onConflict 대상 유니크 제약이 D1에 없으면 upsert가 의도대로 동작 안 할 수 있음 → **추가 점검 권장(중)**.
