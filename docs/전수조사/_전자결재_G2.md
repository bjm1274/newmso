## 분류별 발견

### SEC 보안 (제출검증·XSS·인쇄 HTML 이스케이프)

- **[높음] 공문발송 권한 검증 부재 (제출 검증)** — `ApprovalComposerView.tsx:79,144,253,265` 의 `PERMISSION_KEYWORDS=['공문발송']` 및 "권한 필요" 배지는 **표시 전용**이다. 실제 제출 경로 `useApprovalSubmit.ts:523` 은 `formType === '공문발송' && !officialDocumentRequest` 로 *페이로드 존재*만 검사하고, 사용자가 공문발송 권한이 있는지는 검증하지 않는다. `request_category: 'official_document_dispatch'` 만 부여(`:610`). → 권한 없는 사용자도 공문발송 기안 상신 가능. Grep 확인: `useApprovalSubmit.ts` 내 `공문발송` 매치는 `481/523/606/610` 4건뿐, 권한 가드 없음.
- **[정보] XSS — 인쇄 HTML 이스케이프는 대체로 양호** — `approval-print-utils.tsx` 및 `ApprovalMetaPanels.tsx` 의 모든 사용자 값은 `escapeHtml()` 경유. 본문 줄바꿈도 `escapeHtml(...).replace(/\n/g,'<br>')`(`:384`)로 이스케이프 후 치환이라 안전. 단, **design 객체의 URL 계열**(`sealImageUrl`/`backgroundLogoUrl`)은 `escapeHtml`만 적용(`:273,320,359`) — 속성값 이스케이프는 되나 `javascript:` 스킴 차단은 없음. design은 관리자 템플릿 출처라 위험은 낮으나 의심(스킴 화이트리스트 권장).
- **[정보] 상세 미리보기 iframe** — `ApprovalDetailModal.tsx:224` `srcDoc={detailPreviewHtml}` 는 동일 `buildApprovalPrintHtml` 결과라 이스케이프 보장. sandbox 속성은 없음(의심, 방어적으로 `sandbox` 권장).

### D 중복

- **[높음] useApprovalSubmit / useApprovalComposeDraft 책임 거대화** — `useApprovalSubmit.ts` 774줄, `useApprovalComposeDraft.ts` 575줄. submit 훅 한 콜백(`submitApproval`, `:478~751`)에 양식별 검증(연차/연차계획서/공문/보고서/물품)·재고 리뷰·문서번호 생성·insert·알림·문서보관함 동기화·중복확인이 모두 집중. 양식별 validation은 별도 맵/함수로 분리 가능. (jm 원칙 500줄 초과)
- **[높음] escapeHtml 3중 정의** — `전자결재-utils.ts:162`, `인사관리서브/document-print-utils.ts:7`, `마이페이지/certificate-print-utils.ts:24` 에 동일 구현 3벌. 공용 모듈 1곳으로 통합 필요.
- **[중간] 근무표 렌더 로직 2벌** — `ApprovalMetaPanels.tsx` `renderRosterInfoHtml`(`:449~550`, HTML 문자열)과 `RosterRequestInfoPanel`(`:552~653`, JSX)이 `staffRowMap`/`resolveBand`/`getStyleForBand`/날짜배열 구성 로직을 거의 그대로 중복. band 분류·일자 매핑은 공용 헬퍼로 추출 가능.

- **[중간] insert 무한 루프 가능성(의심)** — `useApprovalSubmit.ts:143~158` `insertApprovalWithLegacyFallback` 는 `while(true)` 로 누락 컬럼을 제거 재시도. `APPROVAL_OPTIONAL_INSERT_COLUMNS=['company_id','approver_line','doc_number']` (constants `:50`) 는 정본 스키마에 **모두 존재**(schema `approvals` `company_id`/`approver_line`/`doc_number`). 정상 환경에선 1회 종료되나, 컬럼명이 정본과 달라 무음실패하는 D1 프록시 특성상 `isMissingColumnError` 가 다른 에러를 오탐하면 루프 탈출 보장 약함(반복 횟수 상한 없음). 방어적 상한 권장.
- **[낮음] console.error 직접 사용** — `useApprovalSubmit.ts:233,336,343,350,693,699` 등 다수 `console.error` (프로젝트 `logger` 혼재). `:450`만 `logger.warn`. 일관성 부족.
- **[낮음] 알림 insert 실패 시 로컬 폴백 fetch** — `useApprovalSubmit.ts:212~231` `error.message`에 'fetch' 포함 시 localhost에서만 `/rest/v1/notifications` 직접 POST 후 조용히 return. 운영 환경 실패는 `console.error`만(`:233`) — 사용자 미고지(설계상 의도일 수 있음, 의심).
