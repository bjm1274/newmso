## 3. 검증 쿼리 (Step 1·2 완료 후 확인)

```sql
-- 직종 시드 확인 (13건 기대)
SELECT count(*) AS job_categories FROM job_categories;

-- 직종-교육 매핑 시드 확인 (14건 기대: 법정 9 + 권장 5)
SELECT count(*) AS required_trainings FROM job_category_required_trainings;

-- 활성 직원 leave_balances 초기화 확인
SELECT count(*) AS active_balances
FROM leave_balances lb
JOIN staff_members sm ON sm.id = lb.staff_id
WHERE sm.is_active = true;

-- 면허 백필 결과 확인 (기존 staff_members.license 보유자 수와 일치해야)
SELECT count(DISTINCT staff_id) AS migrated_licenses FROM staff_licenses;

-- 근무유형 백필 결과 (기존 staff_members.shift_id 보유자 수와 일치해야)
SELECT count(*) AS primary_shifts FROM staff_shift_assignments WHERE is_primary = TRUE;

-- companies.leave_policy 컬럼 추가 확인
SELECT column_name FROM information_schema.columns
WHERE table_name='companies' AND column_name IN ('leave_policy','unused_leave_compensation','fiscal_year_start_month');
```

## 4. 롤백 노트 (실패 시)

전 SQL이 **idempotent**라 재실행으로 복구 가능. 다만 다음만 주의:

| 위험 | 대응 |
|---|---|
| `register_staff_full` RPC 함수 정의 오류 | `DROP FUNCTION register_staff_full(...)` 후 010 마이그레이션 재실행 |
| 백필 SQL 중간 실패 (트랜잭션 X) | 재실행 — 모두 `ON CONFLICT DO NOTHING` 또는 존재 체크 패턴 |
| Seed 행 중복 | 시드 SQL 자체가 `ON CONFLICT (id) DO NOTHING` 또는 `WHERE NOT EXISTS` 사용 |

DROP / TRUNCATE 절대 실행 금지 — 기존 데이터 보존.

## 7. 자주 묻는 질문

**Q. 통합 파일(`run_2026-05-11_ALL.sql`) 대신 마이그레이션 9개를 각각 실행해도 되나?**
A. 가능. 순서는 `001 → 002 → 003 → 004 → 005 → 006 → 007 → 010 → 020 → seed A → seed B`. 통합 파일이 더 간단함.

**Q. 백필 SQL을 안 실행하면?**
A. 기존 직원의 면허·근무유형은 신규 테이블에 이전되지 않음. 자격안전센터·근무현황 화면에서 빈 값으로 표시될 수 있음. **반드시 실행 권장**.

**Q. 본 SQL이 본 디자인 리디자인 작업과 충돌하나?**
A. 충돌 없음. v2 라우트는 더미 데이터, v1 라우트는 본 SQL의 신규 기능 사용. 두 영역 격리됨.

**Q. 재배포 시 다시 실행해야 하나?**
A. 아니. 한 번 적용된 SQL은 idempotent라 재실행해도 무해하지만 불필요. 신규 마이그레이션 파일이 추가될 때만 실행.
